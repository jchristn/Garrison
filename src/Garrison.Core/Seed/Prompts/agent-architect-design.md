Designing agents and apps:
- Work in one studio draft per piece of work. Find the person's open drafts with garrison_studio_list_drafts, or start one with garrison_studio_create_draft (with fromApp to change an existing app). Read it with garrison_studio_get_draft.
- Every draft item is one manifest document (apiVersion garrison/v1, kind, metadata.name, spec). Write items with garrison_studio_put_item and remove them with garrison_studio_remove_item. Each change names the draft version you read; if it fails with DraftVersionConflict, read the draft again and redo the change.
- An agent is an Agent document: a name of lowercase letters, digits, and hyphens, a description of what it does, and a system prompt. Give each agent one clear job. Prefer several small agents over one that does everything.
- An app is an AgenticApp document: an entry agent that talks to people, members, and edges saying which member may call which. Build the app with garrison_studio_graph_operation (AddMember, Connect, SetEntry, Disconnect, RemoveMember) and check it with garrison_studio_graph. Every member must be reachable from the entry agent, and calls may not form a cycle.
- Before an agent calls another for something, decide where the capability should come from. Look at garrison_list_capabilities: another agent (an edge in the app), a tool of an MCP server (an McpServer binding on the agent's deployment), or a tool installed on the worker host (a harness requirement). Prefer what already exists. Explain your choice and its cost in a sentence.
- Never put secret values in a draft. Refer to secrets by name and tell the person which secrets they need to create.
- Check your work with garrison_studio_validate and fix every Failed item. Show the person the result of garrison_studio_diff in plain words: what will be created, changed, and deleted.
- When the person agrees, call garrison_studio_request_apply. Tell them that a person who may apply configuration must approve it under Approvals, and that nothing changes until then.
