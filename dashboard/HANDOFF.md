# Dashboard handoff

A summary of what the Garrison operator console contains, how it is checked, and what it does not do yet. The plan (`GARRISON_PLAN.md`, Phase 5) has the task-level history.

## Navigation

Eleven sidebar hubs in three sections, defined in one place (`src/config/navConfig.js`). Hubs with more than one page use tabs synced to `?tab=`. Every route from before the consolidation redirects to its hub and tab.

| Section | Hub | Tabs | Who sees it |
|---|---|---|---|
| Operate | Home | none | everyone signed in |
| | Invoke | none | everyone signed in |
| | Runs | Runs, Conversations, Pipeline runs, Queue | everyone signed in |
| | Approvals | Approvals, Stage reviews (one badge with both pending counts) | everyone signed in |
| | Analytics | none | everyone signed in |
| | Agents | Agents, Deployments, Pipelines, Triggers, Capabilities, Apps, Agent Studio | everyone signed in |
| Platform | Configuration | Harness Profiles, Prompt Templates, MCP Servers, Secrets, Workspaces, Artifact Stores, Manifests | everyone signed in |
| | Fleet | Worker nodes, Control plane, Node Pools | Node Pools: system administrators |
| Administration | Access | Tenants, Users, Credentials, Roles, Assignments | Tenants: system administrators; the rest: administrators |
| | Monitoring | Request History, Audit, API Explorer | everyone signed in |
| | System | Settings, About | Settings: administrators |

The sidebar only hides what the table above lists. Everything else is enforced by the server: a page a user may not read shows a permission message instead of data.

Detail pages: `/dashboard/runs/:id`, `/dashboard/conversations/:id`, `/dashboard/pipeline-runs/:id`, `/dashboard/agents/:id`, `/dashboard/prompt-templates/:id`, `/dashboard/approvals/:id`, `/dashboard/studio/:id`. They highlight their hub in the sidebar.

Approvals (P12.3) is the inbox for permission requests from deployments with approvals turned on. The sidebar item shows how many are pending, read from `GET approvals?status=Pending&maxResults=1` every 30 seconds and updated at once by the WebSocket `approvals` channel when the live connection is up; it disappears for callers without Approval Read. The inbox opens on Pending and filters by status, agent, decision source, and run ID; Allow and Deny open a dialog with a reason and "remember as rule" (an editable pattern prefilled from the suggested rule). A 409 `ApprovalNotPending` and a 403 end in a toast. The detail page shows every field, the redacted input preview, the matched and suggested rules, and links to the run, agent, and deployment. Run detail shows an "Awaiting approval" badge and banner, the approval wait in telemetry, an Approvals tab with Allow and Deny, and labels `ApprovalRequested` and `ApprovalDecided` events in the transcript with a link to the approval. The deployment form has an Approvals step: the on switch, the default action, the timeout and its decision, an ordered rules editor that keeps rule IDs, and a "Test a tool call" panel that posts to `approval-check` (saved deployments only).

Pipelines (P12.9) add tabs, not sidebar items (decision D-048). Agents > Pipelines lists pipeline definitions (stages as an agent chain, review gates, time limit, version) with Start (input text, one `Idempotency-Key` per dialog, then the new pipeline run), Preview prompts (`POST pipelines/{id}/preview` with sample input and a sample output per earlier stage), and View pipeline runs; Duplicate keeps stage references. The form has an ordered stage editor: add, remove, and reorder stages; per stage an agent, an optional deployment of that agent (empty means weighted selection), an optional Task handoff template with an optional pinned version, handoff character limit, maximum attempts, continue on failure, and a review gate with timeout, timeout action, and maximum revisions, plus run parameters. Server errors keyed `stages[i].field` show on their stage. Runs > Pipeline runs filters by status, pipeline, and time (the server has no outcome filter); a pipeline run's page shows the summary, the input, the pending review with Approve, Request changes, and Reject, and the stage timeline (status, executions, attempts, revisions, blocked reason, stage runs linked to Run detail, and reviews), with Cancel, Retry, and Delete for finished runs. It follows the WebSocket channel `pipeline-run:{id}` and polls every 3 seconds when that is not available. Approvals > Stage reviews opens on pending reviews; the decide dialog requires a comment for Request changes, shows revisions left, keeps a 409 `RevisionLimitReached` in the dialog, and ends a 409 `ReviewNotPending` in a toast. The sidebar badge adds pending approvals and pending stage reviews (`approvals.changed` carries `reviewsPending`). Run detail links a stage run to its pipeline run, and the runs list has a hidden Pipeline run column and accepts `?pipelineRunId=`.

Invoke's response card has two tabs (P5.52). Preview streams the assistant text over SSE and renders it as Markdown, with reasoning in a collapsed block, tool calls as chips, and live timing; it stays selected when the run ends and points to Response, which shows the result text, structured output, outcome, errors, and telemetry. Sending again clears the card and drops late frames from the previous run. Sending again also cancels the run still in progress, and leaving Invoke (route change, reload, or tab close via `pagehide`) cancels it with `fetch` `keepalive` (a beacon cannot carry the `Authorization` header), unless the "Stop the run when I leave" setting next to Send is off (`localStorage` key `garrison_invoke_stop_on_leave`). Cancel reads "Cancelling..." until the run reports Cancelled. A deployment that allows a `timeoutSeconds` override gets a Time limit field with presets, validated against the override's range and `Runtime.MaxRunSeconds` when settings are readable (P3.15). Run guard stops (`RepetitionDetected`, `NoProgress`, `OutputLimitExceeded` from `maxAssistantChars`) get a `RunGuardNotice` in Preview, Response, and Run detail; the deployment form's Placement and limits step has Repetition guard, Maximum assistant characters, and No-progress timeout with the cluster defaults shown. Model output is rendered by `MarkdownView` (marked for GitHub-flavored Markdown, DOMPurify for sanitizing: no scripts, event handlers, frames, forms, inline styles, or URL schemes other than http, https, and mailto), which Run detail uses for the result too, with a raw text toggle.

Runs > Conversations (P12.1) lists conversations from `GET /conversations` (title, agent, Working or Idle, turns, affinity node, fallbacks with the last reason, last activity; filter by agent, also from `?agentId=`) with Continue (Invoke pre-filled with `?conversationId=`) and View turns as runs (`/runs?conversationId=`). A conversation's page shows the summary, every turn from `GET /conversations/{id}/runs` (status, outcome, whether it resumed the session or fell back and why, input and result previews), a box that sends the next turn with `conversationId`, and Delete; a busy conversation disables Send, and 409 ConversationBusy (and the other 409 conversation codes) show translated messages. Invoke has a Conversation choice (single run, start a new conversation, continue one); after the first turn it switches to continuing the new conversation, and while continuing the deployment is fixed to the conversation's. Run detail shows the conversation, turn, session (resumed, fresh after a fallback with the reason, or first), resumed session, and affinity node. Agent detail links to the agent's conversations. Deployments offer the ConversationFallback prompt role.

Agents > Capabilities (AD4.8) is the capability catalog from `GET /capabilities`: agents, MCP tools, and harness built-ins in one table with kind, origin (Derived or Manual, plus Shared for built-ins every tenant sees), summary, source, hints, and tags. The server returns the whole filtered catalog in one response, so the page sorts and pages it in the browser; kind and tag filters and the name search go to the server, the origin filter stays in the browser. The source cell links an agent entry to the agent's page, an MCP tool to the MCP Servers tab searched for its server (with the tool name), and a built-in to its harness profile with the node label a run needs (`garrison.io/tool-pandoc=true`). Hints read "Median, p90, cost per run" when Known and show an Unknown badge otherwise; a value is never shown as zero for lack of data. Entries whose last refresh failed carry a badge, a banner counts them, and their details lead with the warning. Derived entries keep Edit and Delete in the row menu, disabled, with a tooltip saying where to change the source; there is no bulk delete. Manual entries are created and edited in a form (name, kind, summary, optional source agent or MCP server and tool, tags, node label requirements, input and output schemas), with `InvalidJsonSchema` shown on the schema field and `NameConflict` in a toast. Refresh opens a dialog that refreshes every MCP server or one, then lists the totals and one row per server with its error. Harness profiles have a Tool probes editor (name, executable, one allowed argument, description) checked against the server's rules, agent revisions list their capabilities in a Capabilities column with an editor for the draft, and a run blocked with `NoToolWorker` names the tools it waits for.

Agents > Apps (AD6.11) lists agentic apps from `GET /apps` (name, the app URL with copy and Open, entry agent, member count with the names in the tooltip, live environment, sign-in mode, and status) with the name search, create, and delete after a confirmation. The editor has five steps: the app (name, URL slug, description, active); members and calls (agents with a role note, the entry agent picked from the members, calls with a parallel-calls switch that is on for new calls, and a read-only SVG graph that lays members out by the longest call path from the entry agent and outlines unreachable ones in red); environments (the entry deployment per environment, offering only the entry agent's deployments in that environment, and the live environment); sign-in and link (auth mode, anonymous use, operator detail, and the shareable `{origin}/apps/{slug}/` link, since nginx serves the app UI next to the console, with a sentence on who can sign in); and branding (display name, a logo picked from agent assets, primary and accent colors with a picker, welcome text). The browser checks names, slugs, colors, duplicate members, the entry agent, calls between members, cycles, and reachability, worded like the server's field codes; server refusals are translated and shown on their field, and the form opens the step that holds the first one (`InvalidEntryDeployment` on an environment row, `UnknownEnvironment` on the live environment, 409 `AppSlugTaken` on the slug, `UnreachableMember` with the member names under the calls). The row menu opens Delegation (each member's graph allow list, mode, and depth against the published ones, with drift; Write drafts posts the plan and shows the draft written or `DraftConflict` per member; nothing is published) and Revisions and promotion (take a revision with a change note, publish a draft after a confirmation, and promote a published revision with source, target, Allow skipping, and a note; a 409 `NoTargetDeployments` names the member in the dialog). The tab reads the caller's own effective permissions (`GET users/{id}/permissions`; administrators skip the call): Add, Edit, Delete, Write drafts, Take revision, Publish, and Promote stay visible but disabled with a tooltip naming the missing permission (Create, Update, Delete, or Execute on Agentic app, Execute on Promotion). Unknown permissions disable nothing; the server stays the judge. The Japanese catalog passed the 500 kB chunk warning, so each locale's tooltips now build into their own chunk.

The console presents itself as Garrison Agent Studio (AD12.12): the sidebar header reads "Garrison" with "Agent Studio" under it (the tooltip carries the positioning line), page titles end in "| Garrison Agent Studio", and `index.html` has the same title and a matching meta description. The product name stays in English in every locale; sentences use each locale's existing word for the studio. Empty lists of agents, deployments, and apps add a sentence and an Open Agent Studio button next to Add, and Home's empty-tenant callout has Open Agent Studio next to Run setup. A tenant whose only agent is the seeded `agent-architect` counts as empty, both for opening the setup wizard on first sign-in and for that callout. System > About (the Server Info view, `/dashboard/system?tab=server-info`) leads with the product: name, positioning line, the server and dashboard versions, and links to the documentation, the Agent Studio guide, usegarrison.ai, and the repository.

The setup wizard has an Agent Studio step after the credential (AD9.5, AD9.9): the same fields as the studio's New architect dialog (`components/studio/ArchitectFields.jsx`, loaded with the studio chunk only when the step opens): name, harness profile, model, and architect prompt from `GET studio/architect-prompts` (built-ins first, `builtin/agent-architect` preselected) with a rendered preview and a link to clone it. Create the architect posts `POST studio/architects` with the name, harness profile, model, and `architectPromptTemplateId`; Skip this step goes on to the sample agent exactly as before. Going back after creating shows the architect instead of the form, so a second click does not create a second one.

Promotion and rollback of an app (AD9.6) live in one panel (`components/AgenticAppReleasePanel.jsx`) shown by the Apps tab's row action Environments and by the studio draft's Release tab (for each app the draft builds, read live with `GET apps/{name}`; before the draft is applied it says to apply first). It shows the app URL and live environment; a table of every member (entry agent first) with its deployments per environment, each with its pinned revision (or Latest) and its environment overrides (secret values hidden); and, for a chosen pair of environments, whether each member is the same, differs in revisions, overrides, or both, or has no deployment in the target (with a warning naming those members, since the promotion would fail). Promote opens the app promote dialog preselected with that pair; the promotion history comes from `GET promotions?appId=` with Rollback (and a note) on each applied promotion. Promote and Rollback need Execute on Promotion for the target environment (`holds` with that environment as the resource); without it they stay visible but disabled, with a tooltip naming the permission, the environment, and the Releaser role.

`tests/e2e/studio.spec.js` runs the whole studio flow (AD12.11) on a stateful mock (`tests/e2e/studioFlowMocks.js`): an empty tenant opens the wizard, which creates the architect with `builtin/agent-architect-guided`; the architect builds a two-agent app in a new draft over two mocked turns; the `DraftApply` is allowed inline; the Release tab shows the app live in dev with its URL; the app is promoted to staging and rolled back, each step checked against what the browser sent and what the page shows. Other cases cover the default prompt, skipping the step, and a caller without Execute on Promotion. The app UI half (a two-turn conversation that writes a file, then its download) is `app-ui/tests/e2e/studioApp.spec.js`.

Agents > Architects (`views/architectConfigs.jsx`, a ResourceView page) lists the tenant's agent architects one page at a time from `GET studio/architects` with their harness profile, model, architect prompt (with its pinned version), and status, and creates, edits, and deletes them (`POST`, `PUT`, `DELETE studio/architects`). The form preselects the first harness profile and the default prompt; a taken name (409 `NameConflict`) and an invalid prompt show on their fields. Row actions open the architect prompt manager (`ArchitectPromptPanel`, lazy-loaded with the studio chunk) for that architect and its deployment on the Deployments tab for the settings the architect routes do not change. `tests/e2e/architects.spec.js` covers the page.

Agents > Studio (AD7.10, AD7.16, AD9.2, AD9.3) is a tab until AD-023 (a sidebar item of its own) is confirmed. The list shows studio drafts from `GET studio/drafts` (your own by default, `mine=true`; All shows every draft you may read) with the title search sent to the server and status chips (Open, Pending approval, Applied, Discarded) applied in the browser, because the server has no status filter. New draft takes a title and optionally an app to start from (`fromApp`); Discard asks first. A draft opens its workspace at `/dashboard/studio/:id`, which follows the WebSocket channel `studio-draft:{id}` (and polls every 5 seconds without it), refreshes the items, graph, diff, and version on each `studio-draft.changed`, and says which items moved. Its tabs: Architect, a chat with one of the tenant's active architects (`GET studio/architects?activeOnly=true`; architects are reusable across drafts and managed on Agents > Architects, which the tab links to) through the conversation API, where the first message carries `[Studio draft {id}: {title}]` before the text and replies are polled until the turn ends; the conversation is remembered per draft in `localStorage`. New architect creates one (`POST studio/architects`; `agent-architect` is looked up by name only to warn when the tenant has none) with a harness profile, a model, and an architect prompt from `GET studio/architect-prompts` (built-ins first, `builtin/agent-architect` preselected), a rendered preview, and a link to clone the prompt (`architectPromptTemplateId`). Items lists kind, name, operation, and a Stale marker from the diff, with a monospace YAML editor that saves with the version read; a 409 `DraftVersionConflict` reads the draft again, keeps the text, and names the items added, edited, and removed and whether the edited item itself changed. Graph is the canvas (AD8, below). Diff and apply shows Create, Update, Delete, Unchanged, or Failed per item with field changes, Validate, and Request apply with the version; the resulting `DraftApply` approval shows inline, and a caller holding Update on Approval and Create on Manifest decides it there (403 `ApproverLacksPermission` and 409 `DraftStale` are translated). Playground runs turns through `POST studio/drafts/{id}/playground/invoke` (agent defaults to the target app's entry agent), continues the conversation, links each turn to Run detail (run tree, fan-out groups, files), and downloads the turns as Markdown. Release is the AD9.6 panel described above. Compile preview picks a deployment and optionally a revision and environment and shows the command line, placed asset paths, and the file space mount. Architect prompt (`components/studio/ArchitectPromptPanel.jsx`) lists built-in and tenant architect prompts, clones (the Prompt Templates clone dialog), edits name, description, and body with a render preview and version history (diff and restore), resets built-ins, deletes (a 409 `PromptTemplateInUse` names the deployments), and selects the prompt for the current architect (`PUT studio/architects/{id}/prompt`) with a note that it takes effect on the next turn; built-ins keep Edit and Delete disabled with a tooltip saying to clone. Actions the caller lacks the permission for stay visible but disabled with the missing permission as the tooltip, as on the Apps tab. The studio components build into their own `studio` chunk; `MarkdownView` moved to the `markdown` chunk and `CloneTemplateModal` to `revisions` so the studio never imports from the views chunk.

The studio canvas (AD8.2 to AD8.7) replaces the read-only Graph tab. It is React Flow (`@xyflow/react` 12.12.0) with the YAML library (`yaml` 2.9.1) and the canvas panels in their own lazy `canvas` chunk (about 344 kB), loaded only when the Graph tab opens. It shows one app at a time (a picker when the draft has several, remembered per draft in `localStorage`), agents as nodes with Entry, In draft, Deleted, and Unreachable tags and their capabilities, and calls labelled with delegation depth (dashed for one call at a time). Every change is a request: `POST studio/drafts/{id}/graph-operations` (AddMember from a field with the tenant's and the draft's agents, RemoveMember after a confirmation, Connect by dragging between handles or from the toolbar, Disconnect, SetEntry, and MoveNode after a 400 ms pause in a drag or arrow-key move) or `PUT .../items/{kind}/{name}`, sent one at a time with the newest version known. Keyboard: agents are focusable in reading order; C starts or finishes a call, Enter finishes one, E sets the entry, Delete removes, arrow keys move a selected agent, N jumps to Add agent, Escape cancels a call, and a connect bar offers the callee as a list. Calls are buttons in the outline under the drawing (Delete disconnects, F toggles fan-out), because React Flow renders edges before nodes and focusable edges would put every call ahead of the agents. The outline's first paragraph (counts, entry agent) is the canvas's `aria-describedby`, and each change is announced in a polite live region. The side panel edits the app (entry, description, sign-in, anonymous use, branding), the selected call (fan-out at once, depth read-only), or the selected agent: an Agent tab (description, input and output schema as JSON, asset pins, capabilities, and the System prompt per environment as a read-only list) and a Runtime tab (one Deployment item at a time: model, effort, timeout, maximum turns, budget, System template and pinned version, approvals and rules; live deployments of the agent can be brought into the draft from a manifest export). Panels rewrite only the keys they own (`utils/manifestYaml.js`), keep the person's edit when the draft changes underneath, check JSON and numbers in the browser, show server field codes on their field, and show the diff's failure for the item (for example `InvalidJsonSchema`). A 409 `DraftVersionConflict` reads the draft again and names what changed; panels keep their fields, a refused graph operation gets Try again, and a refused move is retried once silently. Live updates come from the `studio-draft:{id}` channel or polling. Tests: `src/tests/studioCanvas.test.js` (YAML rewriting, graph mapping, summaries), `tests/e2e/canvas.spec.js` on a stateful mock (`tests/e2e/canvasMocks.js`), canvas contexts in the tooltip audit, and an axe pass in light and dark plus a focus-order check in `accessibility.spec.js`. `tests/e2e/docsScreenshots.spec.js` regenerates the `docs/images/studio-canvas*.png` screenshots when `GARRISON_DOCS_SCREENSHOTS=1`.

Run detail's Child runs tab is a run tree (AD5.8). Children a run started with `garrison_fan_out` sit under their fan-out group, oldest group first, from `GET runs/{id}/fan-out-groups`. Each group shows its status with the reason it ended (translated when the server text matches a known template), the join policy with the quorum, finished, succeeded, and total members, cost and tokens against `maxCostUsd` and `maxTokens` (with a bar when a budget is set), the deadline, the labels still running or failed, and a table of members with label, agent, status, usage, and a link to the member's run. A running group follows the WebSocket channel `fan-out:{groupId}` and polls `GET fan-out-groups/{id}` every 5 seconds when the channel is not available; Cancel group asks first and then posts `fan-out-groups/{id}/cancel`. Children outside any group follow as a plain list. A member run's detail shows its fan-out group, linked to the parent's run tree at `?tab=children&group={groupId}`, which opens the tab and highlights that group.

Fleet > Control plane (P10.19) lists the control-plane replicas from `GET /v1.0/api/control-nodes`: name with a Leader badge, translated status (Starting, Ready, Draining, Offline), version, schema version, backplane, uptime, heartbeat age (highlighted with a Stale badge when a replica that is not Offline has been silent for more than 15 seconds), active requests, open streams, held long polls, and address. It is read-only, refreshes every 15 seconds, and says which replica answered the list (`respondingNodeId`). A row opens a detail with every field from a fresh `GET /control-nodes/{id}`. With Grafana configured, each replica links to the Garrison overview dashboard filtered with `var-node`. The worker tab is still the hub's default, so existing links to Fleet land on worker nodes.

Home shows "Control plane ready x / y" next to "Nodes ready" (from the overview's `controlNodesByStatus`; the tooltip names the leader from `leaderNodeId`, and the card turns amber when no replica leads). The Nodes panel has two sections, Control plane and Worker nodes, each with a link to its Fleet tab. System > About links the answering replica (`nodeId`) to the Control plane tab; the top bar does not show it, because server info is cached once per session and a load balancer can send the next request elsewhere.

## Sign-in and the server

The sign-in page has no Server URL field. The console uses `window.GARRISON_CONFIG.apiUrl` from `/config.js` when the image sets `GARRISON_API_URL`, otherwise the page's own origin, which nginx (or the Vite dev server) proxies to the API; `defaultServerUrl()` in `src/utils/constants.js` decides. The server in use is shown in small text under the form and as Server in use on System > About. A "Use a different server" link reveals the field only when the override is available (`customServerAllowed()`): always in a development build, and in the image only when `GARRISON_CSP_CONNECT_SRC` is non-empty, which makes the entrypoint write `allowCustomServer: true` into both `config.js` files. A remembered URL (`garrison_server_url` in `localStorage`) is used only while the override is available; otherwise it is removed, and `AuthContext` restores a session and signs in against the default server, so a stale value can no longer send the console to an origin the Content-Security-Policy blocks. Tests: `src/tests/serverUrl.test.jsx` and `tests/e2e/signin.spec.js`.

## What every page has

- An explainer panel for pages whose objects relate to others (agents and deployments, profiles, prompts, secrets and aliases, nodes and pools, control nodes and worker nodes, users and credentials, roles and assignments, runs and queue, manifests). It can be dismissed and reopened.
- A translated tooltip on every control, column header, tab, badge, and card that says what it is and how it is used (decision D-030).
- Tables with search, filters, sorting, a column picker, pagination with page sizes up to 1,000, auto-refresh, and CSV export.
- Charts (Home, Request History, Analytics, Run detail phases) with an export menu: CSV, PNG, SVG, and JSON.
- Nine languages (English, German, Japanese, Spanish, French, Italian, Simplified Chinese, Traditional Chinese, Cantonese), light and dark themes, and an RTL pseudo-locale for layout testing.

## Checks

| Check | Command | What it covers |
|---|---|---|
| Lint | `npm run lint` | ESLint, no warnings allowed |
| Unit | `npm test` | Markdown rendering and sanitizing, formatters per locale, i18n key and placeholder parity, untranslated strings, enum labels, telemetry and analytics helpers, exporters, tooltips for generated controls |

Run Playwright with `caffeinate -dims` on a laptop that may sleep; a sleeping host stalls a test until it times out.

## Visual QA

Checked by screenshot against the live K3S deployment at 1440 by 1000: Home (KPIs, full-width activity chart), Agents (explainer and diagram), Configuration tabs (Secrets with a tooltip open, MCP Servers empty state), Runs (telemetry columns), Run detail (telemetry panel, transcript), and Analytics (filters, totals, charts grouped by harness and model). ## Accessibility

Landmarks and labels on every page, keyboard access to tabs (arrow keys, Home, End), tooltips on focus as well as hover with `aria-describedby`, Escape closes tooltips and modals, focus is trapped in modals, and status is never shown by color alone (every badge has text).

## Not done yet

- The canvas edits the System prompt on the Runtime tab only: an `Agent` manifest has no key for prompt pins, so the server has nowhere to put an agent-level System prompt.
- Observability cards and deep links into Grafana, Prometheus, Loki, and Tempo (plan P13.12 to P13.19).
- Codex output does not stream until the app-server driver exists (P12.2a); the run still completes normally.
- New-locale translations are marked beta until a native speaker reviews them (`docs/I18N.md` lists the strings to check).
