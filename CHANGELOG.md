# Changelog

All notable changes to Garrison are recorded here. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org). Versions below 1.0 are alpha and may break compatibility in any release.

## [0.2.0] - 2026-10-29

The Agent Studio release. Garrison stays a horizontally elastic runtime for headless agent harnesses, and gains a studio on top of it for building, testing, deploying, operating, and observing agentic applications (AD-027). The work is tracked in `archive/AGENT_DESIGN_DEPLOY_PLAN.md`; task IDs below refer to it. The database schema moves from version 34 to 43, and both Sqlite and PostgreSQL migrate on startup.

### Added

- **Release start (AD0.1 to AD0.5).** Branch `feature/agent-studio`, version `0.2.0` everywhere the version is written (the .NET build, images, Compose, Kustomize, the Helm chart, the dashboard, all four SDKs, Postman, and docs), and `scripts/check-version.sh` (with a `.bat` twin and the push-only `version.yaml` workflow), which fails when a mirror drifts from `src/Directory.Build.props` or carries an `-alpha` suffix.
- **Agent revisions, environments, and promotion (AD1.1 to AD1.10, schema 35).** Immutable agent revisions with one open draft per agent, content hashes, and a field-level diff (`RevisionUnchanged` on publishing an unchanged draft). Deployments gain `agentRevisionId` (pin) and `environment` (default `dev`), validated against an ordered per-tenant environment list (`UnknownEnvironment`); runs record `agentRevisionId`. The compiler reads the pinned revision, or the latest published one when unpinned. Promotion repins the next environment's deployments in one transaction with a `PromotionRecord`, and rollback restores the exact previous pins; skipping an environment is `PromotionOrderViolation` unless `allowSkip`. Routes for revisions, environments, and promotions; MCP tools `garrison_list_agent_revisions`, `garrison_get_agent_revision`, `garrison_publish_agent_revision`, `garrison_promote`, and `garrison_rollback_promotion`; resource types `AgentRevision` and `Promotion`; the built-in role `Releaser`; manifest `environment`, `agentRevision`, and `revision: { publish: false }`; SDK clients in all four languages; the dashboard Revisions tab, environment column and filter, pin, promote, and rollback.
- **Agent assets (AD2.1 to AD2.9, schema 36).** Versioned `SystemPrompt`, `Skill`, `ReferenceFile`, and `DocumentTemplate` assets, content-addressed by SHA-256 under `.garrison-assets/` in an artifact store of the asset's choosing (default the Garrison database), kept out of artifact listings and retention. Revisions pin assets. Built-in harness placements put Claude Code skills in `.claude/skills/<name>/` and everything else in `assets/<name>/`, listed in the system prompt by the new `builtin/agent-assets-instructions` fragment. Workers fetch assets through per-file download tickets, verify the hash (`AssetIntegrityFailed`), and pass bytes to run pods. New settings `Assets.MaxFileBytes`, `Assets.MaxVersionBytes`, `Assets.MaxFilesPerVersion`, and `Assets.AllowMacroFormats`. The `AgentAsset` manifest kind, MCP read and management tools, SDK clients, and the dashboard Assets tab.
- **Conversation file spaces (AD3.1 to AD3.9, schema 37).** One file space per conversation, pipeline run, or root run, shared by every turn and every delegated run in the tree. Workers sync it into `fileSpaceMountPath` (default `files`) at run start and write changes back at run end, fenced by epoch (`StaleFileUpload`). Writes carry a base version; a stale write is kept under a conflict name and raises a `FileConflict` warning. Settings `FileSpaces.MaxFileBytes`, `FileSpaces.MaxTotalBytes`, and `FileSpaces.MaxFiles`. MCP tools `garrison_files_list`, `garrison_files_read`, `garrison_files_write`, and `garrison_files_delete`; REST routes for conversation and run file spaces with download tickets; the `conversation-files:{conversationId}` WebSocket channel; pipeline stages share their pipeline run's space; continuation archives skip the mount path. KubernetesJob runs relay changed files over the pod line protocol, up to 6 MiB per file (AD3.4, also checked on a live k3d cluster). SDK clients and the dashboard Files tab.
- **Capability catalog (AD4.1 to AD4.8, schema 38).** One descriptor per Garrison agent, MCP tool, harness built-in, or manual entry, derived automatically and refreshed by the leader sweep. MCP tool lists are cached with a TTL, keeping the last good list on failure. Harness profiles can declare tool probes (bare executable plus one version or help flag); workers report found tools as `garrison.io/tool-{name}` labels before registering, and an agent's `capabilities` become run requirements (`NoToolWorker` while no worker has them). Cost and latency hints over a bounded window report `Unknown` below a minimum sample. MCP tools `garrison_list_capabilities` and `garrison_describe_capability`; `garrison_list_agents` gains hints; the protected `builtin/garrison-catalog-instructions` fragment; settings `Capabilities.SweepSeconds`, `McpRefreshSeconds`, `McpTimeoutMs`, `HintWindowDays`, `HintMinimumSamples`, and `HintMaxSamples`; SDK clients and the dashboard Capabilities tab.
- **Fan-out and gather (AD5.1 to AD5.9, schema 39).** `garrison_fan_out` starts up to `Delegation.MaxFanOutWidth` members (default 8) after checking every one; `garrison_gather` returns partial results under `All`, `Any`, or `Quorum` join policies; `garrison_cancel_fan_out`. Groups end on join, timeout, cost or token budget (`BudgetExceeded`), or cancellation, and cancel their running members. Gather checkpoints a parent with `suspensionEnabled` instead of holding its slot. Setting `Delegation.GatherResultCharLimit`; templates `builtin/garrison-fan-out-instructions` and `builtin/fan-out-gather-result`; REST routes for fan-out groups, the `fan-out:{groupId}` WebSocket channel, `fanOutGroupId` on runs, SDK clients, the dashboard run tree grouped by fan-out group, and `examples/fan-out.yaml`.
- **Agentic apps and the app UI (AD6.1 to AD6.12, schema 40).** The `AgenticApp` resource: members, one entry agent, edges, per-environment entry deployments, branding, and sign-in mode, with a cluster-wide slug (`AppSlugTaken`). Delegation policies derived from the graph are written to member drafts, reporting drift and never overwriting a manual draft (`DraftConflict`). App revisions pin every member, and app promotion moves every member in one transaction. The built-in role `AppUser`, app sessions (`gas_` tokens), anonymous sessions when enabled, and settings `Apps.SessionMinutes`, `Apps.AnonymousSessionMinutes`, and `Apps.MessagesPerMinute`. The app gateway under `/v1.0/apps/{slug}/` with server-sent turn and file streams that resume after `Last-Event-ID`. A new `app-ui/` single-page app (React 19, Vite, nine locales, light and dark themes) served by the dashboard image at `/apps/{slug}/`. The `AgenticApp` manifest kind, MCP tools `garrison_list_apps`, `garrison_get_app`, `garrison_create_app`, and `garrison_update_app`, SDK clients plus a JavaScript app gateway client, and the dashboard Apps tab with the shareable URL.
- **Studio drafts and the agent architect (AD7.1 to AD7.9, AD7.11 to AD7.15, AD7.17, schema 41).** Studio drafts of manifest documents with optimistic versions (`DraftVersionConflict`), creation from an existing app, a per-item diff against live configuration, and validation by manifest dry run. Applying takes a `DraftApply` approval decided by a person with Create on `Manifest` (`ApproverLacksPermission`), re-validated at decision time (`DraftStale`). Deployments with `managementAccess: Drafts` give their runs draft access for the person who started them. Ten studio MCP tools, the `studio-draft:{draftId}` WebSocket channel, and resource type `StudioDraft`. The protected `agent-architect` agent is seeded in every tenant with the `agent-architect-skills` asset. Architect prompts `builtin/agent-architect` and `builtin/agent-architect-guided`, built from the fragments `builtin/agent-architect-design` and `builtin/agent-architect-runtime`. `GET /studio/architect-prompts`, `GET` and `PUT /studio/architects/{deploymentId}/prompt`, and `architectPromptTemplateId` and `architectPromptVersion` on deployment create (`NotAnArchitectDeployment`, `InvalidArchitectPrompt`). Unpinned architect prompts render their current version on each turn. MCP tools `garrison_studio_list_architect_prompts`, `garrison_studio_get_architect_prompt`, `garrison_studio_set_architect_prompt`, `garrison_clone_prompt_template`, `garrison_update_prompt_template`, `garrison_reset_prompt_template`, and `garrison_render_prompt_template`. SDK clients in all four languages.
- **Studio graph (AD8.1).** A graph projection of a draft's apps (members, entry marker, capabilities, edge depth, and fan-out flags) and graph operations `AddMember`, `RemoveMember`, `Connect`, `Disconnect`, `SetEntry`, and `MoveNode` that rewrite the draft's `AgenticApp` item.
- **Playground and deploy (AD9.1, AD9.3, AD9.4, AD9.7, AD9.8).** Playground runs (run kind `Playground`) of draft revisions on ephemeral `playground-{agent}` deployments in the reserved `draft` environment, through `POST .../agents/{id}/playground/invoke`, `POST .../studio/drafts/{id}/playground/invoke`, and `garrison_studio_playground_invoke`. Compile preview accepts `agentRevisionId` and `environment` (`NoDeploymentInEnvironment`). Applying an approved draft publishes revisions of changed agents and repins their pinned `dev` deployments. SDK support in all four languages.
- **Reference converter, MCP binding, and research example (AD10.1 to AD10.7).** `examples/agentic-apps/doc-converter` (Markdown to Word or PDF with a reference document, Word to PDF), the worker build argument `INCLUDE_DOC_TOOLS` (pandoc, LibreOffice Writer, fonts), the pattern for binding an external MCP server with credentials from a secret, `examples/agentic-apps/research-overview` (orchestrator, researchers, writer, converter, branding, anonymous sign-in), the `examples-<provider>` Touchstone suite, and `scripts/run-research-example.sh`.
- **Agent Studio in the dashboard (AD7.10, AD7.16, AD8.2 to AD8.7, AD9.2, AD9.3, AD9.5, AD9.6, AD9.9).** An Agent Studio tab: draft list and workspace with the architect chat, items with a YAML editor and conflict notice, diff with validate, request apply, and the approval decided inline, a canvas built on `@xyflow/react` (drag or keyboard to add, connect, set the entry, remove, and move; agent, call, app, and per-environment runtime panels; screen-reader summary), playground, compile preview, release panel with promote and rollback, and the architect prompt panel. The setup wizard gains an optional Agent Studio step that creates the architect with a chosen prompt. Everything updates live over `studio-draft:{id}`, in nine locales.
- **Agent architects as a resource.** Architects are tenant-wide and reusable: any studio draft can use any of them. `GET`, `POST .../studio/architects` and `GET`, `PUT`, `DELETE .../studio/architects/{deploymentId}` list (paginated, with `search`, `activeOnly`, and `ordering`), create, read, change, and delete them. An architect is stored as a deployment of `agent-architect` with `managementAccess: Drafts`; the architect routes change only its name, description, harness profile, model, active flag, and prompt, and keep the deployment's other settings. New MCP tools `garrison_studio_list_architects`, `garrison_studio_get_architect`, `garrison_studio_create_architect`, `garrison_studio_update_architect`, and `garrison_studio_delete_architect`, SDK support in all four languages, and an Agents > Architects page in the dashboard, with each row opening its architect prompts and its deployment. A draft's Architect tab picks from the active architects and links to that page.
- **Architect credentials.** An architect takes `credentialSecretId`, the secret its harness signs in with, bound to its deployment as alias `credential` (REST, MCP, all four SDKs; 400 `InvalidCredentialSecret`). Architects created by the setup wizard and the New architect dialog used to have no credential, so Claude Code answered "Not logged in" on every turn; the dashboard now suggests a secret whose kind fits the harness, warns when there is none, shows the credential on Agents > Architects, and the studio chat explains a missing credential or a `NotCredentialed` turn with buttons to fix the architect and to open Secrets. "Manage architects" and "Open conversation" in the studio chat are buttons. Every architect form field that points at another page (harness profile, credential, architect prompt) names that page, links to it in a new tab, offers Refresh list, and reads its choices again when you come back to the tab; each field has one message: the credential says which secret kinds the chosen harness takes, where to add one, and what happens without it.
- **Studio chat.** The architect chat on a draft is a real chat: your messages in bubbles on the right and the architect's answers on the left, each with its time and a copy button. Answers stream in as the model writes them (Server-Sent Events, with a caret, tool calls as chips that turn green or red, and thinking folded away), and the transcript follows new output only while you are at the bottom. Before the first output you see bouncing dots, a rotating phrase that never repeats a recent one, and the time waited; a turn still waiting for a worker says so. Every finished answer keeps its telemetry (model, time to first token, streaming time, total time, input, output, cached, and reasoning tokens, tokens per second, tool calls, and cost) behind an (i) icon in its header. Tool calls, usually MCP calls, are cards that open to show their arguments and result, for streamed turns and for earlier turns alike. Record identifiers in an answer (an approval `apr_...`, a run, a conversation, an agent, a draft, a pipeline run, a prompt template) link to their pages, with an Open button for each under the answer. Enter sends; Ctrl+Enter or Shift+Enter adds a new line (in the architect chat and the playground). A caution under the message box says AI can make mistakes. Copying works on https, on localhost, and on plain http to another host (a hidden-textarea fallback where the Clipboard API is missing), and says so when the browser refuses.
- **Consistent button heights.** Every button has a 1px border and a fixed line height, so primary, secondary, danger, and ghost buttons and links styled as buttons line up side by side; labels no longer wrap inside a button. A Playwright test checks every page, add dialog, and row action dialog.
- **How to get each secret's value.** The Create secret form, the Set value dialog, and the setup wizard's credential step show a guide for the chosen kind: numbered steps, the commands to run (`claude setup-token` for a Claude Code OAuth token, `codex login` under a fresh `CODEX_HOME` for a Codex login), a link to the provider's key page, the environment variable the harness receives, and a caution for subscription logins. Codex logins and file contents get a multi-line value box that keeps line breaks.
- **Deleting agents in the dashboard.** The agent page has a Delete button next to Invoke, and Delete in the Agents table's row menu now asks the person to type `delete` before it works; the dialog names the deployments deleted with the agent, and a refusal from the server (for example 409 `AgentInUse`) stays in the dialog. The protected `agent-architect` keeps Edit and Delete visible but disabled, with the reason in the tooltip, instead of leaving them out. `ConfirmModal` takes a `confirmWord` for other destructive actions.
- **Studio conveniences.** An invoke with `studioDraftId` links a draft to the conversation it starts, and the architect prompts render the linked draft as `studio.draftId`, `studio.draftTitle`, and `studio.draftVersion`. `GET .../studio/drafts` filters by `status`, and `DraftVersionConflict` names the draft's current version.
- **Agent wizard.** Agents > Agents has an Agent wizard button that takes a person from a description of what they need to approved agents running in dev, without visiting other pages. Six steps: the goal (which starts a studio draft, or continues one of yours); model access (harness profile, model, and the credential, which can be added right there with the instructions for getting its value; the wizard then creates or updates one architect per harness profile, `architect-<profile>`, on the guided prompt with that credential); design (the architect chat, starting from the goal, with the draft's contents beside it); review (validation, with one click to send the problems back to the architect); approve (request apply and allow in one step, or wait for someone allowed to decide; then each new agent gets a dev deployment on the chosen harness with the credential bound as `credential`, or the credential is bound to the dev deployment the architect drafted); and try it (a conversation with the app's entry agent on its dev deployment). Agent Studio is no longer a tab: `/dashboard/agents?tab=studio` still opens the drafts list, the wizard links to it and opens any draft's full workspace from its Advanced button, and the empty-list and home-page studio buttons open the wizard. The chat transcript (streaming, polling, history, and scrolling) is one hook, `useChatTranscript`, shared by the architect chat and the wizard's test chat.
- **What the agent is doing, in the app chat.** In an app that shows operator detail, the chat says what the agent is doing while it works (thinking, asking another agent by name, asking several at once, collecting answers, or using a tool) and lists every step live under the answer: its thinking, each tool call and each agent it asked, with a running, done, or failed mark, and what was sent and what came back as readable JSON. The list folds into "Agent activity" when the turn ends. Your messages sit at the far right and the agent's at the far left, across the full width. The wizard's Try it step opens the app's chat.
- **App branding.** An agentic app can set its page background, header (top bar) color, agent message color, conversation list color, message input color, and file list color (each #RRGGBB, with readable text and secondary text picked for contrast), a typeface (System, Sans, Serif, Rounded, or Mono, using fonts browsers already have), and a browser tab icon (`faviconAssetId`, else the logo), alongside the existing primary and accent colors, logo, and welcome text (schemas 42 and 43). The fields are on REST, MCP, manifests (`branding.backgroundColor`, `headerColor`, `agentBubbleColor`, `conversationListColor`, `composerColor`, `filesColor`, `font`, `favicon`), the public app info, and a new `GET /v1.0/apps/{slug}/favicon`. Edit app shows the display name next to the name, since the display name takes any characters and is what the chat shows, and each color field shows the color the chat really uses when it is left empty, with a Default button to clear it.
- **Telemetry and copy in the app chat.** In an app that shows operator detail, an (i) beside each answer shows, on hover, focus, or tap, how the turn ran: the model, the time to first token, streaming, tool, and total times, waits for other agents, approvals, and a worker, the input, output, cached, and reasoning tokens, the output speed, the tool calls, and the cost. The gateway's turn view carries this as `telemetry` for those apps. Every message has a copy button in its top right corner that works on https, localhost, and plain http, and turns into a green check for a moment.
- **Managing conversations and files in the app chat.** The conversation list filters by name, sorts by latest activity, oldest first, or name, and lets you rename a conversation in place or delete it after a confirmation (not while the agent is answering), through the new gateway routes `PUT` and `DELETE /v1.0/apps/{slug}/conversations/{id}` (409 `ConversationBusy` while a turn runs; the runs are kept). The file list has compact rows sorted by newest, oldest, largest, smallest, or name. The dividers between the conversation list, the conversation, and the file list can be dragged or moved with the arrow keys, and the widths are remembered in the browser.
- **Support triage example (AD12.13).** `examples/agentic-apps/support-triage`: a support desk that asks a classifier for the queue and a knowledge lookup for the article, built in the studio and exported as a bundle, with an end-to-end Touchstone case.
- **opencode and pi harnesses (P12.49).** Built-in profiles `builtin/opencode` (`opencode run --format json`) and `builtin/pi` (`pi --mode json`), with the harness types `OpenCode` and `Pi`, the parsers `OpenCodeJsonl` and `PiJsonl`, the MCP configuration formats `OpenCodeJson` and `PiJson`, the configuration templates `builtin/opencode-config` and `builtin/pi-mcp-config`, worker probes, and optional worker image installs (`INCLUDE_OPENCODE`, `INCLUDE_PI`). Both resume sessions for structured output repairs and conversation turns; neither has a `sessionFormat` yet, so durable suspension stays off for them (D-064).

### Changed

- Direct agent edits (REST, MCP, self-registration, and Agent manifests without `revision.publish: false`) publish their content as the next revision when it changed, so every existing edit path keeps working and still leaves a history (AD-030). Migration builds revision 1 for every existing agent.
- `builtin/garrison-tools-instructions` includes the catalog and fan-out fragments when delegation is on, and `builtin/default-system` includes the asset listing, so delegating agents and agents with assets are told about them (AD2.3, AD4.7, AD5.6).
- A revision's `SystemPrompt` asset replaces the deployment's `System` binding (AD-031).
- Agent manifests accept `capabilities` and `assets`; Deployment manifests accept `environment`, `agentRevision`, and `managementAccess` (AD1.7, AD2.6, AD7.4, AD7.8).
- Templates can read a JSON object input's fields as `input.fields.<name>` (AD10.1).
- Re-applying an unchanged `HarnessProfile` without a `sessionFormat` no longer reports `Updated` (AD5.9).
- The dashboard image also serves the app UI under `/apps/`, and `/apps/config.js` carries the same `GARRISON_API_URL` as the console (AD6.7).
- Run objects carry `agentRevisionId`, `fanOutGroupId`, and `fileSpaceId`; conversations can be filtered by `appId` (AD1.3, AD3.1, AD5.7, AD6.11).
- The dashboard sign-in no longer asks for a server URL. The console uses `GARRISON_API_URL` when it is set and otherwise the page's own origin, which the image's nginx proxies to the server. A "Use a different server" link appears only in development builds or when `GARRISON_CSP_CONNECT_SRC` allows extra origins, and a remembered server URL is ignored otherwise. Compose, Kustomize, and Helm pass both settings to the dashboard.
- The app UI uses the JavaScript SDK's gateway client through the new `@garrison/sdk/gateway` entry point instead of its own copy (AD12.8).

- Applying a studio draft is all or nothing. The manifest dry run now runs the write-time checks too (deployment and app validation against the planned records), and a document that fails while writing rolls back every document written before it, including the prompt template versions it added. A draft whose approval was allowed but could not be applied no longer stays Pending with part of it live: the approval is cancelled, the draft reopens, and the decision answers 409 `DraftInvalid` saying that nothing was changed. The dashboard shows that message in the decision dialog; only 409 `ApprovalNotPending` says someone else decided.

- When the agent architect validates a draft, secrets are checked against the person the architect works for. The architect's run never holds Execute on Secret itself, so every deployment that bound a credential failed with `SecretUseDenied`, even for a tenant administrator, and the architect asked people to grant themselves roles they already had. Applying is still checked as the person who approves.

- MCP tool results carry the record as `structuredContent`, a JSON object with the same fields as REST, as well as the JSON text block older clients read.
- Tool results from Claude Code and Codex are recorded as the tool's own output. They used to be the MCP content blocks, `[{"type":"text","text":"..."}]`, with the tool's JSON inside a string; the dashboard also unwraps runs recorded before this change.
- The agent wizard's Design step fits the window, so only the conversation scrolls, and the Send button sits beside the message box at its height (also in the Try it step and the studio workspace).

- The app chat's message box is one line tall (it grows when you resize it), and the Send button always matches its height.
- Languages are no longer marked beta. The dashboard and the app UI list the same nine languages by their own names.

### Breaking

- **JSON fields are JSON, not strings.** Responses no longer carry JSON serialized into strings. An agent's, revision's, and capability's `inputSchemaJson` and `outputSchemaJson` are now `inputSchema` and `outputSchema` (objects; requests send objects too, and a JSON string is still accepted). A run's `structuredOutputJson` is `structuredOutput`, also on fan-out members and MCP run summaries. A run event's `rawEventJson` is `rawEvent` (an object), or `rawEventText` when the line is not valid JSON (a plain line, or one truncated to the configured size); a tool call's JSON arguments are `toolInput` and a tool result's JSON output is `toolOutput`, with `text` left out for those, and transcripts do the same. An approval carries `input` (the tool arguments or the studio draft diff) when it is JSON and `inputPreview` only for clipped text. A notification delivery's `payload` is an object; the signed bytes sent to the endpoint are unchanged. MCP server test `toolDetails` carry `inputSchema`, and an agent revision diff's `from` and `to` are JSON values. Validation errors name `inputSchema` and `outputSchema`, and manifest export writes the schemas as mappings. The worker protocol, the dashboard, the app UI, all four SDKs, Postman, and the docs use the new shapes. Request history bodies stay strings, since they can be any media type.
- **Version and tags.** The version is `0.2.0` and image tags are `v0.2.0`, with no `-alpha` suffix; a 0.x version means alpha. Replace pinned `v0.1.0-alpha` tags with `v0.2.0` for the server, worker, and dashboard together (AD0, AD-028).
- **Reset on a built-in prompt template.** `POST .../prompt-templates/{id}/reset` on a built-in used to answer 409 `BuiltInImmutable`. It now re-applies the shipped content and answers 200, adding a version only when the stored text drifted (AD-025, AD7.13). Clients that treated the 409 as "this is a built-in" should read `isBuiltIn` instead. Update and delete of built-ins still answer 409.
- **Deleting a bound prompt template.** Deleting a template that any deployment binds, pinned or not, answers 409 `PromptTemplateInUse` and names the deployments (AD-026, AD7.15). Switch or unbind those deployments first.
- **Deleting an app member.** Deleting an agent that belongs to an agentic app answers 409 `AgentInUse` (AD6.1). Remove it from the app first.
- **Environments.** Deployment environments are validated against the tenant's list (400 `UnknownEnvironment`), and the `draft` environment is reserved for the playground (400 `ReservedEnvironment`) (AD1.3, AD9.1). Rename any deployment environment outside the list before upgrading automation that sets it.
- **Dashboard image build context.** `dashboard/Dockerfile` now builds from the repository root because it includes `app-ui/`: run `docker build -f dashboard/Dockerfile .` from the root instead of building inside `dashboard/` (AD6.7). Compose, the build scripts, and the Kubernetes scripts already do.
- **Architect prompt catalog is paginated.** `GET .../studio/architect-prompts` and `garrison_studio_list_architect_prompts` return an `EnumerationResult` (`objects`, `totalRecords`, and so on) and accept `maxResults`, `skip`, and `search`, instead of a bare array. The order is unchanged: built-ins, then their tenant clones, then other tenant System templates.
- **Custom ingresses and proxies.** End-user apps need `/apps/` routed to the dashboard and `/v1.0/apps/` to the server, with proxy buffering off for `/v1.0` so turn and file streams flow (AD6.12). The supplied Compose, Kustomize, and Helm configurations already route both.

### Security

- Run tokens of deployments with `managementAccess: Drafts` reach studio drafts only for the person who started the run, always within that person's permissions; they can never apply a draft, decide an approval, delete live resources, or read secret values, and the grant ends with the run (AD-017, AD7.4). Runs can never decide a `DraftApply` approval, whatever their permissions.
- Runs cannot read or change architect prompts or prompt templates through MCP, including the architect's own runs (AD7.14).
- App sessions are a separate credential: `gas_` tokens stored only as SHA-256 hashes, accepted only on `/v1.0/apps/{slug}/` for that app and its owner's own conversations, refused by the management API, and expiring per `Apps.SessionMinutes` and `Apps.AnonymousSessionMinutes`. Anonymous use needs both `authMode: Anonymous` and `anonymousEnabled`. Runs started through an app run as the app, bounded by the entry agent's graph-derived allow list (AD-021, AD-035, AD6.5).
- The `AppUser` role grants Execute on one `AgenticApp` at resource scope and nothing else. The `Releaser` role holds Execute on `Promotion` and can be limited to one target environment by resource scope (AD1.4, AD6.5).
- Asset and file space downloads use short-lived per-file tickets, workers verify SHA-256 before a run starts, and run pods still receive bytes rather than URLs or credentials (AD2.4, AD3.3). File space paths refuse traversal, absolute paths, and links.
- Macro-enabled Office formats are refused as assets unless `Assets.AllowMacroFormats` is set (AD2.2).
- Tool probes are limited to a bare executable on the `PATH` with one version or help flag, because they run on shared worker hosts outside any run (AD-033).
- The MCP binding pattern keeps the bound server's bearer token out of events, transcripts, and run records (AD10.3).

## [0.1.0-alpha] - Unreleased

The first build of Garrison: a multi-tenant control plane that runs headless agent harnesses on pull-based worker nodes and exposes them over REST, MCP, and A2A. This release is the MVP milestone in `archive/GARRISON_PLAN.md`.

### Control plane

- D-063 makes the artifact file ceiling explicitly configurable up to 256 MiB while keeping the 16 MiB default. This permits larger complete-HOME continuation archives when operators also allow them in REST/proxy limits; extraction bounds and fencing remain enforced. C# SDK compiled settings preserve the same range. Download validation follows the configured cap across storage providers, removing a separate hardcoded 64 MiB restore ceiling while retaining recorded-length checks.
- Worker cleanup now follows the final checkpoint outcome. Failed or cancelled capture/upload preserves a `KeepOnFailure` workspace while removing private HOME/config state.

- D-062 adds tenant-scoped run placement explanations and exact completed-scope SQL counters through REST and all four SDKs. Placement is advisory and does not reserve or mutate runs; shared/background queries and counters lost before a best-effort flush remain separate from attributed lifecycle scopes.
- Held synchronous invocation and pipeline waits share `Scheduling.MaxSynchronousWaiters` (default 256). When that budget is full, the operation returns its accepted run for polling instead of occupying another listener slot. Invocation can return HTTP 202 before its requested wait expires; callers must poll that run ID rather than resubmit it. This prevents worker heartbeat/completion starvation under large synchronous bursts. Resident synchronous delegation reserves capacity before creating a child and fails with `DelegationCapacityExhausted` when full, preserving the child reserve.
- Optional agent memory uses `IAgentMemoryStore` with a persistent filesystem implementation and agent-scoped MCP read/write/delete tools. Enable it with `docker/compose.agent-memory.yaml`; NotDory remains an optional external example.
- Application stage metrics/spans and intrinsic gateway timing cover the new execution paths. Base Docker Compose now starts the observability services and exports OTLP by default; allow an 8 GB Docker memory budget and about 10 GB disk as a starting point. Prometheus preserves application component labels separately from server/worker target identity.

- A run that delegates and waits can no longer deadlock its children (P12.38, D-049). The wait is recorded before the child is created; each worker lends the slots of its waiting runs to their children through a bounded child reserve (`ChildReserveSlots`, default 2, served by a second lease long poll) and caps how many of its runs may wait at once (`MaxResidentWaiters`, default `MaxConcurrentRuns`, never so many that every slot holds a waiting run). A deployment's `maxConcurrentRuns` leaves out a delegated run's waiting ancestors in the same deployment. Beyond those bounds, or when `Runs.DelegationChildQueueDepth` (default 100) waited children are already queued, the delegation fails at once with `DelegationCapacityExhausted` (REST 429 with `Retry-After` from `Runs.DelegationRetryAfterSeconds`, the same code in MCP and A2A). Delegated runs are claimed ahead of new top-level work through a QoSKit priority queue (D-036). Nodes report `childReserveSlots` and `maxResidentWaiters`; migration 22 adds them and the `run_child_waits` table. See `docs/SCALING.md`, "Delegation capacity".

- Pipelines run agents as ordered stages with optional human review gates (P12.9, D-048). Each stage is an ordinary run of its agent in its own workspace; the previous stage's result text, structured output, and artifact references reach it through the new `PipelineStage` prompt role (`builtin/pipeline-stage` with the `builtin/pipeline-revision` fragment, a deployment binding, or a per-stage handoff template). Reviews offer Approve (notes reach the next stage), Request changes (the stage runs again with the feedback, up to `maxRevisions`, then 409 `RevisionLimitReached`), and Reject; undecided reviews wait indefinitely unless the stage sets a timeout and its action. When the node is not Ready, the wait ends, or the directories are gone (outcome `ConversationStateLost`, requeued without using an attempt), another node runs the turn as a fresh session seeded with the transcript of the earlier turns from the new `builtin/conversation-fallback` template (deployment role `ConversationFallback`, limits `Runtime.ConversationTranscriptTurns` and `Runtime.ConversationTranscriptChars`), and the fallback is recorded on the run (`conversationFallbackReason`), as a `ConversationFallback` event, and on the conversation. One turn runs at a time: a turn sent while the previous one is unfinished is refused with 409 `ConversationBusy`. New routes `GET .../conversations`, `GET`/`DELETE .../conversations/{id}`, and `GET .../conversations/{id}/runs` (resource type `Conversation`; deletes are audited as `ConversationDeleted`), a `conversationId` filter on `GET .../runs`, new run fields (`conversationId`, `conversationTurn`, `resumeSessionId`, `affinityNodeId`, `affinityUntilUtc`, `conversationFallbackReason`), the `conversations` table (migration 12), worker settings `ConversationRetentionHours` (default 24) and `ConversationSweepIntervalSeconds`, metrics `garrison_conversation_turns_total`, `garrison_conversation_fallbacks_total`, `garrison_conversation_busy_total`, and `garrison_worker_conversations_swept_total` (Runs and Workers dashboards), dashboard pages, SDK support in C#, Python, JavaScript, and Go, and Postman requests. The fake harness gains `--report-turns`, `--session-id`, and the `resume <session>` form.
- Worker node with capability probes, an isolated workspace and home directory per run, MCP pre-flight, output parsers for every built-in harness, secret scrubbing, buffered event delivery that survives control-plane outages, and drain on shutdown.

### Protocols

- MCP server on Voltaic with agent discovery, invocation, and run tracking tools whose descriptions are prompt templates. Only system administrators see the `tenantId` argument; run-token sessions and other callers act in their own tenant, and the descriptions tell models to leave optional arguments out.
- A2A gateway with one agent card per agent and JSON-RPC send, stream, get, list, cancel, and subscribe. Cards advertise `Rest.ExternalBaseUrl`; reusing a `messageId` with different content returns 409.
- Agents can be addressed by name or ID on every agent route, with authorization checked against the resolved agent.
- A tenant overrides the description of any built-in MCP tool for its own callers with a `ToolDescription` template named `mcp-tool-<tool name>`, rendered with `tool.name`, `tool.defaultDescription`, `tenant.id`, and `garrison.version`; `mcp-tool-description` and `a2a-skill-description` tenant templates likewise replace the built-in agent tool and skill descriptions (G-3).
- Agents with `exposeMcpTool` are offered as MCP tools of their own (named by `mcpToolName` or the agent name), listed per tenant to callers allowed to execute them and to run tokens allowed to delegate to them; calling one invokes the agent and waits. Descriptions come from `toolDescriptionTemplateId` or `builtin/mcp-tool-description` (G-5).
- One renderer builds every A2A agent card (the public card, the tenant catalog, and the REST `.../card` route), with the full template language for skill descriptions and the bearer scheme always keyed `garrison` (G-4).

### Defaults

- First start seeds tenant `default` with the administrator `admin@garrison` and password `password` (`GARRISON_ADMIN_EMAIL`, `GARRISON_ADMIN_PASSWORD`). Change them before the server is reachable by anyone else.

### Compatibility notes

These changes landed after the M1 integration and change behavior a client may depend on.

- **Node protocol and administrator accounts (P15.1).** A credential or user that reached the node protocol only through `isTenantAdmin` or an `All` grant (such as a `TenantAdmin` credential used as a worker key) is now refused with 403; give workers a `NodeAgent` credential, which every shipped configuration already does. Creating or rotating a system administrator's credential, or changing their password or email, now needs a system administrator (400 otherwise). A run token's `POST .../runs/{id}/retry` answers 403. Requests larger than 128 MiB answer 413; raise `Rest.MaxRequestBodyBytes` if you send larger bodies.

- **Empty input (D-050).** Invoking an agent, creating a run, testing a deployment, or starting a pipeline with no body or with an empty or whitespace `input` used to start a run with empty input; it now answers 400 `ValidationFailed` with field code `InputRequired` on `input`, and nothing is created. For an agent with no deployment, the 400 now comes before the 409 `NoActiveDeployment`. MCP and A2A already rejected an empty input and still do. Retrying an existing run reuses its stored input and is not affected.
- **Codex sandbox default (G-29).** On containerized workers and in run pods, deployments of `builtin/codex` and `builtin/codex-app-server` without a `sandbox` parameter now run with `danger-full-access` instead of `workspace-write` (which could not run shell commands there). Set `sandbox` on the deployment to keep the old value. Workers run directly on a host are unchanged. Upgrade workers with the server: an older worker does not report `containerized`, so its runs keep `workspace-write`.
- **Response warnings (I-08).** Create and update responses may carry a new `warnings` array, and manifest apply items a new `warnings` list. Clients that reject unknown properties need to accept them; stored values did not change.
- **Effect policy replaces retryOnNodeLoss (P12.29).** `retryOnNodeLoss` is deprecated and still accepted on input for one release over REST, MCP, and manifests: alone, `true` maps to `AtLeastOnce` and `false` to `AtMostOnce`. A request that also sends `effectPolicy` with a different meaning is now rejected with 400 and the field code `EffectPolicyConflict` on `effectPolicy` (a manifest item reports it as its `errorCode`). Responses carry `effectPolicy` plus a derived, read-only `retryOnNodeLoss` (`true` only for `AtLeastOnce`), so a client that reads a deployment, changes `effectPolicy`, and sends the whole body back must drop or update `retryOnNodeLoss`. The default for new deployments did not change: `retryOnNodeLoss` already defaulted to `false` on every surface (REST, MCP, manifests, the dashboard form, and the C# SDK), and the new default `AtMostOnce` is the same behavior. Existing deployments keep their behavior through the migration. The C# SDK's `Deployment.RetryOnNodeLoss` is now a view of `EffectPolicy`; the Python, JavaScript, and Go SDKs gain `effectPolicy`.

- **Metric names and labels (P13.21 to P13.24).** Dashboards and alerts built on the earlier metrics need updating: `garrison.run.stage.duration`, `garrison.compile.duration`, and the worker duration histograms now have a unit, so their Prometheus names end in `_seconds` (`garrison_run_stage_duration_seconds_bucket`); `garrison.harness.tokens` is joined by the `garrison_run_tokens_total` counter, which is the one to sum; `garrison.worker.harness.tokens` and `garrison.worker.harness.cost_usd` are counters (`_total`), as they always were in the code; `garrison_http_requests_total` gains `route`, `status_code`, and `tenant`; and the run metrics gain `tenant`, `agent`, `deployment`, and `model`. The packaged dashboards use the new names.

- **Start gate and liveness port (P10.20, G-24).** Workers now call `.../started` before launching, with `processId` null, and again with the process ID; servers accept both. Upgrade workers together with the server: an older worker still launches before it reports, so the double-execution fix applies only to updated workers. The liveness probe moved to port 8702; a custom manifest that copied the old probe keeps working because `/v1.0/api/health/live` is still served on 8700.
- **Database errors (G-23, G-25).** Requests that used to fail with `500 InternalError` (or an HTML page) during a database outage or pool exhaustion now answer `503 DatabaseUnavailable` or `503 DatabaseBusy` with `Retry-After`. Clients should retry them.

- **DELETE status codes (G-7).** Deleting one resource now answers 204 No Content with an empty body everywhere. Agents, deployments, harness profiles, prompt templates, MCP servers, secrets, workspace templates, and artifact stores used to answer 200 with `{"deleted": true, "cascaded": n}`, and `DELETE /v1.0/api/tenants/{tenantId}` used to answer 200 with `{"deletedCount": n}`. Filter deletes (runs, audit records, request history) keep 200 with `DeleteCountResponse`, and `DELETE /v1.0/token` keeps 200 with `{"valid": false}`. Clients that read the old bodies must stop; the SDKs already treat an empty body as success. The C# SDK's `Tenants.DeleteAsync` now returns `Task` instead of `Task<DeleteCountResponse>`.
- **Password hashes (G-2).** The `passwordsha256` column keeps its name and size (128 characters) but holds the encoded PBKDF2 hash; no migration is needed. A database rolled back to an earlier build cannot verify upgraded hashes, so those users would need a password reset. The internal model property `User.PasswordSha256` is now `User.PasswordHash`; it was never part of the API (`[JsonIgnore]`).
- **exposeMcpTool and mcpToolName (G-5).** The flag now has an effect: an agent that had it set before this build becomes an MCP tool for its tenant. `mcpToolName` is validated (1 to 64 letters, digits, `_`, `.`, `-`, not starting with `garrison_`); saving an agent with an invalid name answers 400.
- **Rejected (G-5).** The `Rejected` run status and outcome, previously never set, are now used for runs refused at claim. Deactivating a deployment or agent now stops its queued runs from starting.
- **A2A context identifiers (P12.1).** A task's `contextId` used to be its root run's identifier; it is now its conversation's identifier (`cnv_...`), or the `contextId` the client sent. Every A2A message starts or continues a conversation, so a second message with the same `contextId` resumes the agent's session instead of starting fresh, and a message sent while the same context's previous task is still working is rejected with `ConversationBusy`. Use a new `contextId` (or none) for independent requests. `ListTasks` with a conversation's `contextId` lists its tasks; a root run identifier still lists a delegation chain.
- **Mux sessions (P12.1).** `builtin/mux` now persists the Mux session (`--session-id <run id>`, no `--no-session-persistence`) for conversation turns as well as for agents with an output schema; the condition is the new template variable `run.persistSession`. Clones of the profile keep their own conditions.
- **Workers and conversations (P12.1).** Upgrade workers with the server: an older worker ignores the conversation settings in the execution spec, runs a resumed turn in fresh per-run directories, and the harness then fails because the session is missing.
- **A2A cards (G-4).** `GET .../agents/{idOrName}/card` now matches the public card: the bearer scheme is keyed `garrison` instead of `bearer`, `provider` and `securityRequirements` are present, input modes follow `inputMode` (`Structured` takes `application/json`), and output modes are `text/plain` and `application/json`. The public card renders skill templates with the full template language instead of substituting two placeholders.
