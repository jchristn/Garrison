# Changelog

All notable changes to Garrison are recorded here. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org). Versions below 1.0 are alpha and may break compatibility in any release.

## [0.1.0-alpha] - Unreleased

The first build of Garrison: a multi-tenant control plane that runs headless agent harnesses on pull-based worker nodes and exposes them over REST, MCP, and A2A. This release is the MVP milestone in `GARRISON_PLAN.md`.

### Control plane

- Watson 7 host with per-feature route registrars, OpenAPI at `/openapi.json`, CORS, request history capture, and a central operation scope map that records the permission every route and MCP tool requires.
- Data layer for Sqlite and Postgresql with versioned, idempotent migrations, structured tables and child tables for every entity, and first-boot seeding.
- Authentication with bearer session tokens (AES-256 with a random IV plus HMAC), credential headers, AWS-style signed requests with replay protection, the administrator API key, and run tokens for delegation.
- User passwords are stored as PBKDF2-HMAC-SHA256 with a random 16-byte salt and 600,000 iterations (`Auth.PasswordHashIterations`, live), encoded as `pbkdf2-sha256$<iterations>$<salt>$<hash>`. Hashes from earlier builds (unsalted SHA-256) keep working and are rehashed on the next successful sign-in, as are hashes with fewer iterations than configured. Sign-in for an unknown or inactive account spends the same verification time as a real one (G-2).
- RBAC with built-in and custom roles, permissions over resource types and operations, tenant and resource scoped assignments, explicit deny, credential owner ceilings, effective-permission inspection, and audit records for denials and privileged changes.
- Settings API that separates node-local file settings from cluster runtime settings stored in the database, with restart-required metadata and a restart endpoint.

- Multiple control-plane replicas behave like one (Phase 10): signed-request nonces, the token rate limit, and MCP sessions are shared through the database; an event backplane (Postgresql LISTEN/NOTIFY, or a polled table) wakes SSE, A2A, invoke, and lease long-poll waiters and invalidates settings and permission caches on every replica; deployment `maxConcurrentRuns` is exact under concurrent claims; idempotent run creation is atomic across replicas; tenant-dedicated node pools are filtered in the claim query. See `docs/SCALING.md`.
- MCP sessions work on every replica without sticky routing: Garrison serves the public MCP port and relays to Voltaic on a loopback port, replaying a session's handshake on a replica that has not seen it.
- Migrations and built-in seeding run under a database startup lock, one replica at a time. `GET /v1.0/api/health/live` (always 200 while the process runs) and `GET /v1.0/api/health/ready` (same as `/v1.0/api/health`: 503 while migrating, starting, degraded, or draining) split liveness from readiness.
- Graceful shutdown drains: readiness turns off, long polls, SSE (`server.draining`), A2A, WebSocket, and synchronous waits end, and in-flight requests get 15 seconds.
- Control-plane replicas are visible like worker nodes (P10.19): each replica registers a `control_nodes` row (migration 7) as `Starting`, heartbeats it every 5 seconds as `Ready` with its version, schema version, backplane, requests in flight, open SSE and WebSocket streams, and held lease long polls, turns `Draining` on SIGTERM and `Offline` on a clean exit; the leader marks rows silent for 30 seconds `Offline` and deletes rows `Offline` for 24 hours (cluster settings `ControlPlane.HeartbeatIntervalMs`, `OfflineAfterMs`, `OfflineRetentionHours`). `GET /v1.0/api/control-nodes` and `/{id}` (Read on `Node`) mark the leader (`isLeader`, `leaderEpoch`, from the coordination lease) and name the replica that answered (`respondingNodeId`); the overview adds `controlNodesByStatus` and `leaderNodeId`; Prometheus gets `garrison_control_nodes` by `status`. The C#, Python, JavaScript, and Go SDKs list and read control nodes.
- Connection pool settings (`Database.MinPoolSize`, `ConnectionTimeoutSeconds`, `CommandTimeoutSeconds`, `ConnectionIdleLifetimeSeconds`, and `GARRISON_DB_MAX_POOL_SIZE`), read-path indexes (migration 6), optional JSON Lines archival of runs and events before retention deletes them (`Archive.Directory`), and cluster-wide `garrison_runs_queued` and `garrison_runs_active` gauges.

### Configuration

- Harness profiles that describe a headless invocation as data, with built-in profiles for Claude Code, Codex, Mux, Gemini CLI, a generic JSON-lines CLI, and a fake harness.
- Versioned prompt templates with a logic-light template language, live render preview, built-ins that can be cloned and reset, and recorded template versions on every run.
- MCP servers, encrypted secrets, workspace templates, artifact stores, agents with A2A cards, and deployments that bind them with overrides, placement, limits, and per-run parameters.
- Declarative manifests (`garrison/v1`) with dry run, apply, and export.

### Runtime

- Pull-based scheduling with an atomic compare-and-set claim, fencing epochs, lease heartbeats, and long-poll leasing.
- Leader election through a database lease, with a maintenance loop that requeues or fails runs whose node disappeared, enforces deadlines, marks silent nodes lost, and prunes old runs and events.
- Run lifecycle with cancellation, retry, idempotency keys, events streamed over SSE and WebSocket, and delegation limited by allowlist, depth, and recursion rules.
- Structured output validation: when an agent has an output schema, the control plane validates each run's final output against it (JsonSchema.Net), makes one repair attempt that resumes the harness session in the same lease with the `Repair` prompt template when the profile supports resume, and otherwise fails the run with `SchemaValidationFailed`. Runs carry `outputSchemaValid`, `schemaValidationErrors`, and `repairAttempts`.
- Run telemetry measured on the worker's clock: time to first token, streaming, execution, queue, and total time, output tokens per second, input, output, cached, and reasoning tokens, tool calls, cost, the served model (for Codex, read from its session file), and the time spent waiting on delegated runs with time to first token excluding it.
- Analytics API (`GET .../analytics/runs` and `.../dimensions`): gap-filled time buckets with averages and p50/p95, filters by agent, harness, deployment, and model, and grouping by agent, harness, model, or harness and model.
- Queued runs that no worker can take report why (`blockedReason`: no Ready worker, no worker with the harness, or no matching pool), with a one-time warning event and an optional fail-after setting.
- Runs whose tenant, agent, or deployment was deactivated or deleted while they were queued end `Rejected` (outcome `Rejected`) when a worker claims them, instead of starting or failing to compile (G-5).
- Claude Code output streams token by token (`--include-partial-messages`); Mux streams natively.
- Codex output can stream too (P12.2a, G-12). A new built-in profile, `builtin/codex-app-server`, runs `codex app-server` and the worker drives it over JSON-RPC on stdin and stdout (new prompt delivery mode `CodexAppServer` and output parser `CodexAppServer`): it sends `initialize`, logs in with the API key from an `OpenAiApiKey` secret (`account/login/start`, because the app-server ignores `CODEX_API_KEY` and `OPENAI_API_KEY`) or uses the `CodexAuthJson` login as before, starts the thread (or resumes it with `thread/resume` for a structured output repair), sends the prompt as one turn with the agent's output schema, and closes stdin when `turn/completed` arrives. Agent message deltas become `AssistantText` events and reasoning deltas `Thinking` events as they arrive, so time to first token and streaming time are real for Codex; command, MCP, file change, and web search items become tool events, and the turn's token usage counts only that turn even on a resumed thread. Approval requests are declined (a headless run has nobody to ask) and shown as warnings; token refresh requests are refused, so the G-22 credential handling (`codexRunAuth`, `CODEX_REFRESH_TOKEN_URL_OVERRIDE`) is unchanged. `builtin/codex` keeps `codex exec --json` and stays the default, because the app-server is still marked experimental in Codex 0.159.3. The protocol driver (`CodexAppServerDriver`) exposes thread start and resume and turn start as separate steps for multi-turn conversations (P12.1). The fake harness gains `--format codex-app-server` and `--request-approval`.
- Pause tolerance (P3.16): when the host sleeps or the Docker VM freezes, the leader no longer marks every worker `Lost`, every replica `Offline`, and healthy runs `NodeLost` on resume. A maintenance tick more than the maintenance interval plus `Scheduling.PauseGraceMs` (new cluster setting, 5000 ms) after the previous one is a pause: the leader logs a Warning (`event=maintenance.pause`), heartbeats itself, and defers lease expiry, deadlines, `Lost` and `Offline` marking, and blocked-run failures for one heartbeat window plus the grace. Runs whose worker re-confirms its lease in that window get their deadline moved by the paused time. A leader whose own control node heartbeat is stale marks nothing. Workers detect their own pauses (new worker setting `PauseGraceMs`) and heartbeat at once, and log the pause when a lease turns out stale anyway. See `docs/SCALING.md`, "Pauses".
- Bounded, self-stopping runs (P3.15). Worker run guards for every harness, set per deployment (`repetitionGuard`, `maxAssistantChars`, `noProgressSeconds`, migration 8) over new cluster defaults (`Runtime.RepetitionGuard`, `Runtime.MaxAssistantChars`, `Runtime.NoProgressSeconds`): a run whose assistant text degenerates into one short repeated unit or into text with no letters or digits ends `RepetitionDetected`, one that writes more than 200,000 characters ends `OutputLimitExceeded`, and one with no text, thinking, tool call, or tool result for 300 seconds while no tool call is open ends `NoProgress`. A tripped guard emits one `RunGuardTriggered` warning, keeps the partial output as the result, and stops the harness with SIGTERM then SIGKILL after the kill grace, now sent to the harness's child processes too (libc `kill`, no `kill` binary needed). The cluster cap `Runtime.MaxRunSeconds` (default 3600) bounds every run's deadline, including a per-run `timeoutSeconds` override (now an allowed override field), and the deadline enforcer applies it to older runs.
- Pod-per-run executor (Phase 11, D-033). Deployments choose `executor: Process` or `KubernetesJob` (node pools get a `defaultExecutor`; runs record the executor; migration 9). A Job-capable worker creates a Job and an owned spec Secret per run, the pod runs `garrison-worker run-one` with the process executor and run guards, and the worker relays only stdout lines carrying the run's random nonce. Run pods have no service account token, a read-only root filesystem, no capabilities, `RuntimeDefault` seccomp, emptyDir work, home, config, and `/tmp`, per-deployment `podResources`, an optional `runtimeClassName`, image pull secrets, and a `garrison-run` NetworkPolicy that the harness waits for (egress canary). Cancel and timeout delete the Job; restarts reconcile orphaned Jobs; pod failures end `PodFailed` with the cause; evicted pods count as node loss. New workspace kind `PersistentVolume`. Worker Role, RoleBinding, `garrison-run` ServiceAccount, and Helm `kubernetesExecutor` values.
- ChatGPT logins stored as `CodexAuthJson` secrets keep working (G-22). The control plane, not the run, refreshes a login whose access token expires within `Codex.RefreshBeforeExpirySeconds` (default one day), using the Codex CLI's token endpoint and client (`Codex.TokenEndpoint`, `Codex.ClientId`), and writes the rotated tokens back to the secret, encrypted. One refresh per secret runs at a time across all replicas (a database lease), the write-back is a compare-and-swap on the stored value, and the leader refreshes idle logins every `Codex.RefreshCheckIntervalSeconds`. Runs receive the login without its refresh token (new template filter `codexRunAuth`) and with Codex's own refresh pointed at a closed loopback port, so a run can never use up the stored refresh token. A login OpenAI rejects for good (`refresh_token_reused`, `invalid_grant`, 401) marks the secret `NeedsReauthentication`; its runs fail at once with outcome `NotCredentialed` and a message that names the secret and the fix, and setting a new value clears the state. Secrets gain `status`, `statusMessage`, `statusUtc`, `refreshedUtc`, and `accessTokenExpiresUtc` (migration 10), shown in the dashboard Secrets list and form and in the C#, Python, JavaScript, and Go SDKs. The quick start now recommends `OpenAiApiKey` for shared deployments and signing in with a separate `CODEX_HOME` for a stored login.
- Cancellation reaches the harness in well under a second: workers hold a cancellation watch long poll (`POST /v1.0/api/node/watch`) that the control plane answers as soon as a held run is cancelled on any replica; the heartbeat stays the fallback. Cancelling a run cancels its delegated runs. Callers that go away cancel their runs: REST `wait=true` invoke, test, and create on client disconnect (`cancelOnDisconnect`, default true, opt out in the body or query), MCP `garrison_invoke_agent` on `notifications/cancelled` (relayed across replicas) or session close, and A2A blocking `SendMessage` and `SendStreamingMessage` on disconnect. The SDKs expose the new outcomes and `cancelOnDisconnect`.
- The fake harness gained `--ignore-sigterm`, `--loop-text`, `--spawn-child`, and `--tool-sleep-ms` for testing the stop path and the guards.
- Mux 1.3.0 support (1.2.0 output still parses): the `failed` run status with the last error as the run's error, `NotCredentialed` for a model 401 or `config_unresolved_env`, cached and reasoning tokens and cost from `usage`, a warning when Mux falls back to its default context window, the `contextWindow` and `maxTokens` deployment parameters (also `MUX_CONTEXT_WINDOW` and `MUX_MAX_TOKENS` for the sample agent), and `--session-id` for agents with an output schema so the structured output repair can resume the session. Resume and native output schemas were verified against real Claude Code, Codex, and Mux. The generated Mux `settings.json` turns off features meant for a person at a terminal: persistent memory (`memoryEnabled`, which added the `remember`, `recall`, and `forget` tools and a `## Memory` prompt section), user and project skills, task planning, `@path` file attachments (`fileMentionMaxBytes: 0`), and the setup wizard.
- Worker metrics (leases, runs, duration, tokens, cost, completion reports) and a span per harness execution that joins the run's trace.
- Observability integration (Phase 13): `Observability.*` cluster settings and `GARRISON_GRAFANA_URL`-style environment variables for Grafana, Prometheus, Loki, and Tempo, an `observability` block in server info, `GET /v1.0/api/observability/status` with cached server-side probes, a W3C `traceId` on every run (schema migration 5) shared by the `run:create`, `run:claim`, `run:compile`, and `harness <type> exec` spans, `run=<runId> trace=<traceId>` on every run log line, and `/metrics` relayed on the REST and worker health ports so `kubectl port-forward` works. The dashboard shows a card per service on Home and links runs, nodes, KPIs, request history, and analytics into Grafana.
- Full telemetry coverage (P13.20 to P13.28): every Garrison metric is declared once in a catalog on the `Garrison` meter (103 metrics, histogram buckets per metric, a docs table and a CI test generated from it). Per-run metrics carry `tenant`, `agent`, `deployment` (by name), `harness`, and `model`, on the server and the worker, covering creations, every terminal transition, stage durations (`queue`, `claim`, `compile`, `startup`, `first_token`, `first_token_excl_delegation`, `streaming`, `execution`, `delegation_wait`, `total`), tokens by direction, cost, output rate, tool calls, guard trips, and cancellations. REST requests are measured by route template, method, status, and tenant from one post-routing hook; MCP tools, MCP sessions, A2A methods and task states, SSE streams, the live-update WebSocket, invocation waits, `cancelOnDisconnect` cancels, and delegation depth and denials have their own metrics and spans. The ADO.NET driver times every statement and transaction by provider, operation, and table (with a client span named after the statement, never its SQL), counts connections, Sqlite write-lock waits, and retries; one HTTP handler records every outbound call (node protocol, Kubernetes API, MCP server tests, observability probes, the MCP cluster proxy); every background service iteration (maintenance steps, leader election, control node heartbeat, gauges, backplane, retention, settings refresh, worker heartbeat and lease) gets a span and metrics, and idle iterations are tagged so Alloy drops their traces. New gauges report queue depth per agent, blocked runs by reason, nodes and MCP sessions, the leader flag, and observability reachability. Worker spans cover workspace preparation, MCP preflight, KubernetesJob runs, and completion reports; KubernetesJob metrics cover Jobs, pod start latency, pod failures by reason, and orphan cleanup. A cardinality guard (`Telemetry.MaxLabelValues`, default 200) folds excess label values into `other` and counts them, and duration histograms carry trace exemplars (`Telemetry.Exemplars`; Prometheus runs with exemplar storage and the datasource links exemplars to Tempo). Log lines carry `tenant`, `agent`, `deployment`, `model`, `node`, and `route` fields next to `run` and `trace`, and Alloy promotes `tenant` to a Loki label. Grafana gains eight section dashboards (Agents, Models and tokens, Kubernetes executor, Scheduler and queue, Database, Control plane, Security and auth, Logs and traces) next to the six rewritten ones, all in the `Garrison` folder with tenant, agent, deployment, harness, model, and node variables, log and trace links, and exemplars; `server-info` lists their UIDs and the dashboard links to each from Home and to the Agents dashboard from Agent detail. `docs/TELEMETRY.md` holds the coverage matrix, and `k8s/tests/telemetry-verify.sh` checks a cluster end to end, including a headless pass over every Grafana panel.
- Start gate for leased runs (P10.20): a worker asks the control plane to acknowledge the start (`POST .../node/runs/{runId}/started`, now sent before launch) and launches the harness only after a 200 for its lease epoch, which moves the run to Running. A worker that is refused or cannot get the acknowledgement before its lease expires abandons the run without launching it, so a still-Leased run never started anywhere and its requeue is safe, while a started run follows `retryOnNodeLoss` (`NodeLost` by default). A worker partitioned right after claiming no longer runs a harness that is also started elsewhere.
- Run tokens are fenced by lease epoch (P10.21): each run token session records the epoch it was minted for (migration 11), a requeue revokes the expired attempt's tokens, and a run token is accepted only while its run is Leased, Running, or Cancelling at that epoch, so a stale harness cannot delegate through MCP, A2A, or REST.
- Database failures answer JSON (G-25, G-23): authentication, the administrator tenant check, authorization, and handlers run inside one exception mapping, and Watson's last-resort exception route answers JSON too, so no request gets an HTML error page. An exhausted connection pool or a PostgreSQL without free connection slots answers `503 DatabaseBusy`, an unreachable or restarting database `503 DatabaseUnavailable`, both with `Retry-After` (`Rest.DatabaseRetryAfterSeconds`, default 2); MCP tools return the same codes as tool errors and A2A as JSON-RPC `-32603` with HTTP 503.
- Separate liveness listener (G-24): `Rest.LivenessPort` (default 8702, `GARRISON_LIVENESS_PORT`) answers `GET /v1.0/api/health/live` from a dedicated thread from process start, without the database, the REST request queue, or the thread pool. The Kubernetes and Helm liveness probes use it with a 10-second period and timeout and a failure threshold of 6, so overload makes a replica unready instead of restarting it.
- Readable manifest spec errors (G-26): a spec field with the wrong type or a value that is not allowed fails its document with `errorCode` `ManifestInvalid`, `errorField` (for example `documents[1].spec.kind`), and a message that names the document, field, value, and allowed values, without serializer type names or byte positions. Manifest apply items gain `errorCode` and `errorField` (migration 11).
- Concurrent node registration (G-27): workers registering at the same moment no longer fail with a duplicate-key 500 when they create the same node pool (or register the same node twice); the loser re-reads the row the winner created.
- Worker node with capability probes, an isolated workspace and home directory per run, MCP pre-flight, output parsers for every built-in harness, secret scrubbing, buffered event delivery that survives control-plane outages, and drain on shutdown.

### Protocols

- MCP server on Voltaic with agent discovery, invocation, and run tracking tools whose descriptions are prompt templates. Only system administrators see the `tenantId` argument; run-token sessions and other callers act in their own tenant, and the descriptions tell models to leave optional arguments out.
- A2A gateway with one agent card per agent and JSON-RPC send, stream, get, list, cancel, and subscribe. Cards advertise `Rest.ExternalBaseUrl`; reusing a `messageId` with different content returns 409.
- Agents can be addressed by name or ID on every agent route, with authorization checked against the resolved agent.
- A tenant overrides the description of any built-in MCP tool for its own callers with a `ToolDescription` template named `mcp-tool-<tool name>`, rendered with `tool.name`, `tool.defaultDescription`, `tenant.id`, and `garrison.version`; `mcp-tool-description` and `a2a-skill-description` tenant templates likewise replace the built-in agent tool and skill descriptions (G-3).
- Agents with `exposeMcpTool` are offered as MCP tools of their own (named by `mcpToolName` or the agent name), listed per tenant to callers allowed to execute them and to run tokens allowed to delegate to them; calling one invokes the agent and waits. Descriptions come from `toolDescriptionTemplateId` or `builtin/mcp-tool-description` (G-5).
- One renderer builds every A2A agent card (the public card, the tenant catalog, and the REST `.../card` route), with the full template language for skill descriptions and the bearer scheme always keyed `garrison` (G-4).

### Defaults

- First start seeds tenant `default` with the administrator `admin@garrison` and password `password` (`GARRISON_ADMIN_EMAIL`, `GARRISON_ADMIN_PASSWORD`). Change them before the server is reachable by anyone else.

### Compatibility notes

These changes landed after the M1 integration and change behavior a client may depend on.

- **Metric names and labels (P13.21 to P13.24).** Dashboards and alerts built on the earlier metrics need updating: `garrison.run.stage.duration`, `garrison.compile.duration`, and the worker duration histograms now have a unit, so their Prometheus names end in `_seconds` (`garrison_run_stage_duration_seconds_bucket`); `garrison.harness.tokens` is joined by the `garrison_run_tokens_total` counter, which is the one to sum; `garrison.worker.harness.tokens` and `garrison.worker.harness.cost_usd` are counters (`_total`), as they always were in the code; `garrison_http_requests_total` gains `route`, `status_code`, and `tenant`; and the run metrics gain `tenant`, `agent`, `deployment`, and `model`. The packaged dashboards use the new names.

- **Start gate and liveness port (P10.20, G-24).** Workers now call `.../started` before launching, with `processId` null, and again with the process ID; servers accept both. Upgrade workers together with the server: an older worker still launches before it reports, so the double-execution fix applies only to updated workers. The liveness probe moved to port 8702; a custom manifest that copied the old probe keeps working because `/v1.0/api/health/live` is still served on 8700.
- **Database errors (G-23, G-25).** Requests that used to fail with `500 InternalError` (or an HTML page) during a database outage or pool exhaustion now answer `503 DatabaseUnavailable` or `503 DatabaseBusy` with `Retry-After`. Clients should retry them.

- **DELETE status codes (G-7).** Deleting one resource now answers 204 No Content with an empty body everywhere. Agents, deployments, harness profiles, prompt templates, MCP servers, secrets, workspace templates, and artifact stores used to answer 200 with `{"deleted": true, "cascaded": n}`, and `DELETE /v1.0/api/tenants/{tenantId}` used to answer 200 with `{"deletedCount": n}`. Filter deletes (runs, audit records, request history) keep 200 with `DeleteCountResponse`, and `DELETE /v1.0/token` keeps 200 with `{"valid": false}`. Clients that read the old bodies must stop; the SDKs already treat an empty body as success. The C# SDK's `Tenants.DeleteAsync` now returns `Task` instead of `Task<DeleteCountResponse>`.
- **Password hashes (G-2).** The `passwordsha256` column keeps its name and size (128 characters) but holds the encoded PBKDF2 hash; no migration is needed. A database rolled back to an earlier build cannot verify upgraded hashes, so those users would need a password reset. The internal model property `User.PasswordSha256` is now `User.PasswordHash`; it was never part of the API (`[JsonIgnore]`).
- **exposeMcpTool and mcpToolName (G-5).** The flag now has an effect: an agent that had it set before this build becomes an MCP tool for its tenant. `mcpToolName` is validated (1 to 64 letters, digits, `_`, `.`, `-`, not starting with `garrison_`); saving an agent with an invalid name answers 400.
- **Rejected (G-5).** The `Rejected` run status and outcome, previously never set, are now used for runs refused at claim. Deactivating a deployment or agent now stops its queued runs from starting.
- **A2A cards (G-4).** `GET .../agents/{idOrName}/card` now matches the public card: the bearer scheme is keyed `garrison` instead of `bearer`, `provider` and `securityRequirements` are present, input modes follow `inputMode` (`Structured` takes `application/json`), and output modes are `text/plain` and `application/json`. The public card renders skill templates with the full template language instead of substituting two placeholders.
