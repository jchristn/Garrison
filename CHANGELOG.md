# Changelog

All notable changes to Garrison are recorded here. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org). Versions below 1.0 are alpha and may break compatibility in any release.

## [0.3.0] - Unreleased

The autonomous agents release, tracked in `AUTONOMOUS_AGENTS_PLAN.md` (task IDs `AA<phase>.<n>`, decisions `AA-<nnn>`). If you upgrade from 0.2.0 on one of the images named in the Mux migration entry under Fixed, read that entry first: a Mux deployment that a restart changed needs its manifest applied again.

### Added

- Keepers (AA1): a mandate gives an agent a standing job, and Garrison wakes it on a schedule to look after it. Each wake is a tick, one run of kind `Keeper` on the mandate's deployment, which ends with the keeper reporting `Quiet`, `Acted`, `Attention`, or `Escalated` through `garrison_keeper_complete_tick`. In Backoff mode quiet ticks lengthen the interval up to a maximum and anything else brings it back to the minimum, with positive jitter; only one tick runs at a time. Mandates have revisions that are drafted and published, run as the principal that last saved them, and are managed over REST (`/mandates`, `/mandate-ticks`), the management MCP tools, manifests (`kind: Mandate`), and the `mandate:{id}` WebSocket channel. New prompt templates `builtin/keeper-system` and `builtin/keeper-tick`, cluster settings `Autonomy.*`, metrics `garrison.keeper.*`, and the Grafana dashboard `garrison-autonomy`. See `docs/KEEPERS.md`.
- Dashboard: an Autonomy group in the sidebar with a Keepers page (AA1.16). The list filters by status and agent and has Pause, Resume, Wake now, and View runs in each row. Creating a keeper writes its first revision in the same form. Each keeper's page shows its schedule, current revision, a chart of the interval after each tick, a paged tick table with an outcome filter, and the revision list with a diff against the previous revision and Publish for drafts. It updates live over the `mandate:{id}` channel and otherwise polls. Delete offers to cancel a running tick when the server answers `MandateActive`. Home has an Autonomy card that counts keepers and lists the ones whose last tick needs a person, and a keeper tick's run links back to its keeper. All nine locales are translated.
- SDKs: a Mandates client in C#, Python, JavaScript/TypeScript, and Go for keepers, their revisions, ticks, and pause, resume, and wake, plus the runs `mandateId` filter and the `Keeper` run kind (AA1.17).
- Postman: a Mandates folder covering every keeper route, with a forced delete in Cleanup (AA1.18).
- Escalations (AA2.1 to AA2.12): a run can ask a person, a role, or another agent for a decision with `garrison_escalate`, optionally with choices, a default answer, a severity, and a timeout. Non-blocking escalations let the run carry on, and a keeper's answer wakes it with the answer in its next tick input. A Blocking escalation suspends the run through durable continuation and resumes it when someone answers. Timeouts use the default answer, cancel, or escalate up to the keeper's default target. Escalations are answered and cancelled over REST (`/escalations`), the run-token MCP tools, and the management tool `garrison_list_escalations`; they stream on the `escalations` WebSocket channel and notify endpoints with `EscalationRaised` and `EscalationExpired`, which an endpoint can filter by minimum severity. Mandate revisions gain a default escalation target. New prompt templates `builtin/escalation-received` and `builtin/escalation-answered`, cluster settings `Escalations.DefaultTimeoutSeconds` and `Escalations.MaxQuestionBytes`, and metrics `garrison.escalations` and `garrison.escalation.answer.duration`.
- Dashboard: an Escalations tab under Autonomy (AA2.13). It opens on the open escalations, filters by status, severity, addressed-to kind, and agent, and answers or cancels from the row menu. The answer dialog shows the question and context as the agent wrote them, offers the options as buttons with the default marked, and takes free text. Each escalation's page links to its raising run, keeper, answering run, and the escalation it was passed up from or to. The Autonomy item in the sidebar counts open escalations (live over the `escalations` channel, otherwise polled), and Home lists them most urgent first with Answer. Keeper revisions gain a default escalation target, notification endpoints gain a minimum escalation severity, and all nine locales are translated.
- SDKs: an Escalations client in C#, Python, JavaScript/TypeScript, and Go to list, read, answer, and cancel escalations, plus the escalation target on keeper revisions, the minimum severity and escalation events on notification endpoints, and the run's escalation ID (AA2.14). The C# SDK's resource type enum also gains Mandate and Escalation.
- Postman: an Escalations folder with list filters, the 404s for an unknown escalation, a keeper default escalation target, and a notification endpoint for escalation events at a minimum severity (AA2.15).
- Docs: `docs/ESCALATIONS.md`, and escalations in the REST, MCP, and WebSocket references and in the continuation, notifications, keepers, manifests, prompts, configuration, and management MCP guides (AA2.16). The NotificationEndpoint manifest kind now carries `escalationMinimumSeverity`, which apply had dropped.
- Brakes (AA3.1 to AA3.7): freezes stop new runs of an agent, deployment, keeper, or agentic app with 409 `Frozen` and skip the keeper wakes in their scope until a person lifts them; `cancelActiveRuns` also cancels what is already running. The autonomy kill switch (`GET, PUT /autonomy/kill-switch`) stops every keeper tick in the tenant and leaves ordinary invocations working. A keeper revision's `budgetPerDayUsd` now caps its daily spend: the keeper becomes `CapReached` until the next UTC day and an `Urgent` escalation goes to its default user or role, while `budgetPerTickUsd` lowers each tick's harness budget and stops a tick that has spent it. Freezes are managed over REST (`/freezes`), the management MCP tools `garrison_list_freezes`, `garrison_freeze`, and `garrison_lift_freeze` (never offered to runs), the `freezes` WebSocket channel, and the `FreezeApplied` and `MandateCapReached` notifications. Usage quotas gain a `Mandate` scope. New metrics `garrison.freezes` and `garrison.spend.cap.hits`, schema version 48, and the `brakes-*` suites.
- Brakes in the dashboard: an Autonomy > Freezes tab, Freeze and Lift with confirmation dialogs on agent, keeper, deployment, and app pages, frozen banners, and the autonomy kill switch on Settings and the Home Autonomy card (AA3.8).
- SDKs: a Freezes client in C#, Python, JavaScript/TypeScript, and Go to list, read, apply, and lift freezes and to read or set the autonomy kill switch, plus the FreezeApplied and MandateCapReached notification events and the Mandate usage quota scope (AA3.9).
- Postman: a Freezes and Kill switch folder that freezes and lifts a keeper and an agent, checks the 409 Frozen refusal, and turns the kill switch on and off (AA3.10).
- Docs: `docs/BRAKES.md` covers freezes, keeper spend caps, and the autonomy kill switch, with the REST, MCP, WebSocket, notification, security, configuration, and keeper docs updated to match (AA3.11).
- Scoped memory (AA4.1 to AA4.12): besides each agent's private memory, the agents of an agentic app now share an `App` memory scope. Every entry has metadata in the database (key, category, tags, version, size, SHA-256, who wrote it, when it was last read, and an optional expiry) and its text in a replaceable `IScopedMemoryStore`. `garrison_memory_read`, `write`, and `delete` take `scope`, `scopeId`, and `expectedVersion` (409 `MemoryVersionConflict` when someone wrote in between), and new `garrison_memory_list` and `garrison_memory_search` list a scope and search keys, tags, and text. REST `/memory/scopes` and `/memory/entries` let people browse, read, and delete entries with the new Memory permissions. Agent memory written before 0.3.0 is imported in place and appears in listings. Deleting an agent, an app, or a tenant deletes its memory, files included. Keeper ticks recall entries tagged `recall` through the new `builtin/memory-recall` template, and `builtin/memory-curator-system` helps a keeper tidy a shared scope. New cluster settings `Memory.Scoped.Enabled`, `Memory.Scoped.MaxValueBytes`, and `Memory.Scoped.MaxEntriesPerScope`; metric `garrison.memory.operations` with a Memory row on the Autonomy dashboard; schema version 49.
- Dashboard: an Autonomy > Memory tab lists memory scopes and entries with who wrote each and when it was last read, shows an entry's text as plain data, and deletes entries after confirmation (AA4.13).
- SDKs and Postman: a Memory client in C#, Python, JavaScript/TypeScript, and Go to list memory scopes and entries, read an entry's text, and delete entries, and a Postman Memory folder that writes an entry over MCP and reads, searches, and deletes it over REST (AA4.14).
- Docs: `docs/AGENT_MEMORY.md` covers memory scopes, the access policy, provenance, recall, curation, memory from before 0.3.0, and replacing the store, with the REST, MCP, configuration, backup, security, prompts, keepers, and NotDory docs updated to match (AA4.15).
- Reports (AA5.1 to AA5.9): a run files an immutable report upward with `garrison_file_report`: kind (`Status`, `Incident`, `Decision`, `Handoff`, `Brief`), health, audience, title, body, period, metrics, issues, and decisions. A replayed filing returns the first report. The entry agent of an app reads its members' reports with `garrison_list_reports` and `garrison_get_report`, peers do not read each other's, and a manager keeper's tick input carries its team's new reports through the new `builtin/report-digest` template, framed as data. People read reports, a metric series per author, and file their own with REST `/reports` and the new Report permissions. An `Unhealthy` report can notify (`ReportUnhealthy`), and the tenant `reports` WebSocket channel sends `report.filed`. New cluster settings `Reports.MaxBodyBytes` and `Reports.DigestMaxReports`; metric `garrison.reports` with a Reports row on the Autonomy dashboard; schema version 50.
- Dashboard: an Autonomy > Reports tab lists reports with author, kind, health, app, and date filters and files a report from a dialog; the report page shows its health, metrics, issues, and decisions as plain text and charts a metric for its author over time (AA5.10).
- SDKs and Postman: a Reports client in C#, Python, JavaScript/TypeScript, and Go to list, read, and file reports and read a metric series, the `ReportUnhealthy` notification event, and a Postman Reports folder (AA5.11, AA5.12).
- Docs: `docs/REPORTS.md` covers filing, who reads which report, the manager's tick digest, metric series, notifications, settings, and permissions, with the REST, MCP, WebSocket, notification, configuration, prompts, keepers, and security docs updated to match (AA5.13).
- Messages between agents (AA6.1 to AA6.11): a run writes to another agent with `garrison_send_message` along an app edge, answers with `garrison_reply_message`, receives its inbox with `garrison_read_inbox`, and acknowledges with `garrison_ack_message`. Normal mail reaches a keeper with its next tick through the new `builtin/inbox-delivery` template, framed as data; urgent mail wakes the keeper now, or starts a run of the new kind `Message` through `builtin/message-wake` for an agent without one. Loop guards refuse messages past `Messaging.MaxHops`, `Messaging.ThreadBudget`, or `Messaging.LineRatePerMinute`, to a frozen agent, or without a line, and every refusal is stored with its reason. People write to any agent and browse messages and threads with REST `/messages` and `/message-threads` and the new AgentMessage permissions; the `agent-inbox:{agentId}` WebSocket channel reports each change. Escalations to an agent now arrive as urgent messages. New cluster settings `Messaging.*`, metrics `garrison.messages`, `garrison.message.delivery.lag.duration`, and `garrison.message.loop.guard` with a Messaging row on the Autonomy dashboard; schema version 51.
- Dashboard: an Autonomy > Messages tab with filters and a Rejected view that shows each refusal's reason, a thread page, a Send message dialog that explains a refused message, an Inbox tab on each agent's page, and a count of loop-guard rejections on the Home Autonomy card. All nine locales are translated (AA6.12).

- Organizations (AA7.1 to AA7.8, AA7.11 to AA7.13): an organization is a tree of org units, each with a lead agent, members with titles and mandates, an optional app, peer lines, and day or month budgets on its whole subtree. People edit the working tree with REST `/organizations/{id}/units`, snapshot it as a revision that pins each mandate's current revision, publish it, and roll back to an earlier one, with promotion records of subject Organization. The live revision is the chain of command: messages travel reporting and peer lines, Manager and Chain reports reach the leads above, OrgUnit and Organization memory scopes open to members, escalations to Manager go to the agent's manager and escalate up the chain, freezes take OrgUnit and Organization targets, and a subtree that spends its budget is refused with 409 `BudgetExhausted` while its manager is told. Member runs get `builtin/org-context` in their system prompt and the `garrison_org_chart` and `garrison_org_whoami` tools; Agent capabilities carry the agent's unit and mandate summary. New user MCP tools for organizations, the `organization:{orgId}` WebSocket channel (`org.changed`, `report.filed`, `spend.updated`), Organization permissions, the `garrison.org.budgets.exhausted` gauge with an Organizations row on the Autonomy dashboard, and schema version 52.
- Organizations in manifests and the studio (AA7.9, AA7.10): a `kind: Organization` document holds the organization's units nested under their parents and publishes the tree when it applies (unless `publish: false`); exports follow its agents, mandates, and apps. Studio drafts hold Organization items, the graph shows organizations, units, and peer lines, and new graph operations add and remove units, members, and peer lines. The architect skill documents the kind.

- Executive authority (AA8.1 to AA8.11): a deployment with `managementAccess: OrgSubtree` whose agent leads an org unit is that unit's executive. Its runs work on studio drafts limited to the units below its own: their agents, deployments, mandates, and the templates and assets only they use. Hard limits no rule lifts refuse a draft that touches the executive itself or its own unit or anything above it (`SelfModification`, `OutsideSubtree`), deletes records or touches secrets or other kinds (`ForbiddenKind`), raises a budget (`BudgetIncrease`), or changes management access (`AuthorityChange`). People write change rules (`/change-rules`, prefix `cru_`) that pre-authorize narrow change classes (PromptRetune, WakeTuning, MandateTextEdit, AddWorker, RemoveWorker, ModelChange, DeploymentWeight) in a unit's subtree with optional limits and expiry; a draft whose every change a rule covers applies at once with approval source `Rule`, otherwise a person decides. Every executive apply is recorded as an org revision, and rolling the organization back undoes it. Proposals are listed and decided at `/organizations/{id}/proposals`, stream as `proposal.changed` on the organization channel, and rule applies notify `OrgProposalApplied` endpoints. New MCP tools `garrison_list_change_rules` (executive runs and people) and the change rule and proposal tools for people, the `builtin/executive-system` prompt fragment (compile preview now shows the organization and executive fragments), metric `garrison.org.proposals`, span `org proposal validate`, schema version 53, and the `executives-*` suites. A run token now reaches only drafts of the person it acts for over REST, as it already did over MCP.
- Dashboard: Autonomy > Change rules lists and edits the rules that pre-approve routine executive changes (organization, covered unit, change classes, limits, expiry). The organization page gains a Proposals tab with each executive proposal's decision (applied by rule, approved, needs approval, denied), a review of its changes with the rule covering each and any refusals, and Approve and Deny. Deployments gain a Management access choice, including OrgSubtree (AA8.12).
- SDKs and Postman: change rules (`ChangeRules` client) and organization proposals (list, read, decide) in C#, Python, JavaScript/TypeScript, and Go, with the `OrgSubtree` management access, `ChangeRule` resource type, `OrgProposalApplied` event, executive fields on studio drafts, refusals and rule matches on draft diffs, and draft links on org revisions; Postman gains a Change rules folder (AA8.13).
- Docs: `docs/EXECUTIVES.md` explains executive authority (`managementAccess: OrgSubtree`), its hard limits and refusal codes, change classes, change rules and how drafts match them, rule applies recorded as org revisions with revert drafts that rollback applies, the proposals routes and MCP tools, `proposal.changed`, and `OrgProposalApplied`, with a worked example; `docs/SECURITY.md` gains an executive authority threat section, and the REST, MCP, WebSocket, organization, studio, manifest, prompt, notification, and revision docs cover the feature (AA8.14).
- Evaluation data model (AA9.1, AA9.2): eval sets with versions, tags, and cases (input, hidden flag, expected text, checks with a scorer, argument, and weight, and files), eval runs against an agent revision or a deployment with their case and check results, shadow trials, and canary releases with steps, in schema version 54 on Sqlite and Postgresql. Approved eval sets never change: editing one opens the next version as a Draft with copies of its cases. Runs gain `evalRunId` and `shadowTrialId` and the `Eval` and `Shadow` kinds; new resource types `EvalSet`, `EvalRun`, `ShadowTrial`, and `CanaryRelease`; the `CanaryRolledBack` notification event; cluster settings `Evaluation.MaxConcurrentCases` and `Evaluation.MaxCasesPerSet`.
- Evaluation engine (AA9.3 to AA9.6, AA9.11 to AA9.14): eval runs score an agent revision (a studio draft's too) or a deployment against an eval set, each case as its own `Eval` run, a few at a time (`Evaluation.MaxConcurrentCases`) and within an optional budget, with ExactMatch, Contains, JSON Schema, and judge scorers. A judge agent grades through the new `builtin/eval-judge` template, which frames the case and the answer as data, and replies with a score, passed, and a reason. Eval runs can also replay a deployment's recent inputs. Only people approve eval sets; an executive's own set never gates its own change, and its runs see hidden cases as scores only. An environment can now require an eval set and a threshold, and promotion into it fails with `EvalGateFailed`, naming the eval run, until a run of the revision passes the latest approved version (schema version 55). New routes under `/eval-sets` and `/eval-runs`, MCP tools `garrison_run_eval`, `garrison_get_eval_run`, `garrison_list_eval_sets`, `garrison_create_eval_set`, and `garrison_approve_eval_set`, the `eval-run:{id}` WebSocket channel, and the `garrison.eval.runs` and `garrison.eval.case.duration` metrics.
- Shadow trials (AA9.7): a trial copies a sampled share of the runs a source deployment finishes to another deployment of the same agent as `Shadow` runs, after the source run finished and off its completion path, so the source run is never delayed or changed. A shadow run answers no caller, conversation, trigger, pipeline, or app, sends no run notification, and runs at the lowest priority under the identity of the person who started the trial. Its run token refuses every tool that would cause an effect with `ShadowRunRefused` (non-read tools, agent tools, messaging, escalation, report, memory writes, studio drafts, file writes, other runs), its tool list hides them, its permission prompts are always denied, it neither reads nor writes back a file space, and Claude Code shadows are put in permission mode so their own tools ask first. Each finished shadow run is compared with its source through the `IShadowComparer` seam (default: normalized text) and counted as agreed, diverged, or a candidate failure; the leader completes trials at their end time. A shadow run's cost is recorded like any run's and counts toward spend and org budgets.
- Canary releases (AA9.8): a release moves an agent's traffic from a baseline deployment to a candidate in steps. Each step's percent becomes the candidate's weight (percent times 10 on the 0 to 1000 scale) and the baseline gets the rest. The leader advances a step once it has its minimum runs and minutes and the candidate's error rate (failed and timed-out runs over finished ones, not counting shadow and eval runs) and, with an eval gate, its latest completed eval score are within the thresholds; past the last step the candidate is promoted to weight 1000 and the baseline to 0. A crossed threshold rolls both weights back to where they started, early if the error rate is already over with enough runs, and sends the `CanaryRolledBack` notification. Every move is a compare-and-set, so replicas and a concurrent abort never apply weights twice.
- Shadow trial and canary routes and tools (AA9.12, shadow and canary part): `GET, POST /shadow-trials`, `GET /shadow-trials/{id}`, `POST /shadow-trials/{id}/stop`, `GET, POST /canary-releases`, `GET /canary-releases/{id}`, `POST /canary-releases/{id}/abort`, and the MCP tools `garrison_list_shadow_trials`, `garrison_get_shadow_trial`, `garrison_start_shadow_trial`, `garrison_stop_shadow_trial`, `garrison_list_canary_releases`, `garrison_get_canary_release`, `garrison_start_canary`, and `garrison_abort_canary`, for people only. Viewers and Auditors read them, Editors and AgentDevelopers start them, and AgentOperators read, stop, and abort them.
- Telemetry (AA9.14, shadow and canary part): `garrison.shadow.comparisons` by `result` and `garrison.canary.transitions` by `result`, and the spans `shadow compare` and `canary step`, which set an error status on failure.
- Eval gates on change rules (AA9.10): a rule that lists `AddWorker` or `ModelChange` can name `gateEvalSet` and `gateThreshold` (default 1, schema version 56). Such a change is covered only once the draft has a completed eval run against the set's latest approved version, created after the draft's items last changed, at or above the threshold; until then it waits for a person, its rule match carries `code` `EvalGatePending` with the reason, and a covered change names the passing run in `gateEvalRunId`. Rule validation adds `GateClassRequired`, `GateSetRequired`, `EvalSetNotFound`, and `EvalSetNotApproved`. An executive can ask again to apply a proposal that waits: still uncovered it gets the same pending approval, covered now the old approval is cancelled and the draft applies by rule. Drafts record `contentChangedUtc`. Eval runs of a draft now evaluate the draft's deployment too: a Deployment document for the agent (a model change, for example) becomes an eval copy in the `draft` environment that the cases run on, and a worker the draft adds is evaluated as protected eval copies of its agent and deployment. Proposals (read, summary, `proposal.changed`) and the `OrgProposalApplied` notification carry `evidence`: the draft's eval runs with score, threshold, and passed, and shadow trials and canary releases of the deployments it changes. The executive prompt lists each rule's gate. MCP `garrison_create_change_rule` and `garrison_update_change_rule` take `gateEvalSet` and `gateThreshold`.
- Shadow comparisons through the eval scorers (AA9.7 follow-up): a trial with `comparisonEvalSetId` scores the candidate's output with the distinct checks of the set's cases (its latest approved version, or the named set when none is approved), with the source run's output as the reference; ExactMatch and Contains compare with the source output, JsonSchemaValid and Judge keep their arguments. `useJudge` adds a Judge check that runs the set's judge agent with `builtin/eval-judge` as the person who started the trial. The outputs agree when the score passes. Starting a trial that needs a judge without a judge agent fails with `JudgeAgentRequired` or `JudgeAgentNotFound`. A trial without either still compares normalized text.
- Canary eval gates run their own evals (AA9.8 follow-up): once a gated step has its minimum runs and minutes, the leader starts an eval run of the candidate on the release's eval set with `minEvalScore` as the threshold, as the person who started the release, and uses its score. Each step needs an eval run created since it started; eval runs anyone else starts on the same set and candidate count too. A failed eval run, or one that cannot start, rolls the release back. If two replicas start one each, the next sweep cancels the newer.
- Dashboard: Autonomy gains Eval sets, Eval runs, Shadow trials, and Canary releases (AA9.15). An eval set's page lists its cases (input, expected output, scorers, hidden) with a case form that edits each check per scorer (exact text, text to find, JSON Schema, or the judge's rubric, with a weight), the set's versions, and its recent runs; Approve freezes a draft, and editing an approved version, the set or a case, opens the next version as a draft and follows it. Run set evaluates a deployment (its cases or its recent inputs) or an agent revision with an optional threshold and budget. An eval run's page follows the `eval-run:{id}` channel case by case (polling without it) with progress, score against the threshold, cost against the budget, and a row per case with failing and errored cases marked and a failing-only filter; a case opens with the expected output against the output as a line diff and each check's score, scorer note, and judge run. Shadow trials show compared, agreed, diverged, and candidate failure counts with the agreement rate, and canary releases show their steps with the current one, the eval gate, and the rollback reason; both start from a form and stop or abort with a reason. Enum mirrors for the eval enums, the four resource types, the `Eval` and `Shadow` run kinds, and `CanaryRolledBack`; nine locales with tooltips and explainers (the eight translations want a native review), unit tests, mocks, contract routes, and an e2e spec with an accessibility scan at 1280 and 390 px in both themes.
- Studio playground: a succeeded turn has Save as eval case (AA9.9), which turns its input and answer into a case (both editable, with optional checks and hidden) of a chosen eval set or a new one with origin Playground, with `sourceRunId` set to the playground run, and then links to the set and to running it against the playground agent's draft revision.
- Eval case files reach the case run (AA9.3 hardening): each file of a case is written into the workspace of that case's run before its harness starts, inline text as bytes (never rendered as a template) and asset files from the asset's latest version, downloaded and checked against their SHA-256. Copies in use by a run, an eval run, a shadow trial, or a canary release are kept; eval runs and results always are.

Postman gains Eval sets, Eval runs, Shadow trials, and Canary releases folders.

### Fixed

- A server restart broke every Mux deployment that used `baseUrl` and a model instead of a named endpoint. The startup runtime migration moved such a deployment to a saved connection that kept neither the URL nor the model, so its next run called `gpt-4o-mini` at `https://api.openai.com/v1` and failed with a 404. In the AA12.7 round 2 trials every org keeper and the lead failed this way after a restart. The migration now leaves those deployments alone; named-endpoint deployments still move. New Touchstone case `provider-api-<provider>/mux-legacy-endpoint`. The migration reached `main` on 2026-11-02 and is in the published `v1.3.0` image and the `v0.2.0` and `latest` images rebuilt on 2026-11-10, so a deployment changed by a restart on those images needs its manifest applied again after upgrading.
- Garrison's prompts named its MCP tools by their plain names, but most harnesses show them with the server name in front (Mux: `garrison.garrison_keeper_complete_tick`), so a model on Mux called tools that do not exist (AA12.7). Harness profiles have a new `mcpToolNamePrefix` field (schema migration 60), set for Claude Code, Mux, Gemini CLI, opencode, pi, and the provider API from each harness's own code. The compiler renders it as `garrison.toolPrefix`, the built-in system prompt fragments name every tool with it, and the new `builtin/mcp-tool-names` fragment tells the model how plain names in its task, messages, and the deployment's own prompts map to the names it sees. Codex is unchanged.
- A run the harness reported as successful counted as `Succeeded` even when the model gave no answer and called no tools, as Mux did after spending its whole output budget on reasoning. A keeper tick then ended `Unreported` and a message run left its message `Delivered` with nothing done (AA12.7). The agent harness parsers (Claude Code, Codex, Codex app-server, Gemini CLI, Mux, opencode, pi, provider API) now fail such a run as `HarnessFailed` with a message that starts with `EmptyResponse:` and, when the model used output tokens, suggests a larger output limit. Generic JSON lines and plain text harnesses keep succeeding on empty output.
- Mux 1.8.0 exits 2 when a run completes with errors (a tool call was refused and the model went on), and `builtin/mux` accepted only exit 0, so a run with a complete answer was recorded `Failed` (`HarnessFailed`). In the AA12.7 round 2 team trial the generalist's answer scored 20 of 20 and its run still failed. The profile now accepts exit codes 0 and 2, and the Mux parser no longer fails a run on a `tool_call_denied` error by itself, since the model sees the refusal and may go on; a run still needs Mux's `completed` or `completed_with_errors` event to succeed. New parser case `mux-1.8.0-exit-2`.
- A board brief could contradict the board view. The `builtin/board-brief` section asked the CEO for a brief but gave it nothing to brief from, so the CEO saw only reports filed since its last tick; in the AA12.7 board trial it wrote "All keepers report Healthy" while the board view showed latency `Degraded`, and left out a peer line the board had approved. The section now carries Garrison's own record for the period since the last brief: unit health, spend against budget, organization revisions published, proposals decided and waiting, open escalations, recent unhealthy reports, freezes, and the kill switch, and tells the CEO its brief must agree with it. Agent-written titles, questions, and notes are framed between lines with a random marker (AA-025). A proposal the board denied (which goes back to `Open`) is listed as decided, not as waiting. When nothing waits, the section says so, so a CEO that remembers a proposal as pending is told it is not. New template variables are listed in `docs/PROMPTS.md`.
- Messages between agents referred to files the recipient could not see. In the AA12.7 team trial a tester wrote "see the attached test file", attached nothing, and the reviewer spent its whole run searching the disk. `builtin/inbox-delivery` now tells the recipient it cannot see senders' workspaces and should reply to ask for missing contents, and `garrison_send_message` and `garrison_reply_message` tell the sender to put everything the recipient needs in the body.
- A reply sent without an urgency was always Normal, so in the AA12.7 round 2 team trial the tester's answer to the reviewer's urgent request waited in the reviewer's inbox for good: the reviewer has no keeper, and only urgent mail wakes such an agent. `garrison_reply_message` now keeps the original message's urgency unless the run gives one.

### Changed

- Direct agent edits (REST, MCP, self-registration, and Agent manifests without `revision.publish: false`) publish their content as the next revision when it changed, so every existing edit path keeps working and still leaves a history (AD-030). Migration builds revision 1 for every existing agent.
- `builtin/garrison-tools-instructions` includes the catalog and fan-out fragments when delegation is on, and `builtin/default-system` includes the asset listing, so delegating agents and agents with assets are told about them (AD2.3, AD4.7, AD5.6).
- A revision's `SystemPrompt` asset replaces the deployment's `System` binding (AD-031).
- Agent manifests accept `capabilities` and `assets`; Deployment manifests accept `environment`, `agentRevision`, and `managementAccess` (AD1.7, AD2.6, AD7.4, AD7.8).
- Templates can read a JSON object input's fields as `input.fields.<name>` (AD10.1).
- Re-applying an unchanged `HarnessProfile` without a `sessionFormat` no longer reports `Updated` (AD5.9).
- The dashboard image also serves the app UI under `/apps/`, and `/apps/config.js` carries the same `GARRISON_API_URL` as the console (AD6.7).
- Run objects carry `agentRevisionId`, `fanOutGroupId`, and `fileSpaceId`; conversations can be filtered by `appId` (AD1.3, AD3.1, AD5.7, AD6.11).
- The dashboard sign-in no longer asks for a server URL. The console uses `GARRISON_API_URL` when it is set and otherwise the page's own origin, which the image's nginx proxies to the server. A "Use a different server" link appears only in development builds or when `GARRISON_CSP_CONNECT_SRC` allows extra origins, and a remembered server URL is ignored otherwise. Compose, Kustomize, and Helm pass both settings to the dashboard.
- The app UI uses the JavaScript SDK's gateway client through the new `@garrison/sdk/gateway` entry point instead of its own copy (AD12.8).

- Applying a studio draft is all or nothing. The manifest dry run now runs the write-time checks too (deployment and app validation against the planned records), and a document that fails while writing rolls back every document written before it, including the prompt template versions it added. The dashboard shows that message in the decision dialog; only 409 `ApprovalNotPending` says someone else decided.

- The app chat's message box is one line tall (it grows when you resize it), and the Send button always matches its height.

### Breaking

- **JSON fields are JSON, not strings.** Responses no longer carry JSON serialized into strings. An agent's, revision's, and capability's `inputSchemaJson` and `outputSchemaJson` are now `inputSchema` and `outputSchema` (objects; requests send objects too, and a JSON string is still accepted). A run's `structuredOutputJson` is `structuredOutput`, also on fan-out members and MCP run summaries. A run event's `rawEventJson` is `rawEvent` (an object), or `rawEventText` when the line is not valid JSON (a plain line, or one truncated to the configured size); a tool call's JSON arguments are `toolInput` and a tool result's JSON output is `toolOutput`, with `text` left out for those, and transcripts do the same. An approval carries `input` (the tool arguments or the studio draft diff) when it is JSON and `inputPreview` only for clipped text. A notification delivery's `payload` is an object; the signed bytes sent to the endpoint are unchanged. MCP server test `toolDetails` carry `inputSchema`, and an agent revision diff's `from` and `to` are JSON values. Validation errors name `inputSchema` and `outputSchema`, and manifest export writes the schemas as mappings. The worker protocol, the dashboard, the app UI, all four SDKs, Postman, and the docs use the new shapes. Request history bodies stay strings, since they can be any media type.
- **Version and tags.** The version is `0.2.0` and image tags are `v0.2.0`, with no `-alpha` suffix; a 0.x version means alpha. Replace pinned `v0.1.0-alpha` tags with `v0.2.0` for the server, worker, and dashboard together (AD0, AD-028).
- **Reset on a built-in prompt template.** `POST .../prompt-templates/{id}/reset` on a built-in used to answer 409 `BuiltInImmutable`. It now re-applies the shipped content and answers 200, adding a version only when the stored text drifted (AD-025, AD7.13). Clients that treated the 409 as "this is a built-in" should read `isBuiltIn` instead. Update and delete of built-ins still answer 409.
- **Deleting a bound prompt template.** Deleting a template that any deployment binds, pinned or not, answers 409 `PromptTemplateInUse` and names the deployments (AD-026, AD7.15). Switch or unbind those deployments first.
- **Deleting an app member.** Deleting an agent that belongs to an agentic app answers 409 `AgentInUse` (AD6.1). Remove it from the app first.
- **Environments.** Deployment environments are validated against the tenant's list (400 `UnknownEnvironment`), and the `draft` environment is reserved for the playground (400 `ReservedEnvironment`) (AD1.3, AD9.1). Rename any deployment environment outside the list before upgrading automation that sets it.
- **Dashboard image build context.** `dashboard/Dockerfile` now builds from the repository root because it includes `app-ui/`: run `docker build -f dashboard/Dockerfile .` from the root instead of building inside `dashboard/` (AD6.7). Compose, the build scripts, and the Kubernetes scripts already do.
- **Architect prompt catalog is paginated.** `GET .../studio/architect-prompts` and `garrison_studio_list_architect_prompts` return an `EnumerationResult` (`objects`, `totalRecords`, and so on) and accept `maxResults`, `skip`, and `search`, instead of a bare array. The order is unchanged: built-ins, then their tenant clones, then other tenant System templates.
- **Custom ingresses and proxies.** End-user apps need `/apps/` routed to the dashboard and `/v1.0/apps/` to the server, with proxy buffering off for `/v1.0` so turn and file streams flow (AD6.12). The supplied Compose, Kustomize, and Helm configurations already route both.

### Security

- Run tokens of deployments with `managementAccess: Drafts` reach studio drafts only for the person who started the run, always within that person's permissions; they can never apply a draft, decide an approval, delete live resources, or read secret values, and the grant ends with the run (AD-017, AD7.4). Runs can never decide a `DraftApply` approval, whatever their permissions.
- Runs cannot read or change architect prompts or prompt templates through MCP, including the architect's own runs (AD7.14).
- App sessions are a separate credential: `gas_` tokens stored only as SHA-256 hashes, accepted only on `/v1.0/apps/{slug}/` for that app and its owner's own conversations, refused by the management API, and expiring per `Apps.SessionMinutes` and `Apps.AnonymousSessionMinutes`. Anonymous use needs both `authMode: Anonymous` and `anonymousEnabled`. Runs started through an app run as the app, bounded by the entry agent's graph-derived allow list (AD-021, AD-035, AD6.5).
- The `AppUser` role grants Execute on one `AgenticApp` at resource scope and nothing else. The `Releaser` role holds Execute on `Promotion` and can be limited to one target environment by resource scope (AD1.4, AD6.5).
- Asset and file space downloads use short-lived per-file tickets, workers verify SHA-256 before a run starts, and run pods still receive bytes rather than URLs or credentials (AD2.4, AD3.3). File space paths refuse traversal, absolute paths, and links.
- Macro-enabled Office formats are refused as assets unless `Assets.AllowMacroFormats` is set (AD2.2).
- Tool probes are limited to a bare executable on the `PATH` with one version or help flag, because they run on shared worker hosts outside any run (AD-033).
- The MCP binding pattern keeps the bound server's bearer token out of events, transcripts, and run records (AD10.3).

## [0.1.0-alpha] - Unreleased

The first build of Garrison: a multi-tenant control plane that runs headless agent harnesses on pull-based worker nodes and exposes them over REST, MCP, and A2A. This release is the MVP milestone in `archive/GARRISON_PLAN.md`.

### Control plane

- D-063 makes the artifact file ceiling explicitly configurable up to 256 MiB while keeping the 16 MiB default. This permits larger complete-HOME continuation archives when operators also allow them in REST/proxy limits; extraction bounds and fencing remain enforced. C# SDK compiled settings preserve the same range. Download validation follows the configured cap across storage providers, removing a separate hardcoded 64 MiB restore ceiling while retaining recorded-length checks.

Only system administrators see the `tenantId` argument; run-token sessions and other callers act in their own tenant, and the descriptions tell models to leave optional arguments out.

- Agents can be addressed by name or ID on every agent route, with authorization checked against the resolved agent.
- A tenant overrides the description of any built-in MCP tool for its own callers with a `ToolDescription` template named `mcp-tool-<tool name>`, rendered with `tool.name`, `tool.defaultDescription`, `tenant.id`, and `garrison.version`; `mcp-tool-description` and `a2a-skill-description` tenant templates likewise replace the built-in agent tool and skill descriptions (G-3).
- Agents with `exposeMcpTool` are offered as MCP tools of their own (named by `mcpToolName` or the agent name), listed per tenant to callers allowed to execute them and to run tokens allowed to delegate to them; calling one invokes the agent and waits. Descriptions come from `toolDescriptionTemplateId` or `builtin/mcp-tool-description` (G-5).
- One renderer builds every A2A agent card (the public card, the tenant catalog, and the REST `.../card` route), with the full template language for skill descriptions and the bearer scheme always keyed `garrison` (G-4).

### Compatibility notes

These changes landed after the M1 integration and change behavior a client may depend on.

- **Node protocol and administrator accounts (P15.1).** A credential or user that reached the node protocol only through `isTenantAdmin` or an `All` grant (such as a `TenantAdmin` credential used as a worker key) is now refused with 403; give workers a `NodeAgent` credential, which every shipped configuration already does. Creating or rotating a system administrator's credential, or changing their password or email, now needs a system administrator (400 otherwise). A run token's `POST .../runs/{id}/retry` answers 403. Requests larger than 128 MiB answer 413; raise `Rest.MaxRequestBodyBytes` if you send larger bodies.

- **Empty input (D-050).** Invoking an agent, creating a run, testing a deployment, or starting a pipeline with no body or with an empty or whitespace `input` used to start a run with empty input; it now answers 400 `ValidationFailed` with field code `InputRequired` on `input`, and nothing is created. For an agent with no deployment, the 400 now comes before the 409 `NoActiveDeployment`. MCP and A2A already rejected an empty input and still do. Retrying an existing run reuses its stored input and is not affected.
- **Codex sandbox default (G-29).** On containerized workers and in run pods, deployments of `builtin/codex` and `builtin/codex-app-server` without a `sandbox` parameter now run with `danger-full-access` instead of `workspace-write` (which could not run shell commands there). Set `sandbox` on the deployment to keep the old value. Workers run directly on a host are unchanged. Upgrade workers with the server: an older worker does not report `containerized`, so its runs keep `workspace-write`.
- **Response warnings (I-08).** Create and update responses may carry a new `warnings` array, and manifest apply items a new `warnings` list. Clients that reject unknown properties need to accept them; stored values did not change.
- **Effect policy replaces retryOnNodeLoss (P12.29).** `retryOnNodeLoss` is deprecated and still accepted on input for one release over REST, MCP, and manifests: alone, `true` maps to `AtLeastOnce` and `false` to `AtMostOnce`. A request that also sends `effectPolicy` with a different meaning is now rejected with 400 and the field code `EffectPolicyConflict` on `effectPolicy` (a manifest item reports it as its `errorCode`). Responses carry `effectPolicy` plus a derived, read-only `retryOnNodeLoss` (`true` only for `AtLeastOnce`), so a client that reads a deployment, changes `effectPolicy`, and sends the whole body back must drop or update `retryOnNodeLoss`. The default for new deployments did not change: `retryOnNodeLoss` already defaulted to `false` on every surface (REST, MCP, manifests, the dashboard form, and the C# SDK), and the new default `AtMostOnce` is the same behavior. Existing deployments keep their behavior through the migration. The C# SDK's `Deployment.RetryOnNodeLoss` is now a view of `EffectPolicy`; the Python, JavaScript, and Go SDKs gain `effectPolicy`.

- **Metric names and labels (P13.21 to P13.24).** Dashboards and alerts built on the earlier metrics need updating: `garrison.run.stage.duration`, `garrison.compile.duration`, and the worker duration histograms now have a unit, so their Prometheus names end in `_seconds` (`garrison_run_stage_duration_seconds_bucket`); `garrison.harness.tokens` is joined by the `garrison_run_tokens_total` counter, which is the one to sum; `garrison.worker.harness.tokens` and `garrison.worker.harness.cost_usd` are counters (`_total`), as they always were in the code; `garrison_http_requests_total` gains `route`, `status_code`, and `tenant`; and the run metrics gain `tenant`, `agent`, `deployment`, and `model`. The packaged dashboards use the new names.

- **Start gate and liveness port (P10.20, G-24).** Workers now call `.../started` before launching, with `processId` null, and again with the process ID; servers accept both. Upgrade workers together with the server: an older worker still launches before it reports, so the double-execution fix applies only to updated workers. The liveness probe moved to port 8702; a custom manifest that copied the old probe keeps working because `/v1.0/api/health/live` is still served on 8700.
- **Database errors (G-23, G-25).** Requests that used to fail with `500 InternalError` (or an HTML page) during a database outage or pool exhaustion now answer `503 DatabaseUnavailable` or `503 DatabaseBusy` with `Retry-After`. Clients should retry them.

- **DELETE status codes (G-7).** Deleting one resource now answers 204 No Content with an empty body everywhere. Agents, deployments, harness profiles, prompt templates, MCP servers, secrets, workspace templates, and artifact stores used to answer 200 with `{"deleted": true, "cascaded": n}`, and `DELETE /v1.0/api/tenants/{tenantId}` used to answer 200 with `{"deletedCount": n}`. Filter deletes (runs, audit records, request history) keep 200 with `DeleteCountResponse`, and `DELETE /v1.0/token` keeps 200 with `{"valid": false}`. Clients that read the old bodies must stop; the SDKs already treat an empty body as success. The C# SDK's `Tenants.DeleteAsync` now returns `Task` instead of `Task<DeleteCountResponse>`.
- **Password hashes (G-2).** The `passwordsha256` column keeps its name and size (128 characters) but holds the encoded PBKDF2 hash; no migration is needed. A database rolled back to an earlier build cannot verify upgraded hashes, so those users would need a password reset. The internal model property `User.PasswordSha256` is now `User.PasswordHash`; it was never part of the API (`[JsonIgnore]`).
- **exposeMcpTool and mcpToolName (G-5).** The flag now has an effect: an agent that had it set before this build becomes an MCP tool for its tenant. `mcpToolName` is validated (1 to 64 letters, digits, `_`, `.`, `-`, not starting with `garrison_`); saving an agent with an invalid name answers 400.
- **Rejected (G-5).** The `Rejected` run status and outcome, previously never set, are now used for runs refused at claim. Deactivating a deployment or agent now stops its queued runs from starting.
- **A2A context identifiers (P12.1).** A task's `contextId` used to be its root run's identifier; it is now its conversation's identifier (`cnv_...`), or the `contextId` the client sent. Every A2A message starts or continues a conversation, so a second message with the same `contextId` resumes the agent's session instead of starting fresh, and a message sent while the same context's previous task is still working is rejected with `ConversationBusy`. Use a new `contextId` (or none) for independent requests. `ListTasks` with a conversation's `contextId` lists its tasks; a root run identifier still lists a delegation chain.
- **Mux sessions (P12.1).** `builtin/mux` now persists the Mux session (`--session-id <run id>`, no `--no-session-persistence`) for conversation turns as well as for agents with an output schema; the condition is the new template variable `run.persistSession`. Clones of the profile keep their own conditions.
- **Workers and conversations (P12.1).** Upgrade workers with the server: an older worker ignores the conversation settings in the execution spec, runs a resumed turn in fresh per-run directories, and the harness then fails because the session is missing.
- **A2A cards (G-4).** `GET .../agents/{idOrName}/card` now matches the public card: the bearer scheme is keyed `garrison` instead of `bearer`, `provider` and `securityRequirements` are present, input modes follow `inputMode` (`Structured` takes `application/json`), and output modes are `text/plain` and `application/json`. The public card renders skill templates with the full template language instead of substituting two placeholders.
