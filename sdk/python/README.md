# garrison-sdk (Python)

Python client for the Garrison REST API. Requires Python 3.9+ and `requests`.

## Install

The package is not published to PyPI yet, so `pip install garrison-sdk` fails with "No matching distribution found". Install it from your checkout of the repository instead:

```bash
pip install /path/to/Garrison/sdk/python        # or, from the repository root: pip install ./sdk/python
```

Use `pip install -e ./sdk/python` if you want edits to the SDK source to take effect without reinstalling. An editable install writes `garrison_sdk.egg-info` into `sdk/python`; it is gitignored.

## Quick start

```python
from garrison_sdk import GarrisonClient

client = GarrisonClient("http://127.0.0.1:8700")
client.login("admin@garrison", "password")      # the same email and password you use in the dashboard

run = client.agents.invoke("my-agent", "Summarize the release notes", wait=True, wait_seconds=120)
print(run["status"], run.get("resultText"))
```

To sign in with an access key pair instead, call `client.login_with_keys(access_key, secret_key)`. See "Where the credentials come from" below.

## Where the credentials come from

Email and password sign-in works the same on every runtime: tenant `default`, user `admin@garrison`, and the administrator password. There is no default: on Docker Compose it is `GARRISON_ADMIN_PASSWORD` in `docker/.env`, which `update.sh` generates when it is missing. On Kubernetes it is whatever `GARRISON_ADMIN_PASSWORD` held when `k8s/scripts/generate-secrets.sh` ran, or the random one it printed, stored in Secret `garrison-secrets`. A source build in development mode (`GARRISON_ALLOW_INSECURE_DEFAULTS=true`) uses `password`.

The seeded administrator access and secret keys depend on the runtime:

| Runtime | Access key | Secret key |
|---|---|---|
| Docker Compose | `GARRISON_DEFAULT_ACCESS_KEY` in `docker/.env` (generated by `update.sh`) | `GARRISON_DEFAULT_SECRET_KEY` in `docker/.env` |
| Source build in development mode | `access_garrison_default` | `secret_garrison_default_change_me` |
| Kubernetes (Kustomize or Helm) | random, key `default-access-key` in Secret `garrison-secrets` | random, key `default-secret-key` in Secret `garrison-secrets` |

On Kubernetes, read them with:

```bash
kubectl -n garrison get secret garrison-secrets -o jsonpath='{.data.default-access-key}' | base64 --decode; echo
kubectl -n garrison get secret garrison-secrets -o jsonpath='{.data.default-secret-key}' | base64 --decode; echo
kubectl -n garrison get secret garrison-secrets -o jsonpath='{.data.admin-password}' | base64 --decode; echo
```

You can also create a credential of your own in the dashboard (Access > Credentials); the secret key is shown once.

Responses are dictionaries with the server's camelCase field names, exactly as documented in `REST_API.md`.

## Authentication

| Method | Effect |
|---|---|
| `login(email, password, tenant_id=None)` | Issues a user token and switches to bearer authentication. |
| `login_with_keys(access_key, secret_key)` | Issues a credential token and switches to bearer authentication. |
| `use_token(token, tenant_id)` | Uses an existing token. |
| `use_access_key(access_key, secret_key, tenant_id)` | Sends the key pair on every request. |
| `use_signed_requests(access_key, secret_key, tenant_id)` | Signs every request with HMAC-SHA256. |
| `use_admin_api_key(api_key, tenant_id=None)` | Uses the platform admin API key. |

## Modules

`tenants`, `users`, `credentials`, `roles`, `permissions`, `role_permissions`, `user_role_assignments`, `credential_scope_assignments`, `agents`, `deployments`, `harness_profiles`, `prompt_templates`, `mcp_servers`, `secrets`, `workspace_templates`, `artifact_stores`, `manifests`, `runs`, `conversations`, `approvals`, `pipelines`, `pipeline_runs`, `pipeline_reviews`, `triggers`, `notification_endpoints`, `agent_assets`, `file_spaces`, `capabilities`, `fan_out_groups`, `analytics`, `nodes`, `control_nodes`, `node_pools`, `request_history`, `audit`, and `settings`. Collections offer `list`, `get`, `create`, `update`, and `delete` plus resource-specific calls.

Control-plane replicas are read-only: `client.control_nodes.list(max_results, skip, search)` returns a page with `respondingNodeId` (the replica that answered), and `client.control_nodes.get(node_id)` reads one replica. Each record carries `status` (`Starting`, `Ready`, `Draining`, `Offline`), `version`, `schemaVersion`, `backplane`, `startedUtc`, `lastHeartbeatUtc`, `activeRequests`, `openStreams`, `heldLongPolls`, `isLeader`, and `leaderEpoch` (leader only). The tenant overview also returns `controlNodesByStatus` and `leaderNodeId`.

## Permission approvals

When a deployment has `approvalsEnabled` set (Claude Code profiles, and Codex profiles with CodexAppServer delivery), the harness relays permission prompts to Garrison. The deployment's `approvalRules` (each with `action`, a `pattern` in Claude Code rule syntax such as `Bash(git status:*)` or `mcp__github__*`, an optional `inputPattern`, and a `description`) decide each request, and `approvalDefaultAction` (`Allow`, `Deny`, or `Ask`) covers requests no rule matches. `Ask` sends the request to a person, who has `approvalTimeoutSeconds` (10 to 3600, default 300) before `approvalTimeoutDecision` applies.

```python
pending = client.approvals.list(status="Pending")
decided = client.approvals.decide(pending["objects"][0]["id"], "Allow", reason="Looks safe", remember=True)
result = client.approvals.check(deployment_id, "Bash", {"command": "git status --short"})
print(result["action"], result["source"], result.get("rulePattern"))
```

`approvals.list` filters by `status`, `run_id`, `root_run_id`, `agent_id`, `deployment_id`, `decision_source`, `from_utc`, and `to_utc`; for a pending count, pass `status="Pending", max_results=1` and read `totalRecords`. `approvals.get` raises `GarrisonError` (404) for an approval outside the tenant. `approvals.decide` raises 409 (`ApprovalNotPending`) when the approval was already decided, and `remember=True` adds a rule to the deployment (`rule_pattern`, or the approval's `suggestedRule`) and needs Update on that deployment. `approvals.check` records nothing; the input uses Claude Code tool input names (`command`, `cwd`, `url`, `file_path`, `notebook_path`, `path`, `paths`, `pattern`, `query`). Runs carry `pendingApprovals`, `awaitingApproval` (the run stays `Running` while it waits), and `approvalWaitMs`. The module exports `APPROVAL_STATUSES`, `APPROVAL_DECISIONS`, `APPROVAL_SOURCES`, `APPROVAL_RULE_ACTIONS`, and `APPROVAL_KINDS`.

## Pipelines

A pipeline runs ordered agent stages, each in its own workspace, and hands each stage the earlier stages' results through a `PipelineStage` prompt template. A stage with `requiresReview` waits for a person before the next stage starts.

```python
pipeline = client.pipelines.create({"name": "draft-and-edit", "stages": [
    {"name": "write", "agentId": writer_id, "requiresReview": True, "maxRevisions": 2},
    {"name": "edit", "agentId": editor_id}]})
preview = client.pipelines.preview(pipeline["id"], "Announce the release", ["Sample draft"])
run = client.pipelines.start("draft-and-edit", "Announce the release", wait=True, wait_seconds=60,
                             idempotency_key="release-42")
review = client.pipeline_reviews.list(status="Pending", pipeline_run_id=run["id"])["objects"][0]
client.pipeline_reviews.decide(review["id"], "Approve", "Keep it short")
finished = client.pipeline_runs.wait_for_completion(run["id"])
```

`pipelines` offers `list`, `get`, `create`, `update`, and `delete` (identifier or name), plus `start` and `preview`. `start` needs Pipeline Execute and Agent Execute on every stage agent. With `wait=True` it returns when the pipeline run ends or waits for a review, or after `wait_seconds` (0 to 600). `idempotency_key` is sent as the `Idempotency-Key` header: a repeated start returns the same pipeline run, and the same key with a different pipeline or input raises 409 `IdempotencyKeyConflict`. `update` replaces the stages and advances `version`; started pipeline runs keep their snapshot. `delete` raises 409 `PipelineInUse` while pipeline runs are active.

`pipeline_runs.list` filters by `pipeline_id`, `status`, `caller_id`, `from_utc`, and `to_utc`. `get(id, wait_seconds=...)` waits until the pipeline run ends or waits for a review; the detail carries `stages`, `runs` (stage run summaries), and `reviews`. `cancel` also cancels the pending review and the current stage run (409 `PipelineRunFinished` once it ended). `retry` resumes a Failed, TimedOut, or Cancelled pipeline run at the stage where it stopped. `delete` removes a finished pipeline run and its reviews (409 `PipelineRunActive` otherwise). `wait_for_completion` polls until a terminal status and keeps waiting while a review is pending.

`pipeline_reviews.list` filters by `status`, `pipeline_run_id`, `pipeline_id`, `run_id`, `decision_source`, `from_utc`, and `to_utc`. `decide(id, decision, comment)` takes `Approve` (the comment reaches the next stage as review notes), `RequestChanges` (comment required; the stage runs again with it, up to the stage's `maxRevisions`, then 409 `RevisionLimitReached`), or `Reject` (the pipeline run fails with outcome `ReviewRejected`). A decided review raises 409 `ReviewNotPending`. Reviews are authorized as Approval Read and Update; run tokens cannot use pipelines or reviews.

The module exports `PIPELINE_RUN_STATUSES`, `PIPELINE_RUN_TERMINAL_STATUSES`, `PIPELINE_RUN_OUTCOMES`, `PIPELINE_STAGE_STATUSES`, `PIPELINE_REVIEW_STATUSES`, `PIPELINE_REVIEW_DECISIONS`, and `PIPELINE_REVIEW_SOURCES`.

## Triggers and notifications

A trigger starts an agent run or a pipeline run on a cron schedule or when a signed webhook arrives. It runs as the principal that last created or changed it, so creating one needs Execute on its agent (or on the pipeline and every stage agent). A webhook trigger's `signingSecret` is returned only by `create` and `rotate_secret`; store it then.

```python
from garrison_sdk import verify_webhook

hook = client.triggers.create({"name": "on-push", "type": "Webhook", "agentId": agent_id})
fire = client.triggers.deliver_webhook(hook["id"], hook["signingSecret"], '{"ref": "main"}', delivery_id="delivery-1")
nightly = client.triggers.create({"name": "nightly", "type": "Cron", "agentId": agent_id,
                                  "cronExpression": "0 2 * * *", "timeZone": "America/New_York"})
failed = client.triggers.list_fires(nightly["id"], outcome="Failed")
```

`client.triggers` adds `list(type=...)`, `rotate_secret`, `fire` (fires now; an optional `body` reaches the input template as `webhook.body`), `list_fires` (filter by `TRIGGER_FIRE_OUTCOMES`), and `deliver_webhook` (signs and posts a webhook as an external sender would). Runs a trigger started have `kind` `Trigger` and `triggerId`; `client.runs.list(trigger_id=...)` lists them, and pipeline runs carry `triggerId` too.

`client.notification_endpoints` manages URLs that receive signed JSON notifications for `NOTIFICATION_EVENTS` (`Test` is only sent by the test action). It adds `rotate_secret`, `test` (sends a `Test` notification and returns the delivery after its first attempt), `list_deliveries` (filter by `NOTIFICATION_DELIVERY_STATUSES`), and `get_delivery`. A loopback or private URL raises `GarrisonError` 400 with `error["fieldCodes"]["url"] == "DestinationBlocked"` unless the operator turned on `Notifications.AllowPrivateDestinations`; link-local addresses such as 169.254.169.254 are always refused.

`sign_webhook(secret, unix_seconds, body)` builds a signature and `verify_webhook(header, secret, body, tolerance_seconds=300)` checks one. The signature header is `X-Garrison-Signature: t=<unix seconds>,v1=<hex>`, where the hex value is the lowercase HMAC-SHA256, keyed with the UTF-8 bytes of the signing secret, of the timestamp, a period, and the raw body. A header may carry several `v1` values; any match is accepted. The server accepts a webhook only within `Triggers.WebhookToleranceSeconds` (default 300) of its clock, answers every failed check with the same 401 `InvalidSignature`, and returns the earlier fire (HTTP 200, `duplicate` true) for a repeated `X-Garrison-Delivery`. Notifications are signed the same way, so a receiver checks them with the same verify function and ignores a `X-Garrison-Delivery` it has seen before: delivery is at least once.

## Streaming run events

```python
run = client.runs.create("Hello", agent_name="my-agent")
for item in client.runs.stream(run["id"]):
    if "event" in item:
        print(item["event"]["eventType"], item["event"].get("text"))
    if "run" in item:
        print("finished:", item["run"]["status"])
```

The iterator ends after `run.completed`. `runs.events` polls, and `runs.wait_for_completion` waits for a terminal status.

## Conversations

A conversation is a multi-turn session with one agent. Each turn is a run, and every turn after the first resumes the harness session the earlier turns built, on the node that holds that session's directories. Pass `start_conversation=True` to `agents.invoke`, `runs.create`, or `deployments.test` to start one; the returned run's `conversationId` names it. Pass that ID as `conversation_id` to send the next turn.

```python
first = client.agents.invoke("my-agent", "Plan the migration", start_conversation=True)
conversation_id = first["conversationId"]

second = client.agents.invoke("my-agent", "Now write step 1", conversation_id=conversation_id)
print(second["conversationTurn"], second.get("resultText"))   # 2 ...

conversation = client.conversations.get(conversation_id)
turns = client.conversations.list_runs(conversation_id)["objects"]   # oldest first
client.conversations.delete(conversation_id)                         # the runs are kept
```

Turns of one conversation never overlap. A turn sent while the previous one is unfinished is refused, not queued, with 409 `ConversationBusy`; wait for the previous run (or cancel it) and send again:

```python
try:
    client.agents.invoke("my-agent", "Next", conversation_id=conversation_id)
except GarrisonError as e:
    if e.status_code != 409 or e.code != "ConversationBusy":
        raise
    active = client.conversations.get(conversation_id).get("activeRunId")
    if active:
        client.runs.wait_for_completion(active)
```

Other 409 codes are `ConversationAgentMismatch` (the conversation belongs to another agent), `ConversationDeploymentMismatch` (the request names a deployment other than the conversation's), and `ConversationDeploymentUnavailable` (the conversation's deployment was deleted). An unknown `conversation_id` returns 404. `conversations.delete` also returns 409 `ConversationBusy` while a turn is unfinished.

`conversations.list(agent_id, context_id, caller_id, search, max_results, skip, ordering)` filters conversations; `context_id` is the A2A context the conversation was created for. `runs.list(conversation_id=...)` lists a conversation's runs. A conversation carries `turnCount`, `sessionId`, `affinityNodeId` and `affinityNodeName`, `activeRunId`, `lastRunId`, `busy` (true while a turn is unfinished), `fallbackCount`, and `lastFallbackReason`.

Each turn's run has `conversationId`, `conversationTurn` (1 for the first turn, 0 outside a conversation), `resumeSessionId`, `affinityNodeId`, `affinityUntilUtc`, and `conversationFallbackReason`. A fallback happens when the turn cannot resume and starts a fresh session seeded with the transcript of the earlier turns instead; `CONVERSATION_FALLBACK_REASONS` lists the values (`AffinityNodeLost`, `AffinityWaitExpired`, `WorkspaceLost`, `SessionMissing`, `HarnessChanged`, `ResumeUnsupported`, `ExecutorWithoutState`). A turn that could not even fall back ends with outcome `ConversationStateLost`. Deleting a conversation writes a `ConversationDeleted` audit record. See "Conversations" in `REST_API.md`.

## Run metrics

Run dictionaries carry timing and usage fields alongside `inputTokens`, `outputTokens`, `cachedTokens`, and `costUsd`:

| Field | Type | Meaning |
|---|---|---|
| `firstTokenUtc`, `lastTokenUtc` | ISO 8601 UTC string or absent | First and last model output event. |
| `timeToFirstTokenMs`, `streamingMs`, `executionMs`, `queueMs`, `totalMs` | int or absent | Durations in milliseconds. |
| `delegationWaitMs` | int or absent | Time the run spent waiting on child runs it started (delegation), measured from server timestamps of the runs whose `parentRunId` is this run. |
| `timeToFirstTokenExcludingDelegationMs` | int or absent | `timeToFirstTokenMs` minus the delegation wait that happened before the first token; never negative. Use it to compare delegating agents with agents that answer directly. |
| `outputTokensPerSecond` | float or `None` | Output throughput. Always present; `None` when it cannot be measured (no streaming window, or one shorter than 100 ms). |
| `reasoningTokens` | int, default 0 | Reasoning tokens reported by the harness. |
| `toolCallCount` | int, default 0 | Tool calls made during the run. |

The server omits most fields it cannot measure, so read them with `run.get(...)`. A few keys are always present and are `None` when there is nothing to report: `outputTokensPerSecond`, `blockedReason`, `outputSchemaValid`, and `schemaValidationErrors`. `run.get(...)` handles both cases.

`run["blockedReason"]` is computed by the server when a run is read. It is `None` unless the run is `Queued` and no Ready worker can run it. Values: `NoReadyWorker` (no node is Ready), `NoCapableWorker` (no Ready node reports the run's harness), `NoMatchingPool` (capable nodes exist but none matches the deployment's node pool or node selector), `NoIsolatingWorker` (the run is `Untrusted` or its deployment has an egress allowlist, and no Ready node with its harness can isolate it or enforce the allowlist), `NoToolWorker` (the run's agent uses a harness built-in capability such as pandoc, and no Ready worker that can run it reports that tool). `RUN_BLOCKED_REASONS` lists them. The tenant overview counts these runs as `blockedRuns`. See "Blocked runs" in `REST_API.md`.

Runs stopped by a worker run guard end `Failed` with outcome `RepetitionDetected` (the assistant text degenerated into a short repeated unit or into text with no letters or digits), `OutputLimitExceeded` (more assistant text than the deployment's `maxAssistantChars`), or `NoProgress` (nothing happened for `noProgressSeconds`). The partial output is in `run["resultText"]`, and the run has one `Warning` event with code `RunGuardTriggered`. A waiting invoke cancels its run when the connection drops; pass `cancel_on_disconnect=False` to `agents.invoke` or `runs.create` to keep the run going. See "Run guards" and "Cancellation" in `REST_API.md`.

When the agent has an output schema, the server validates each run's final output against it. `run["outputSchemaValid"]` is `True` or `False` after validation and `None` when nothing was validated, `run["schemaValidationErrors"]` holds the first few errors of a failed validation, and `run["repairAttempts"]` (0 or 1) counts the structured output repair Garrison makes when the harness can resume its session. A run whose output still does not validate fails with outcome `SchemaValidationFailed`. See "Structured output validation" in `REST_API.md`.

## Executors and run pods

A deployment's `executor` is `"Process"` (a subprocess of the worker, the default) or `"KubernetesJob"` (a Kubernetes Job per run, in its own pod); `RUN_EXECUTORS` lists both. Leaving it out uses the node pool's `defaultExecutor`, then Process. `podResources` (`cpuRequest`, `cpuLimit`, `memoryRequest`, `memoryLimit`, `ephemeralStorageRequest`, `ephemeralStorageLimit`, as Kubernetes quantities) sets the run pod's requests and limits:

```python
client.deployments.create({"agentId": agent["id"], "name": "helper-pod", "harnessProfileId": profile_id,
                           "executor": "KubernetesJob", "podResources": {"memoryLimit": "2Gi", "cpuLimit": "1"}})
```

Runs carry `executor`, nodes list `executors`, and only nodes reporting a run's executor claim it. Workspace templates of kind `"PersistentVolume"` mount the claim named by `persistentVolumeClaim` (KubernetesJob runs only). Run pod failures outside the harness end with outcome `PodFailed`. Nodes also report `containerized` (bool, default `False`): whether the worker runs inside a container or pod, which makes the built-in Codex profiles default their sandbox to `danger-full-access`. See `docs/KUBERNETES.md`.

## Secret status

The control plane refreshes ChatGPT logins stored in `CodexAuthJson` secrets itself, shortly before the access token expires, and writes the rotated tokens back to the secret. When OpenAI rejects the stored refresh token for good (reused, expired, or revoked), the secret's status becomes `NeedsReauthentication`.

Each secret carries `status` (one of `garrison_sdk.SECRET_STATUSES`: `"Ok"` or `"NeedsReauthentication"`), `statusMessage` (the provider error, absent when `Ok`), `statusUtc` (when the status left `Ok`), `refreshedUtc` (when the control plane last refreshed the login itself), and `accessTokenExpiresUtc` (expiry of the stored access token; `CodexAuthJson` only). To find secrets that need attention, list them and check `secret["status"] == "NeedsReauthentication"`, then call `client.secrets.set_value(id, new_auth_json)`. A run whose deployment binds a secret in that state fails before it starts, with outcome `NotCredentialed` and an error message that starts with `SecretNeedsReauthentication:`. (`SecretRefreshFailed:` means the access token was expired and the refresh failed for a passing reason such as a network error; the secret stays `Ok` and a retry may work.) The fix is to replace the value: sign in again with `codex login` using a `CODEX_HOME` nothing else uses, then set the new `auth.json` as the secret's value. Setting a value returns the status to `Ok`. Do not keep using that login on another machine, because both copies share one refresh token; for shared deployments an `OpenAiApiKey` secret is simpler. See "Codex logins" in `docs/SECURITY.md`.

## Run analytics

```python
from datetime import datetime, timedelta, timezone

now = datetime.now(timezone.utc)
result = client.analytics.runs(from_=now - timedelta(days=1), to=now, interval="hour", group_by="agent")
print(result["totals"]["runs"], result["totals"]["costUsd"])
for series in result["series"]:
    for bucket in series["buckets"]:
        print(series["label"], bucket["startUtc"], bucket["runs"], bucket["timeToFirstTokenMsP95"])
```

`analytics.runs(from_=None, to=None, interval=None, agent_id=None, harness_type=None, deployment_id=None, group_by=None, model=None)` accepts `datetime` values or ISO 8601 UTC strings for `from_` and `to`. `interval` is `minute`, `hour`, `day`, `week`, or `auto`. `model` keeps only runs whose served model equals the value, and `"unknown"` matches runs without a recorded model. `group_by` is `none`, `agent`, `harness`, `model`, or `harnessModel`; with `harnessModel` each series key is `Harness|model` (for example `ClaudeCode|claude-sonnet-5-5`) and its label is `Harness / model`. The response carries `fromUtc`, `toUtc`, `interval`, `bucketSeconds` (authoritative bucket size), `truncated` (true when the 100,000 run cap was hit), `totals`, and `series` (each with `key`, `label`, and `buckets`). Totals and buckets share the same metrics: counts by outcome, token totals, `toolCalls`, `costUsd`, and latency averages and percentiles that are `None` when there are no samples. Besides `timeToFirstTokenMsAvg`, `timeToFirstTokenMsP50`, and `timeToFirstTokenMsP95`, the metrics include `timeToFirstTokenExcludingDelegationMsAvg`, `timeToFirstTokenExcludingDelegationMsP50`, `timeToFirstTokenExcludingDelegationMsP95`, and `delegationWaitMsAvg`, so agents that delegate can be compared with agents that answer directly. A range where `from_ >= to`, one that needs more than 400 buckets, or an invalid parameter raises `GarrisonError` with status 400.

To fill filter pickers, `analytics.dimensions(from_=None, to=None)` calls `GET /v1.0/api/tenants/{tenantId}/analytics/runs/dimensions` and returns the distinct values among runs in the range (default: the last 24 hours):

```python
dims = client.analytics.dimensions(from_=now - timedelta(days=7), to=now)
for model in dims["models"]:
    report = client.analytics.runs(from_=now - timedelta(days=7), to=now, model=model)
    print(model, report["totals"]["runs"])
```

The result is `{"agents": [{"id", "name"}], "harnesses": [str], "deployments": [{"id", "name", "agentId"}], "models": [str], "truncated": bool}`. Lists are sorted by name, and `"unknown"` in `models` stands for runs without a recorded model.

## Manifests

```python
result = client.manifests.apply(open("agents.yaml").read(), dry_run=True)
for item in result["items"]:
    print(item["kind"], item["name"], item["result"], item.get("message"))
    for change in item.get("changes", []):
        print("  ", change["field"], change.get("before"), "->", change.get("after"))
```

Each item reports what the apply did, or for a dry run what it would do. Items that are (or would be) `Updated` carry `changes`, a list of `{"field", "before", "after"}` with values as strings truncated to 200 characters. Every item also carries `warnings` (a list of `FieldWarning`, empty when there is nothing to report) for dry runs and applies alike; see "Clamped values".

`manifests.export` returns a multi-document YAML bundle that apply accepts unchanged (`GET .../manifests/export`). With no selectors it exports every tenant-owned resource. `kinds` names whole kinds, `resources` names single records as `Kind/name` (split on the first `/`), `follow_references` also exports what the selection depends on (an agent brings its deployments, the triggers and notification endpoints that target it, and agents it may delegate to; a deployment brings its agent, harness profile, prompt templates, workspace template, and MCP servers; a pipeline brings its stage agents, pinned deployments, handoff templates, and triggers), and `include_built_in` adds referenced built-in prompt templates and harness profiles. Secret values are never exported: the first document is a `kind: Bundle` document listing `requiredSecrets`, `requiredArtifactStores`, and `requiredBuiltIns`, and applying it to a tenant that lacks one fails with `errorCode` `MissingSecret`, `MissingArtifactStore`, or `MissingBuiltIn`. A reference that cannot be resolved fails with `MissingSecret` or `ReferenceNotFound` and an `errorField` naming it. Re-applying an applied bundle reports every document `Unchanged`. An unknown kind is a 400 with field code `UnknownKind`, a malformed resource selector is a 400 with `InvalidSelector`, and a selected resource that does not exist is a 404.

```python
bundle = client.manifests.export(resources=["Agent/triage"], follow_references=True)
check = client.manifests.apply(bundle, dry_run=True)
```

## Transcripts

```python
markdown = client.runs.transcript_markdown(run_id)
transcript = client.runs.transcript(run_id, include_thinking=True)
conversation = client.conversations.transcript(conversation_id)
```

A transcript covers one run, or every turn of a conversation oldest first (`GET .../runs/{id}/transcript` and `GET .../conversations/{id}/transcript`). The Markdown form is for reading and sharing; the JSON form is the typed `Transcript` document (schema `garrison.transcript/v1`): `kind` (`Run` or `Conversation`), `turnCount`, total `usage`, and `turns`, each with the redacted `input`, `entries` (assistant text, tool calls and results, warnings, errors, lifecycle notes; thinking only when requested), `approvals`, `result`, `errorMessage`, `usage` (tokens, tool calls, cost, duration), and timestamps. Secrets read `[REDACTED]`, tool text is cut to the server's `Transcripts.ToolTextMaxChars` (`textTruncated`), and a transcript over `Transcripts.MaxBytes` is cut with `truncated` and a `truncationNote`. Unknown or other-tenant identifiers are a 404.

## Structured input

An agent with `inputSchemaJson` (JSON Schema text) only accepts input that is a JSON document matching it, on every surface. Saving a schema that is not valid JSON Schema fails with field code `InvalidJsonSchema`. An invocation whose input is not JSON is a 400 with field code `InputNotJson` on `input`; one that breaks the schema is a 400 with `InputSchemaViolation` on `input` or `input.<path>` (for example `input.topic` or `input.tags[1]`; a missing required property is reported on its own key).

```python
try:
    client.agents.invoke("triage", json.dumps({"count": 2}), input_content_type="application/json")
except GarrisonError as e:
    print(e.status_code, e.field_codes, e.fields)
```

`GarrisonError.fields` and `GarrisonError.field_codes` are dictionaries (empty when the server sent none). The module exports `INPUT_SCHEMA_FIELD_CODES`, `TRANSCRIPT_FORMATS`, and the `Transcript`, `TranscriptTurn`, `TranscriptEntry`, `TranscriptApproval`, and `TranscriptUsage` typed dictionaries.

## Clamped values

Numbers outside their documented range are not rejected: the server stores the nearest allowed value (deployment `maxAttempts` 99 is stored as 10). Create and update responses for agents, deployments, harness profiles, MCP servers, and workspace templates then carry `warnings`, a list of `FieldWarning` dictionaries (`field`, `code`, `given`, `stored`, `message`). The key is absent when every value was stored as given, and reads never carry it. `FIELD_WARNING_CODES` lists the codes; today the only one is `"ValueClamped"`.

```python
deployment = client.deployments.create({"agentId": agent["id"], "name": "helper", "harnessProfileId": profile_id,
                                        "maxAttempts": 99})
for warning in deployment.get("warnings", []):
    print(warning["field"], warning["code"], warning["given"], "->", warning["stored"], warning["message"])
```

Drop `warnings` before sending a dictionary you read back as an update body; the server ignores it, but it is response-only. See "Warnings" in `REST_API.md`.

## Agent revisions and promotion

An agent's content can be saved as revisions. Each agent has at most one open draft; publishing it makes it immutable. Deployments carry an `environment` (default `dev`) and an optional `agentRevisionId` pin; an unpinned deployment runs the agent's live content. Runs record the `agentRevisionId` they used, and agents report `latestPublishedRevisionId` and `draftRevisionId` (both read only).

```python
draft = client.agents.save_draft("my-agent", {"description": "Tighter summary rules."})
published = client.agents.publish_revision("my-agent", draft["id"], change_note="Tighten summaries")
revisions = client.agents.revisions("my-agent")["objects"]          # newest first
diff = client.agents.diff_revisions("my-agent", 1, published["number"])
for change in diff["changes"]:
    print(change["field"], change["changeType"], change["from"], "->", change["to"])

promotion = client.promotions.promote(published["agentId"], "dev")  # target defaults to the next environment
for item in promotion["items"]:
    print(item["deploymentName"], item["previousRevisionId"], "->", item["newRevisionId"])
client.promotions.rollback(promotion["id"], note="Revert")          # restores the previous pins
client.promotions.list(agent_id=published["agentId"])

envs = client.environments.get()   # {"environments": [{"name", "description", "position"}], "isDefault": True}
client.environments.update({"environments": [{"name": "dev", "position": 0}, {"name": "prod", "position": 1}]})
```

Revisions accept an `arv_` ID or a revision number. `promote` takes `target_environment`, `agent_revision_id`, `allow_skip` (to jump over intermediate environments), and `note`. Typed dictionaries `AgentRevision`, `AgentRevisionDiff`, `TenantEnvironmentList`, and `PromotionRecord` describe the responses; `AGENT_REVISION_STATES`, `REVISION_CHANGE_TYPES`, `PROMOTION_KINDS`, `PROMOTION_OUTCOMES`, and `DEFAULT_ENVIRONMENTS` list the enum values.

## Agent assets

An agent asset is a versioned system prompt, skill, reference file, or document template (kind `SystemPrompt`, `Skill`, `ReferenceFile`, or `DocumentTemplate`; a `SystemPrompt` asset requires a prompt template ID). Assets are addressed by ID or name and their versions by number. Uploading a version sends every file base64-encoded; uploading files identical to the current version returns that version instead of creating a new one. Each returned file carries its lowercase hex `sha256`. A revision pins assets through `assetPins` (`assetId` plus an optional `version`; no version follows the current one), and deleting an asset a revision pins fails with HTTP 409 and code `AssetInUse`. Upload limits answer 413 (`AssetFileTooLarge`, `AssetVersionTooLarge`, `AssetTooManyFiles`). A run whose pinned file fails its SHA-256 check on the worker ends with outcome `AssetIntegrityFailed`.

```python
asset = client.agent_assets.create({"name": "release-notes-skill", "kind": "Skill"})
version = client.agent_assets.upload(asset["id"], [{"path": "SKILL.md", "content": "# Release notes\n", "mediaType": "text/markdown"}],
                                     change_note="first cut")      # content may be bytes or str (UTF-8)
client.agent_assets.upload_raw(asset["id"], "SKILL.md", b"# Release notes v2\n")   # one file as raw bytes
client.agent_assets.versions(asset["id"])                          # plain list, newest first
data = client.agent_assets.download_file(asset["id"], version["number"], "SKILL.md")
client.agents.save_draft("my-agent", {"assetPins": [{"assetId": asset["id"]}]})
client.agent_assets.list(kind="Skill", search="release")
```

`AgentAsset`, `AgentAssetVersion`, `AgentAssetFile`, and `AssetPin` type the responses; `AGENT_ASSET_KINDS` lists the kinds and `RUN_OUTCOME_ASSET_INTEGRITY_FAILED` names the run outcome.

## Conversation file spaces

Every conversation has a file space: versioned files that all of its turns share. The worker mounts the space into each run's workspace under the deployment's `fileSpaceMountPath` (default `files`), and a run reports the space it used as `fileSpaceId`. `client.file_spaces` reads and writes the space from outside. Each method takes the owner (`"conversations"` or `"runs"`, listed in `FILE_SPACE_OWNERS`) and the conversation or run ID, so you can reach a space from any of its turns.

Writes accept an optional `base_version`. Pass the version you last read (0 for a file that should not exist yet). If someone wrote in between, the server keeps both copies: your content lands under a conflict name, and the result has `conflict` set to True and `path` set to that name. Leave `base_version` out to overwrite unconditionally.

```python
cid = run["conversationId"]
result = client.file_spaces.write("conversations", cid, "notes/a.md", "# Notes\n", base_version=0, media_type="text/markdown")
client.file_spaces.write_raw("conversations", cid, "data/raw.bin", b"\x00\x01")    # raw octet-stream body
listing = client.file_spaces.list("conversations", cid, include_deleted=False)    # fileSpaceId, fileCount, totalBytes, files
client.file_spaces.versions("conversations", cid, "notes/a.md")                   # newest first
data = client.file_spaces.read("conversations", cid, "notes/a.md", version=1)      # bytes; read_text decodes UTF-8
link = client.file_spaces.download_url("runs", run["id"], "notes/a.md")           # {"url", "expiresUtc"}; no credentials needed
client.file_spaces.delete("conversations", cid, "notes/a.md")
```

Errors: 400 `InvalidFilePath`, 404 for an unknown conversation, run, or file, and 413 `FileTooLarge`, `FileSpaceFull`, or `TooManyFiles`. `ConversationFile`, `ConversationFileVersion`, `FileSpaceListing`, `FileSpaceUploadResult`, and `FileDownloadUrl` type the responses.

## Capability catalog

The capability catalog describes agents, MCP server tools, and harness built-ins the same way, so an orchestrator can choose between them. A `CapabilityDescriptor` has `id` (`cap_...`), `name`, `kind` (`CAPABILITY_KINDS`: `Agent`, `McpTool`, `HarnessBuiltIn`), `origin` (`CAPABILITY_ORIGINS`: `Derived` or `Manual`), `sourceKey`, the source fields (`sourceAgentId`, `sourceRevisionId`, `sourceMcpServerId`, `sourceToolName`, `sourceHarnessProfileId`, `sourceHarnessType`), `summary`, `inputSchemaJson`, `outputSchemaJson`, `tags`, `requirements` (node labels a run needs, as `{"key", "value"}`), `hints`, `refreshWarning`, `lastRefreshedUtc`, `createdUtc`, and `lastUpdateUtc`. `tenantId` is `None` for descriptors every tenant shares (harness built-ins of built-in profiles).

Derived descriptors follow their source: an agent gets one from its latest published revision, an MCP server one per listed tool, and a harness profile one per entry in its `toolProbes`. You cannot change or delete them (409 `CapabilityDerived`). Manual descriptors are yours to create, replace, and delete. Their names are unique per tenant (409 `NameConflict`), and schemas must be JSON Schema (400 with code `InvalidJsonSchema`). `hints` (`CapabilityHints`) has `status` (`CAPABILITY_HINT_STATUSES`: `Unknown` until enough runs finish, then `Known`), `sampleSize`, `medianDurationMs`, `p90DurationMs`, `meanCostUsd`, `windowDays`, and `computedUtc`; the values are `None` while the status is `Unknown`.

```python
agents = client.capabilities.list(kind="Agent")["objects"]
billing = client.capabilities.list(tag="billing", search="invoice")["objects"]
created = client.capabilities.create({"name": "lookup-invoice", "kind": "McpTool", "summary": "Find an invoice by number.",
                                      "inputSchemaJson": '{"type":"object","properties":{"number":{"type":"string"}}}',
                                      "tags": ["billing"]})
same = client.capabilities.get("lookup-invoice")                  # ID or name
client.capabilities.update(created["id"], {**created, "summary": "Find an invoice by its number."})
result = client.capabilities.refresh()                             # or refresh(mcp_server_id=...)
client.capabilities.delete(created["id"])
```

`refresh` returns a `CapabilityRefreshResult`: `agents`, `harnessBuiltIns`, and `hints` counts, plus `mcpServers`, one entry per MCP server with `mcpServerId`, `mcpServerName`, `tools`, `removed`, `warned`, and `error` (set when the listing failed). Harness profiles accept `toolProbes`, a list of `HarnessToolProbe` dictionaries: `name` (lowercase letters, digits, dots, and hyphens), `executable` (a bare file name on the worker's PATH), `arguments` (at most one of `HARNESS_TOOL_PROBE_ARGUMENTS`, default `["--version"]`), and `description`. Workers that find the tool report the node label `garrison.io/tool-{name}=true`.

## Fan-out groups

A run fans work out to several agents at once by calling the `garrison_fan_out` MCP tool, then collects the results with `garrison_gather`. The SDK cannot start a group; `client.fan_out_groups` reads and cancels them. A `FanOutGroup` has `fanOutGroupId` (`fog_...`), `parentRunId`, `status` (`FAN_OUT_GROUP_STATUSES`: `Running`, `Joined`, `TimedOut`, `BudgetExceeded`, `Cancelled`; every status but `Running` is final), `statusReason`, `joinPolicy` (`FAN_OUT_JOIN_POLICIES`: `All`, `Any`, `Quorum`), `quorum`, the counts `total`, `finished`, and `succeeded`, the label lists `pending` and `failed`, `members`, the totals `costUsd` and `tokens`, the budget `maxCostUsd` and `maxTokens` (absent when unset), `deadlineUtc`, `createdUtc`, and `completedUtc`. `summary`, `continuationMarker`, and `continuationInstruction` are what a harness sees through `garrison_gather` and are normally absent here.

Each `FanOutMember` has `label`, `agent`, `runId` (the child run), `status` (a run status), `outcome` (absent until it finishes), `resultText` with `resultTruncated`, `structuredOutputJson`, `errorMessage`, `filesWritten` (paths in the shared file space), `costUsd`, and `tokens`. A child run's `fanOutGroupId` names its group.

```python
groups = client.fan_out_groups.list_by_run(run_id)                # oldest first; 404 when the run does not exist
group = client.fan_out_groups.get(groups[0]["fanOutGroupId"])
for member in group["members"]:
    print(member["label"], member["status"], member["runId"])
cancelled = client.fan_out_groups.cancel(group["fanOutGroupId"])  # cancels members still running
```

A group that does not exist, or belongs to another tenant, raises `GarrisonError` with status 404.

## Errors

Non-success responses raise `GarrisonError` with `status_code`, `code`, `body`, and the parsed `error` payload. Validation failures carry field details in `error["fields"]`. The settings routes return 400 with `error["errors"]`, an object keyed by setting path (for example `Audit.RetentionDays`) whose values say what is wrong; nothing is saved when any value is rejected.

## Model prices

`client.model_prices` provides tenant-scoped list, get, create, update, and delete operations for `/model-prices`. Prices start empty and are operator-configured USD rates per million tokens, keyed by exact served model and harness. Optional cache/reasoning rates fall back to input/output rates; explicit zero is free. Configure token inclusion flags for the harness accounting convention (Claude Code cache reads are separate). Harness-reported cost, including zero, takes precedence; estimates set `costEstimated`. Saved run costs survive later price edits or deletion. See [REST API](../../REST_API.md#model-prices).

## Usage quotas

The usage-quota module provides CRUD operations and `client.usage_quotas.usage(id)` for current daily UTC meters. Scope an entry to Tenant, Agent, or Deployment; null limits are unlimited and zero disallows usage. Limits cover admissions, completed tokens/cost, and active concurrency. Unknown cost keeps admission open and sets `costAccountingComplete=false`. Refusals carry `QuotaExceeded` and name the limit. Only administrators have built-in write grants. See [REST API](../../REST_API.md#usage-quotas) for accounting boundaries and supported CLI budget enforcement.

Usage quotas default to monitoring only. Explicitly set `enforcementEnabled` to `true` (Go: `EnforcementEnabled`, C#: `EnforcementEnabled`) on an active quota to enforce limits. Disabled enforcement does not reject runs or lower harness budgets.

## Executor capabilities

Deployments accept `requiredCapabilities`: `isolation` (`Process`, `Container`, `SandboxedRuntime`), `egressControl`, `filesystemSnapshot`, `sessionContinuation`, `crossNodeRestore`, and optional required `coldStartClass` (`Immediate`, `Cold`, `Warm`). Defaults add no requirement beyond Process. Runs retain an admission-time copy. Workers expose `executorCapabilities`; legacy executor names promise no advanced capabilities. Set `executor: "KubernetesJob"` with Container requirements. Unsupported requirements remain queued with `NoCapableWorker`.

Kubernetes workers can report `warmStart: true` alongside `coldStartClass: "Cold"`; this satisfies either Cold or Warm requirements. Warm support requires enabled warming and Kubernetes RBAC. Explicit Warm requirements reject PersistentVolume workspaces and custom pod resources.

## Trust level

Deployments accept `trustLevel`: `"Trusted"` (the default) or `"Untrusted"` (`TRUST_LEVELS`). Untrusted runs need at least Container isolation on top of `requiredCapabilities`: an unset `executor` resolves to `KubernetesJob`, `"executor": "Process"` is rejected with field code `UntrustedNeedsIsolation`, and a run no Ready worker can isolate stays `Queued` with `blockedReason` `NoIsolatingWorker`. Runs report the admitted `trustLevel`. A tenant with `requireUntrustedDeployments` (set through `client.tenants.update`) rejects Trusted deployments with field code `TenantRequiresUntrusted`. See "Deployment trust level" in `REST_API.md`.

## Egress allowlist

Deployments accept `egressRules`, a list of `{"cidr": "203.0.113.0/24", "port": 443, "protocol": "TCP"}` dictionaries: `cidr` is required, `port` is 1 to 65535 or `None` for every port, and `protocol` is `"TCP"` (the default) or `"UDP"` (`EGRESS_PROTOCOLS`). An empty list (the default) keeps the cluster's default run egress. With rules, a run pod may reach only DNS, the Garrison server MCP port, and the listed rules; host names are not accepted, so resolve them to CIDR blocks first. Validation errors are 400 field codes: `TooManyEgressRules` (more than 64 rules), `InvalidCidr` (not a CIDR network address, for example a host name or `203.0.113.7/24` with host bits set), `PortOutOfRange`, `InvalidProtocol`, `EgressRulesNeedKubernetesJob` (`executor` `Process` with rules), and `EgressRulesNeedColdStart` (`coldStartClass` `Warm` with rules). With rules, every run needs egress control and at least Container isolation: an unset executor resolves to `KubernetesJob`, and a run no Ready worker can enforce the allowlist for stays `Queued` with blocked reason `NoIsolatingWorker`; it is never run unenforced. See "Egress allowlists" in `docs/SECURITY.md`.

## Effect policy

Deployments accept `effectPolicy` (`EFFECT_POLICIES`): `"AtMostOnce"` (the default for new deployments) ends a run that was already `Running` when its worker was lost `Failed` with outcome `NodeLost`, `"AtLeastOnce"` requeues it while `maxAttempts` allows, and `"Journaled"` behaves as `"AtMostOnce"` until the effect journal exists. A run that was still `Leased` never started, so it is requeued under every policy. Runs report the `effectPolicy` they were admitted under; changing the deployment later does not change how that run is handled. Deployment responses also carry the deprecated `retryOnNodeLoss`, `True` only for `AtLeastOnce`. It is still accepted on input (`True` is `AtLeastOnce`, `False` is `AtMostOnce`), and a body whose `retryOnNodeLoss` disagrees with its `effectPolicy` is rejected with a 400 field error on `effectPolicy` (code `EffectPolicyConflict`). When you change `effectPolicy` on a deployment dictionary you read back, drop `retryOnNodeLoss` from it first. See "Effect policy" in `REST_API.md`.

### Management MCP clients

The same agent/deployment/manifest validation, default bindings, versioning, and audit behavior now serve REST and management MCP. Use normal developer/user credentials for MCP configuration tools; hosted run tokens cannot change configuration. Existing SDK REST methods are unchanged. See [management MCP tools](../../docs/MANAGEMENT_MCP.md) for the MCP contract and replacement semantics.


Effect safety and continuation: run operations expose gateway intent metadata (no raw arguments or secrets). `Suspended` is an active status, so completion waits keep polling until a terminal status. Suspension and resume occur automatically for deployments with `suspensionEnabled` and compatible pinned harness `sessionFormat`; there are no manual suspend/resume endpoints. A raw CLI attempt lost after resuming fails closed if its new epoch lacks a safe checkpoint.

Remote agents use kind `Remote`, protocol `A2A` or `Mcp`, a full `remoteEndpointUrl`, and optionally `remoteCredentialSecretId` and `registrationTtlSeconds`; `mcpToolName` selects the remote MCP tool. Executors include `RemoteA2A` and `RemoteMcp`. See [remote agents](../../docs/REMOTE_AGENTS.md) and [tenant scheduling](../../docs/TENANT_SCHEDULING.md). Queue saturation returns HTTP 429 with code `QueueFull`, rather than creating a failed run.

System administrators can change tenant `schedulingWeight` (1 to 1000, default 1), use server settings for credential/run-token expiry policies and queue bounds, and run the master-key rotation method. Rotation uses keys already configured on the server and returns counts only; clients never supply key material to the endpoint. Keep old keys until a pass reports zero conflicts and failures.

LeaseBroker secret metadata uses `kind: "LeaseBroker"`, `brokerResource`, and optional `brokerAudience`; it rejects a static `value`. Issuance/revocation endpoints and provider authorization are operator-only settings. See the [provider contract](../../docs/CREDENTIAL_BROKER.md) for TTL, tombstone, and tenant authorization requirements.

`client.runs.placement(run_id)` returns read-only placement diagnostics. `client.runs.database_usage(run_id)` returns exact SQL attempts inside completed instrumented lifecycle scopes. Placement eligibility is advisory and reserves no capacity. External invocation wait is best effort: when the server wait budget is full, it returns the accepted run for polling. Resident synchronous delegation instead fails with `DelegationCapacityExhausted` before child creation when no wait slot is available. Poll an accepted run's ID instead of submitting another invocation.
