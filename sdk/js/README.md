# @garrison/sdk (JavaScript and TypeScript)

Client for the Garrison REST API, written in TypeScript and published as ESM and CommonJS with type declarations. It uses `fetch` and Web Crypto, so it runs on Node 18+ and in modern browsers.

## Install

The package is not published to npm yet, so `npm install @garrison/sdk` fails. Build it from your checkout of the repository and install it by path:

```bash
cd /path/to/Garrison/sdk/js && npm install && npm run build
cd /path/to/your-project && npm install /path/to/Garrison/sdk/js
```

Run `npm run build` again in `sdk/js` after pulling SDK changes; `npm install` by path links the folder, so your project picks up the new `dist`.

## Quick start

```ts
import { GarrisonClient } from "@garrison/sdk";

const client = new GarrisonClient("http://127.0.0.1:8700");
await client.login("admin@garrison", "password");   // the same email and password you use in the dashboard

const run = await client.agents.invoke("my-agent", "Summarize the release notes", { wait: true, waitSeconds: 120 });
console.log(run.status, run.resultText);
```

CommonJS works too: `const { GarrisonClient } = require("@garrison/sdk");`.

To sign in with an access key pair instead, call `client.loginWithKeys(accessKey, secretKey)`. See "Where the credentials come from" below.

## Where the credentials come from

Email and password sign-in works the same on every runtime: tenant `default`, user `admin@garrison`, and the administrator password. There is no default: on Docker Compose it is `GARRISON_ADMIN_PASSWORD` in `docker/.env`, which `update.sh` generates when it is missing. On Kubernetes it is whatever `GARRISON_ADMIN_PASSWORD` held when `k8s/scripts/generate-secrets.sh` ran, or the random one it printed, stored in Secret `garrison-secrets`. A source build in development mode (`GARRISON_ALLOW_INSECURE_DEFAULTS=true`) uses `password`.

The seeded administrator access and secret keys depend on the runtime:

| Runtime | Access key | Secret key |
|---|---|---|
| Docker Compose | `GARRISON_DEFAULT_ACCESS_KEY` in `docker/.env` (generated by `update.sh`) | `GARRISON_DEFAULT_SECRET_KEY` in `docker/.env` |
| Source build in development mode | `access_garrison_default` | `secret_garrison_default_change_me` |
| Kubernetes (Kustomize or Helm) | random, key `default-access-key` in Secret `garrison-secrets` | random, key `default-secret-key` in Secret `garrison-secrets` |

On Kubernetes, read them with:

```bash
kubectl -n garrison get secret garrison-secrets -o jsonpath='{.data.default-access-key}' | base64 --decode; echo
kubectl -n garrison get secret garrison-secrets -o jsonpath='{.data.default-secret-key}' | base64 --decode; echo
kubectl -n garrison get secret garrison-secrets -o jsonpath='{.data.admin-password}' | base64 --decode; echo
```

You can also create a credential of your own in the dashboard (Access > Credentials); the secret key is shown once.

Responses are dictionaries with the server's camelCase field names, exactly as documented in `REST_API.md`.

## Authentication

| Method | Effect |
|---|---|
| `login(email, password, tenantId?)` | Issues a user token and switches to bearer authentication. |
| `loginWithKeys(accessKey, secretKey)` | Issues a credential token and switches to bearer authentication. |
| `useToken(token, tenantId)` | Uses an existing token. |
| `useAccessKey(accessKey, secretKey, tenantId)` | Sends the key pair on every request. |
| `useSignedRequests(accessKey, secretKey, tenantId)` | Signs every request with HMAC-SHA256. Do not use secret keys in browser code you do not control. |
| `useAdminApiKey(apiKey, tenantId?)` | Uses the platform admin API key. |

## Modules

`tenants`, `users`, `credentials`, `roles`, `permissions`, `rolePermissions`, `userRoleAssignments`, `credentialScopeAssignments`, `agents`, `deployments`, `environments`, `promotions`, `harnessProfiles`, `promptTemplates`, `mcpServers`, `secrets`, `workspaceTemplates`, `artifactStores`, `manifests`, `runs`, `conversations`, `approvals`, `pipelines`, `pipelineRuns`, `pipelineReviews`, `triggers`, `notificationEndpoints`, `analytics`, `nodes`, `controlNodes`, `nodePools`, `requestHistory`, `audit`, and `settings`. Collections offer `list`, `get`, `create`, `update`, and `delete` plus resource-specific calls. Common objects (`Agent`, `Deployment`, `HarnessProfile`, `McpServer`, `WorkspaceTemplate`, `WorkerNode`, `FieldWarning`, `Run`, `RunEvent`, `Conversation`, `Pipeline`, `PipelineRun`, `PipelineReview`, `EnumerationResult<T>`) are typed; other fields pass through untouched.

Control-plane replicas are read-only: `client.controlNodes.list(query)` returns a `ControlNodeListResponse` (a page of `ControlNode` plus `respondingNodeId`, the replica that answered) and `client.controlNodes.get(nodeId)` reads one replica. `ControlNode` is typed: `status` (`ControlNodeStatus`: `Starting`, `Ready`, `Draining`, `Offline`), `version`, `schemaVersion`, `backplane`, `startedUtc`, `lastHeartbeatUtc`, `activeRequests`, `openStreams`, `heldLongPolls`, `isLeader`, and `leaderEpoch` (leader only). The tenant overview also returns `controlNodesByStatus` and `leaderNodeId`.

## Permission approvals

When a deployment has `approvalsEnabled` set (Claude Code profiles, and Codex profiles with CodexAppServer delivery), the harness relays permission prompts to Garrison. The deployment's `approvalRules` (`DeploymentApprovalRule`: `action`, a `pattern` in Claude Code rule syntax such as `Bash(git status:*)` or `mcp__github__*`, optional `inputPattern`, and `description`) decide each request, and `approvalDefaultAction` (`ApprovalRuleAction`: `Allow`, `Deny`, `Ask`) covers requests no rule matches. `Ask` sends the request to a person, who has `approvalTimeoutSeconds` (10 to 3600, default 300) before `approvalTimeoutDecision` applies.

```ts
const pending = await client.approvals.list({ status: "Pending" });
const decided = await client.approvals.decide(pending.objects[0].id, { decision: "Allow", reason: "Looks safe", remember: true });
const result = await client.approvals.check(deploymentId, { toolName: "Bash", input: { command: "git status --short" } });
```

`approvals.list` takes an `ApprovalFilter` (`status`, `runId`, `rootRunId`, `agentId`, `deploymentId`, `decisionSource`, `fromUtc`, `toUtc`); for a pending count, pass `{ status: "Pending", maxResults: 1 }` and read `totalRecords`. `approvals.get` rejects with `GarrisonError` (404) for an approval outside the tenant. `approvals.decide` rejects with 409 (`ApprovalNotPending`) when the approval was already decided, and `remember` needs Update on the approval's deployment. `approvals.check` records nothing and resolves to an `ApprovalCheckResponse` (`action`, `source`, `ruleId`, `rulePattern`, `suggestedRule`, `approvalsEnabled`); its input uses Claude Code tool input names (`file_path`, `notebook_path`). `Approval` is typed, and `Run` has `pendingApprovals`, `awaitingApproval` (the run stays `Running` while it waits), and `approvalWaitMs`.

## Pipelines

A pipeline runs agents as ordered stages. Each stage receives the caller's input plus the earlier stages' results (text, structured output, and artifact references), rendered by a `PipelineStage` prompt template, and a stage with `requiresReview` waits for a person before the pipeline continues.

```ts
const pipeline = await client.pipelines.create({
  name: "draft-and-edit",
  stages: [
    { name: "write", agentId: writerId, requiresReview: true, maxRevisions: 2 },
    { name: "edit", agentId: editorId },
  ],
});
const preview = await client.pipelines.preview(pipeline.id, { input: "Sample request", sampleOutputs: ["Sample draft"] });
const run = await client.pipelines.start(pipeline.name, { input: "Draft the release note", wait: true, waitSeconds: 60 }, { idempotencyKey: "release-note-42" });
const [review] = (await client.pipelineReviews.list({ status: "Pending", pipelineRunId: run.id })).objects;
await client.pipelineReviews.decide(review.id, { decision: "Approve", comment: "Mention the upgrade steps." });
const finished = await client.pipelineRuns.get(run.id, 60);
```

- `pipelines` accepts an identifier or a name for `get`, `update`, `delete`, `start`, and `preview`. `update` replaces the stages and advances `version`; started pipeline runs keep their snapshot. `delete` rejects with 409 (`PipelineInUse`) while a pipeline run is active.
- `pipelines.start` sends `idempotencyKey` as the `Idempotency-Key` header: the same key and input return the same pipeline run, and a different input rejects with 409 (`IdempotencyKeyConflict`). With `wait`, it returns when the pipeline run ends or waits for a review, or after `waitSeconds` (default 60, at most 600). It needs Pipeline Execute plus Agent Execute on every stage agent.
- `pipelineRuns.list` takes a `PipelineRunFilter` (`pipelineId`, `status`, `callerId`, `fromUtc`, `toUtc`). `get(id, waitSeconds)` returns the detail (`stages`, `runs`, `reviews`); `waitFor(id, timeoutMs, untilReview)` polls. `cancel` rejects with 409 (`PipelineRunFinished`) once the pipeline run ended, `retry` resumes a Failed, TimedOut, or Cancelled pipeline run at its stopped stage (409 `PipelineRunNotRetryable` otherwise), and `delete` removes a finished pipeline run (409 `PipelineRunActive` while active).
- `pipelineReviews` are authorized as Approval Read and Update. `decide` takes `Approve` (the optional comment reaches the next stage), `RequestChanges` (comment required, 400 without one; the stage runs again with the feedback, 409 `RevisionLimitReached` past `maxRevisions`), or `Reject` (the pipeline run fails). A second decision rejects with 409 (`ReviewNotPending`).
- Enums are string unions: `PipelineRunStatus`, `PipelineRunOutcome`, `PipelineStageStatus`, `PipelineReviewStatus`, `PipelineReviewDecision`, and `PipelineReviewSource`. Run tokens cannot use the pipeline APIs.

## Triggers and notifications

A trigger starts an agent run or a pipeline run on a cron schedule or when a signed webhook arrives. It runs as the principal that last created or changed it, so creating one needs Execute on its agent (or on the pipeline and every stage agent). A webhook trigger's `signingSecret` is returned only by `create` and `rotateSecret`; store it then.

```ts
import { verifyWebhook } from "@garrison/sdk";

const hook = await client.triggers.create({ name: "on-push", type: "Webhook", agentId });
const fire = await client.triggers.deliverWebhook(hook.id!, hook.signingSecret!, '{"ref":"main"}', { deliveryId: "delivery-1" });
const nightly = await client.triggers.create({ name: "nightly", type: "Cron", agentId, cronExpression: "0 2 * * *", timeZone: "America/New_York" });
const failed = await client.triggers.listFires(nightly.id!, { outcome: "Failed" });
```

`client.triggers` adds `list({ type })`, `rotateSecret`, `fire` (fires now; an optional `body` reaches the input template as `webhook.body`), `listFires` (filter by outcome), and `deliverWebhook` (signs and posts a webhook as an external sender would). Runs a trigger started have `kind` `Trigger` and `triggerId`; `client.runs.list({ triggerId })` lists them, and pipeline runs carry `triggerId` too.

`client.notificationEndpoints` manages URLs that receive signed JSON notifications for `NOTIFICATION_EVENTS` (`Test` is only sent by the test action). It adds `rotateSecret`, `test` (sends a `Test` notification and resolves with the delivery after its first attempt), `listDeliveries` (filter by status), and `getDelivery`. A loopback or private URL rejects with `GarrisonError` 400 and `fieldCodes.url === "DestinationBlocked"` unless the operator turned on `Notifications.AllowPrivateDestinations`; link-local addresses such as 169.254.169.254 are always refused.

`signWebhook(secret, unixSeconds, body)` builds a signature and `verifyWebhook(header, secret, body, toleranceSeconds = 300)` checks one; both are async because they use Web Crypto. The signature header is `X-Garrison-Signature: t=<unix seconds>,v1=<hex>`, where the hex value is the lowercase HMAC-SHA256, keyed with the UTF-8 bytes of the signing secret, of the timestamp, a period, and the raw body. A header may carry several `v1` values; any match is accepted. The server accepts a webhook only within `Triggers.WebhookToleranceSeconds` (default 300) of its clock, answers every failed check with the same 401 `InvalidSignature`, and returns the earlier fire (HTTP 200, `duplicate` true) for a repeated `X-Garrison-Delivery`. Notifications are signed the same way, so a receiver checks them with the same verify function and ignores a `X-Garrison-Delivery` it has seen before: delivery is at least once.

## Streaming run events

```ts
const queued = await client.runs.create({ agentName: "my-agent", input: "Hello" });
for await (const item of client.runs.stream(queued.id)) {
  if (item.event) console.log(item.event.eventType, item.event.text);
  if (item.run) console.log("finished:", item.run.status);
}
```

The iterator ends after `run.completed`. `runs.events` polls, and `runs.waitForCompletion` waits for a terminal status.

## Conversations

A conversation is a multi-turn session with one agent. Each turn is a run, and every turn after the first resumes the harness session the earlier turns built, on the node that holds that session's directories. Pass `{ startConversation: true }` to `agents.invoke`, `runs.create`, or `deployments.test` to start one; the returned run's `conversationId` names it. Pass that ID as `conversationId` to send the next turn.

```ts
const first = await client.agents.invoke("my-agent", "Plan the migration", { startConversation: true });
const conversationId = first.conversationId!;

const second = await client.agents.invoke("my-agent", "Now write step 1", { conversationId });
console.log(second.conversationTurn, second.resultText);   // 2 ...

const conversation = await client.conversations.get(conversationId);
const turns = (await client.conversations.listRuns(conversationId)).objects;   // oldest first
await client.conversations.delete(conversationId);                             // the runs are kept
```

Turns of one conversation never overlap. A turn sent while the previous one is unfinished is refused, not queued, with 409 `ConversationBusy`; wait for the previous run (or cancel it) and send again:

```ts
try {
  await client.agents.invoke("my-agent", "Next", { conversationId });
} catch (e) {
  if (!(e instanceof GarrisonError) || e.statusCode !== 409 || e.code !== "ConversationBusy") throw e;
  const { activeRunId } = await client.conversations.get(conversationId);
  if (activeRunId) await client.runs.waitForCompletion(activeRunId);
}
```

Other 409 codes are `ConversationAgentMismatch` (the conversation belongs to another agent), `ConversationDeploymentMismatch` (the request names a deployment other than the conversation's), and `ConversationDeploymentUnavailable` (the conversation's deployment was deleted). An unknown `conversationId` returns 404. `conversations.delete` also rejects with 409 `ConversationBusy` while a turn is unfinished.

`conversations.list(filter)` takes a `ConversationFilter` (`agentId`, `contextId` for the A2A context the conversation was created for, `callerId`, `search`, `maxResults`, `skip`, `ordering`). `runs.list({ conversationId })` lists a conversation's runs. A `Conversation` carries `turnCount`, `sessionId`, `affinityNodeId` and `affinityNodeName`, `activeRunId`, `lastRunId`, `busy` (true while a turn is unfinished), `fallbackCount`, and `lastFallbackReason`.

Each turn's `Run` has `conversationId`, `conversationTurn` (1 for the first turn, 0 outside a conversation), `resumeSessionId`, `affinityNodeId`, `affinityUntilUtc`, and `conversationFallbackReason`. A fallback happens when the turn cannot resume and starts a fresh session seeded with the transcript of the earlier turns instead; `CONVERSATION_FALLBACK_REASONS` and the `ConversationFallbackReason` type list the values (`AffinityNodeLost`, `AffinityWaitExpired`, `WorkspaceLost`, `SessionMissing`, `HarnessChanged`, `ResumeUnsupported`, `ExecutorWithoutState`). A turn that could not even fall back ends with outcome `ConversationStateLost`. Deleting a conversation writes a `ConversationDeleted` audit record. See "Conversations" in `REST_API.md`.

## Run timing and usage fields

Finished runs carry timing and usage metrics. Most nullable fields are omitted by the server when they cannot be measured, so treat them as optional. `outputTokensPerSecond`, `blockedReason`, `outputSchemaValid`, and `schemaValidationErrors` are always present and are `null` when there is nothing to report.

| Field | Type | Meaning |
|---|---|---|
| `firstTokenUtc`, `lastTokenUtc` | `string` (ISO 8601 UTC) or absent | First and last model output event. |
| `timeToFirstTokenMs` | `number` or absent | Start to first output event. |
| `streamingMs` | `number` or absent | First to last output event. |
| `executionMs` | `number` or absent | Start to completion. |
| `queueMs` | `number` or absent | Creation to start. |
| `totalMs` | `number` or absent | Creation to completion. |
| `delegationWaitMs` | `number` or absent | Time the run spent waiting on child runs it started (delegation), measured from server timestamps of the runs whose `parentRunId` is this run. |
| `timeToFirstTokenExcludingDelegationMs` | `number` or absent | `timeToFirstTokenMs` minus the delegation wait that happened before the first token; never negative. |
| `outputTokensPerSecond` | `number` or `null` | Output throughput while streaming; `null` when not measurable (no streaming window, or one shorter than 100 ms). |
| `reasoningTokens` | `number` (default 0) | Reasoning tokens reported by the harness. |
| `toolCallCount` | `number` (default 0) | Tool calls made by the run. |

`run.blockedReason` (`RunBlockedReason | null`) is computed by the server when a run is read. It is `null` unless the run is `Queued` and no Ready worker can run it. Values: `NoReadyWorker` (no node is Ready), `NoCapableWorker` (no Ready node reports the run's harness), `NoMatchingPool` (capable nodes exist but none matches the deployment's node pool or node selector), `NoIsolatingWorker` (the run is `Untrusted` or its deployment has an egress allowlist, and no Ready node with its harness can isolate it or enforce the allowlist). The tenant overview counts these runs as `blockedRuns`. See "Blocked runs" in `REST_API.md`.

Runs stopped by a worker run guard end `Failed` with outcome `RepetitionDetected` (the assistant text degenerated into a short repeated unit or into text with no letters or digits), `OutputLimitExceeded` (more assistant text than the deployment's `maxAssistantChars`), or `NoProgress` (nothing happened for `noProgressSeconds`). The partial output is in `run.resultText`, and the run has one `Warning` event with code `RunGuardTriggered`. A waiting invoke cancels its run when the connection drops; pass `{ cancelOnDisconnect: false }` to `agents.invoke` or `runs.create` to keep the run going. See "Run guards" and "Cancellation" in `REST_API.md`.

When the agent has an output schema, the server validates each run's final output against it. `run.outputSchemaValid` (`boolean | null`) is true or false after validation and `null` when nothing was validated, `run.schemaValidationErrors` (`string | null`) holds the first few errors of a failed validation, and `run.repairAttempts` (`number`, 0 or 1) counts the structured output repair Garrison makes when the harness can resume its session. A run whose output still does not validate fails with outcome `SchemaValidationFailed`; `RUN_OUTCOMES` and the `RunOutcome` type list every outcome. See "Structured output validation" in `REST_API.md`.

## Executors and run pods

`Deployment.executor` (`RunExecutor`: `"Process"`, the default, or `"KubernetesJob"` for a Kubernetes Job per run) chooses how runs execute; null uses the node pool's `defaultExecutor`, then Process. `Deployment.podResources` (`RunPodResources`) sets the run pod's requests and limits as Kubernetes quantities. Runs carry `executor`, worker nodes (`WorkerNode`) list `executors`, and only nodes reporting a run's executor claim it. `WorkspaceTemplate` kind `"PersistentVolume"` mounts `persistentVolumeClaim` at the workspace path (KubernetesJob runs only). `RUN_OUTCOMES` includes `PodFailed` for run pods that fail outside the harness. `WorkerNode.containerized` (default `false`) says whether the worker runs inside a container or pod, which makes the built-in Codex profiles default their sandbox to `danger-full-access`. See `docs/KUBERNETES.md`.

## Secret status

The control plane refreshes ChatGPT logins stored in `CodexAuthJson` secrets itself, shortly before the access token expires, and writes the rotated tokens back to the secret. When OpenAI rejects the stored refresh token for good (reused, expired, or revoked), the secret's status becomes `NeedsReauthentication`.

The `Secret` type carries `status` (`SecretStatus`, one of `SECRET_STATUSES`: `"Ok"` or `"NeedsReauthentication"`), `statusMessage` (the provider error, absent when `Ok`), `statusUtc` (when the status left `Ok`), `refreshedUtc` (when the control plane last refreshed the login itself), and `accessTokenExpiresUtc` (expiry of the stored access token; `CodexAuthJson` only). To find secrets that need attention, list them and check `secret.status === "NeedsReauthentication"`, then call `client.secrets.setValue(id, newAuthJson)`. A run whose deployment binds a secret in that state fails before it starts, with outcome `NotCredentialed` and an error message that starts with `SecretNeedsReauthentication:`. (`SecretRefreshFailed:` means the access token was expired and the refresh failed for a passing reason such as a network error; the secret stays `Ok` and a retry may work.) The fix is to replace the value: sign in again with `codex login` using a `CODEX_HOME` nothing else uses, then set the new `auth.json` as the secret's value. Setting a value returns the status to `Ok`. Do not keep using that login on another machine, because both copies share one refresh token; for shared deployments an `OpenAiApiKey` secret is simpler. See "Codex logins" in `docs/SECURITY.md`.

## Run analytics

`analytics.runs(query)` calls `GET /v1.0/api/tenants/{tenantId}/analytics/runs` and returns totals plus time-bucketed series. Every query field is optional: `from`, `to` (ISO 8601 UTC strings or `Date`), `interval` (`minute`, `hour`, `day`, `week`, `auto`), `agentId`, `harnessType`, `deploymentId`, `model` (served model; `"unknown"` matches runs without a recorded model), and `groupBy` (`none`, `agent`, `harness`, `model`, `harnessModel`). With `harnessModel` each series key is `Harness|model` (for example `ClaudeCode|claude-sonnet-5-5`) and its label is `Harness / model`.

```ts
const now = Date.now();
const report = await client.analytics.runs({ from: new Date(now - 86400000), to: new Date(now), interval: "hour", groupBy: "agent" });
console.log(report.totals.runs, report.totals.costUsd, report.bucketSeconds);
for (const series of report.series) {
  for (const bucket of series.buckets) console.log(series.label, bucket.startUtc, bucket.runs, bucket.timeToFirstTokenMsP95);
}
```

`bucketSeconds` is the authoritative bucket size. `truncated` is true when the 100,000-run cap was hit. Averages and percentiles are `null` when a bucket has no samples. Besides `timeToFirstTokenMsAvg`, `timeToFirstTokenMsP50`, and `timeToFirstTokenMsP95`, the metrics include `timeToFirstTokenExcludingDelegationMsAvg`, `timeToFirstTokenExcludingDelegationMsP50`, `timeToFirstTokenExcludingDelegationMsP95`, and `delegationWaitMsAvg`, so agents that delegate can be compared with agents that answer directly. The server returns 400 when `from` is not before `to`, when the range needs more than 400 buckets, or when a parameter is invalid.

`analytics.dimensions({ from, to })` calls `GET /v1.0/api/tenants/{tenantId}/analytics/runs/dimensions` and returns the distinct values among runs in the range (default: the last 24 hours), which is handy for filter pickers. The result is `{ agents: [{ id, name }], harnesses: string[], deployments: [{ id, name, agentId }], models: string[], truncated }`, with each list sorted by name.

```ts
const dims = await client.analytics.dimensions({ from: new Date(now - 7 * 86400000), to: new Date(now) });
for (const model of dims.models) {
  const byModel = await client.analytics.runs({ from: new Date(now - 7 * 86400000), to: new Date(now), model, groupBy: "harnessModel" });
  console.log(model, byModel.totals.runs);
}
```

## Agent revisions and promotion

An agent keeps its content in revisions. `client.agents.saveDraft(agent, content)` creates or replaces the single open draft, `publishRevision(agent, revision, { changeNote })` publishes it, and `listRevisions`, `getRevision`, `deleteRevision`, and `diffRevisions(agent, from, to)` read and compare them. `agent` is an identifier or name; `revision` is an `arv_` identifier or a revision number. `Agent` carries read-only `latestPublishedRevisionId` and `draftRevisionId`.

Each deployment has an `environment` (default `dev`) and an optional `agentRevisionId` pin; null follows the latest published revision. `Run.agentRevisionId` records the revision a run executed. `client.environments.get()` returns the tenant's ordered environments (`dev`, `staging`, `prod` by default, with `isDefault` true) and `update(list)` replaces them.

```ts
const draft = await client.agents.saveDraft("my-agent", { description: "Tighter instructions" });
const published = await client.agents.publishRevision("my-agent", draft.id, { changeNote: "v2" });
// Pins the latest published revision on the next environment after dev (staging by default).
const promotion = await client.promotions.promote({ agentId: published.agentId, sourceEnvironment: "dev" });
await client.promotions.rollback(promotion.id, { note: "revert" });
```

`client.promotions.list({ agentId, appId })` and `get(id)` read `PromotionRecord` audit entries; each lists the deployments it re-pinned in `items`.

## Agent assets

An agent asset is a versioned system prompt, skill, reference file, or document template (kind `SystemPrompt`, `Skill`, `ReferenceFile`, or `DocumentTemplate`; a `SystemPrompt` asset requires a prompt template ID). Assets are addressed by ID or name and their versions by number. Uploading a version sends every file base64-encoded; uploading files identical to the current version returns that version instead of creating a new one. Each returned file carries its lowercase hex `sha256`. A revision pins assets through `assetPins` (`assetId` plus an optional `version`; no version follows the current one), and deleting an asset a revision pins fails with HTTP 409 and code `AssetInUse`. Upload limits answer 413 (`AssetFileTooLarge`, `AssetVersionTooLarge`, `AssetTooManyFiles`). A run whose pinned file fails its SHA-256 check on the worker ends with outcome `AssetIntegrityFailed`.

```ts
const asset = await client.agentAssets.create({ name: "release-notes-skill", kind: "Skill" });
const version = await client.agentAssets.uploadVersion(asset.id, [{ path: "SKILL.md", content: "# Release notes\n", mediaType: "text/markdown" }], "first cut");
await client.agentAssets.uploadRaw(asset.id, "SKILL.md", new TextEncoder().encode("# v2\n"));
const bytes = await client.agentAssets.downloadFile(asset.id, version.number, "SKILL.md");
await client.agents.saveDraft("my-agent", { assetPins: [{ assetId: asset.id }] });
```

`list({ kind, search })`, `get`, `update`, `delete`, `listVersions` (a plain array, newest first), and `getVersion` complete the client. String content is UTF-8 encoded. `AGENT_ASSET_KINDS` lists the kinds and `RUN_OUTCOMES` includes `AssetIntegrityFailed`.

## Conversation file spaces

Every conversation has a file space: versioned files that all of its turns share. The worker mounts the space into each run's workspace under the deployment's `fileSpaceMountPath` (default `files`), and a run reports the space it used as `fileSpaceId`. `client.fileSpaces` reads and writes the space from outside. Each method takes the owner (`"conversations"` or `"runs"`) and the conversation or run ID, so you can reach a space from any of its turns.

Writes accept an optional `baseVersion`. Pass the version you last read (0 for a file that should not exist yet). If someone wrote in between, the server keeps both copies: your content lands under a conflict name, and the result has `conflict: true` and `path` set to that name. Leave `baseVersion` out to overwrite unconditionally.

```js
const cid = run.conversationId;
const result = await client.fileSpaces.write("conversations", cid, "notes/a.md", "# Notes\n", { baseVersion: 0, mediaType: "text/markdown" });
await client.fileSpaces.writeRaw("conversations", cid, "data/raw.bin", new Uint8Array([0, 1]));   // raw octet-stream body
const listing = await client.fileSpaces.list("conversations", cid);            // fileSpaceId, fileCount, totalBytes, files
await client.fileSpaces.versions("conversations", cid, "notes/a.md");          // newest first
const bytes = await client.fileSpaces.read("conversations", cid, "notes/a.md", 1);   // readText decodes UTF-8
const link = await client.fileSpaces.downloadUrl("runs", run.id, "notes/a.md"); // { url, expiresUtc }; no credentials needed
await client.fileSpaces.delete("conversations", cid, "notes/a.md");
```

Errors: 400 `InvalidFilePath`, 404 for an unknown conversation, run, or file, and 413 `FileTooLarge`, `FileSpaceFull`, or `TooManyFiles`. `ConversationFile`, `ConversationFileVersion`, `FileSpaceListing`, `FileSpaceUploadResult`, and `FileDownloadUrl` type the responses.

## Manifests

```ts
const result = await client.manifests.apply(yamlText, { dryRun: true });
for (const item of result.items) {
  console.log(item.kind, item.name, item.result, item.message ?? "");
  for (const change of item.changes ?? []) console.log("  ", change.field, change.before, "->", change.after);
}
```

Each item (`ManifestApplyItem`) reports what the apply did, or for a dry run what it would do. Items that are (or would be) `Updated` carry `changes` (`ManifestFieldChange`: `field`, `before`, `after`), with values as strings truncated to 200 characters. Every item also carries `warnings` (`FieldWarning[]`, empty when there is nothing to report) for dry runs and applies alike; see "Clamped values".

`manifests.export` returns a multi-document YAML bundle that apply accepts unchanged (`GET .../manifests/export`). With no selectors it exports every tenant-owned resource. `kinds` names whole kinds, `resources` names single records as `Kind/name` (split on the first `/`), `followReferences` also exports what the selection depends on (an agent brings its deployments, the triggers and notification endpoints that target it, and agents it may delegate to; a deployment brings its agent, harness profile, prompt templates, workspace template, and MCP servers; a pipeline brings its stage agents, pinned deployments, handoff templates, and triggers), and `includeBuiltIn` adds referenced built-in prompt templates and harness profiles. Secret values are never exported: the first document is a `kind: Bundle` document listing `requiredSecrets`, `requiredArtifactStores`, and `requiredBuiltIns`, and applying it to a tenant that lacks one fails with `errorCode` `MissingSecret`, `MissingArtifactStore`, or `MissingBuiltIn`. A reference that cannot be resolved fails with `MissingSecret` or `ReferenceNotFound` and an `errorField` naming it. Re-applying an applied bundle reports every document `Unchanged`. An unknown kind is a 400 with field code `UnknownKind`, a malformed resource selector is a 400 with `InvalidSelector`, and a selected resource that does not exist is a 404.

```ts
const bundle = await client.manifests.export({ resources: ["Agent/triage"], followReferences: true });
const check = await client.manifests.apply(bundle, { dryRun: true });
```

## Transcripts

```ts
const markdown = await client.runs.transcriptMarkdown(runId);
const transcript = await client.runs.transcript(runId, { includeThinking: true });
const conversation = await client.conversations.transcript(conversationId);
```

A transcript covers one run, or every turn of a conversation oldest first (`GET .../runs/{id}/transcript` and `GET .../conversations/{id}/transcript`). The Markdown form is for reading and sharing; the JSON form is the typed `Transcript` document (schema `garrison.transcript/v1`): `kind` (`Run` or `Conversation`), `turnCount`, total `usage`, and `turns`, each with the redacted `input`, `entries` (assistant text, tool calls and results, warnings, errors, lifecycle notes; thinking only when requested), `approvals`, `result`, `errorMessage`, `usage` (tokens, tool calls, cost, duration), and timestamps. Secrets read `[REDACTED]`, tool text is cut to the server's `Transcripts.ToolTextMaxChars` (`textTruncated`), and a transcript over `Transcripts.MaxBytes` is cut with `truncated` and a `truncationNote`. Unknown or other-tenant identifiers are a 404.

## Structured input

An agent with `inputSchemaJson` (JSON Schema text) only accepts input that is a JSON document matching it, on every surface. Saving a schema that is not valid JSON Schema fails with field code `InvalidJsonSchema`. An invocation whose input is not JSON is a 400 with field code `InputNotJson` on `input`; one that breaks the schema is a 400 with `InputSchemaViolation` on `input` or `input.<path>` (for example `input.topic` or `input.tags[1]`; a missing required property is reported on its own key).

```ts
try {
  await client.agents.invoke("triage", JSON.stringify({ count: 2 }), { inputContentType: "application/json" });
} catch (e) {
  if (e instanceof GarrisonError && e.statusCode === 400) console.log(e.fieldCodes, e.fields);
}
```

`Agent` has `inputMode`, `inputSchemaJson`, and `outputSchemaJson`; `INPUT_SCHEMA_FIELD_CODES` lists the codes.

## Clamped values

Numbers outside their documented range are not rejected: the server stores the nearest allowed value (deployment `maxAttempts` 99 is stored as 10). Create and update responses for agents, deployments, harness profiles, MCP servers, and workspace templates (`Agent`, `Deployment`, `HarnessProfile`, `McpServer`, `WorkspaceTemplate`) then carry `warnings?: FieldWarning[]` (`field`, `code`, `given`, `stored`, `message`). The property is absent when every value was stored as given, and reads never carry it. `FieldWarningCode` lists the codes; today the only one is `"ValueClamped"`.

```ts
const deployment = await client.deployments.create({ agentId: agent.id, name: "helper", harnessProfileId: profileId, maxAttempts: 99 });
for (const w of deployment.warnings ?? []) console.log(w.field, w.code, w.given, "->", w.stored, w.message);
```

Leave `warnings` out when you spread a response into an update body; it is response-only. See "Warnings" in `REST_API.md`.

## Errors

Non-success responses reject with `GarrisonError` carrying `statusCode`, `code`, `body`, and the parsed `error` payload. Validation failures expose field details as `fields`. The settings routes return 400 with `errors`, an object keyed by setting path (for example `Audit.RetentionDays`) whose values say what is wrong; nothing is saved when any value is rejected.

## Model prices

`client.modelPrices` provides tenant-scoped list, get, create, update, and delete operations for `/model-prices`. Prices start empty and are operator-configured USD rates per million tokens, keyed by exact served model and harness. Optional cache/reasoning rates fall back to input/output rates; explicit zero is free. Configure token inclusion flags for the harness accounting convention (Claude Code cache reads are separate). Harness-reported cost, including zero, takes precedence; estimates set `costEstimated`. Saved run costs survive later price edits or deletion. See [REST API](../../REST_API.md#model-prices).

## Usage quotas

The usage-quota module provides CRUD operations and `client.usageQuotas.usage(id)` for current daily UTC meters. Scope an entry to Tenant, Agent, or Deployment; null limits are unlimited and zero disallows usage. Limits cover admissions, completed tokens/cost, and active concurrency. Unknown cost keeps admission open and sets `costAccountingComplete=false`. Refusals carry `QuotaExceeded` and name the limit. Only administrators have built-in write grants. See [REST API](../../REST_API.md#usage-quotas) for accounting boundaries and supported CLI budget enforcement.

Usage quotas default to monitoring only. Explicitly set `enforcementEnabled` to `true` (Go: `EnforcementEnabled`, C#: `EnforcementEnabled`) on an active quota to enforce limits. Disabled enforcement does not reject runs or lower harness budgets.

## Executor capabilities

Deployments accept `requiredCapabilities`: `isolation` (`Process`, `Container`, `SandboxedRuntime`), `egressControl`, `filesystemSnapshot`, `sessionContinuation`, `crossNodeRestore`, and optional required `coldStartClass` (`Immediate`, `Cold`, `Warm`). Defaults add no requirement beyond Process. Runs retain an admission-time copy. Workers expose `executorCapabilities`; legacy executor names promise no advanced capabilities. Set `executor: "KubernetesJob"` with Container requirements. Unsupported requirements remain queued with `NoCapableWorker`.

Kubernetes workers can report `warmStart: true` alongside `coldStartClass: "Cold"`; this satisfies either Cold or Warm requirements. Warm support requires enabled warming and Kubernetes RBAC. Explicit Warm requirements reject PersistentVolume workspaces and custom pod resources.

## Trust level

Deployments accept `trustLevel` (`TrustLevel`): `"Trusted"` (the default) or `"Untrusted"` (`TRUST_LEVELS`). Untrusted runs need at least Container isolation on top of `requiredCapabilities`: an unset `executor` resolves to `KubernetesJob`, `executor: "Process"` is rejected with field code `UntrustedNeedsIsolation`, and a run no Ready worker can isolate stays `Queued` with `blockedReason` `"NoIsolatingWorker"`. `Run.trustLevel` reports the admitted level. A tenant with `requireUntrustedDeployments` (set through `client.tenants.update`) rejects Trusted deployments with field code `TenantRequiresUntrusted`. See "Deployment trust level" in `REST_API.md`.

## Egress allowlist

Deployments accept `egressRules` (`DeploymentEgressRule[]`): `cidr` (required, for example `"203.0.113.0/24"`), `port` (1 to 65535, `null` or omitted for every port), and `protocol` (`EgressProtocol`, `"TCP"` by default or `"UDP"`; `EGRESS_PROTOCOLS`). An empty list (the default) keeps the cluster's default run egress. With rules, a run pod may reach only DNS, the Garrison server MCP port, and the listed rules; host names are not accepted, so resolve them to CIDR blocks first. Validation errors are 400 field codes: `TooManyEgressRules` (more than 64 rules), `InvalidCidr` (not a CIDR network address, for example a host name or `203.0.113.7/24` with host bits set), `PortOutOfRange`, `InvalidProtocol`, `EgressRulesNeedKubernetesJob` (`executor` `Process` with rules), and `EgressRulesNeedColdStart` (`coldStartClass` `Warm` with rules). With rules, every run needs egress control and at least Container isolation: an unset executor resolves to `KubernetesJob`, and a run no Ready worker can enforce the allowlist for stays `Queued` with blocked reason `NoIsolatingWorker`; it is never run unenforced. See "Egress allowlists" in `docs/SECURITY.md`.

## Effect policy

Deployments accept `effectPolicy` (`EffectPolicy`, `EFFECT_POLICIES`): `"AtMostOnce"` (the default for new deployments) ends a run that was already `Running` when its worker was lost `Failed` with outcome `NodeLost`, `"AtLeastOnce"` requeues it while `maxAttempts` allows, and `"Journaled"` behaves as `"AtMostOnce"` until the effect journal exists. A run that was still `Leased` never started, so it is requeued under every policy. `Run.effectPolicy` reports the policy the run was admitted under; changing the deployment later does not change how that run is handled. `Deployment.retryOnNodeLoss` is deprecated: responses carry it as `true` only for `AtLeastOnce`, it is still accepted on input (`true` is `AtLeastOnce`, `false` is `AtMostOnce`), and a body whose `retryOnNodeLoss` disagrees with its `effectPolicy` is rejected with a 400 field error on `effectPolicy` (code `EffectPolicyConflict`). When you spread a deployment you read back into an update and change `effectPolicy`, leave `retryOnNodeLoss` out. See "Effect policy" in `REST_API.md`.

### Management MCP clients

The same agent/deployment/manifest validation, default bindings, versioning, and audit behavior now serve REST and management MCP. Use normal developer/user credentials for MCP configuration tools; hosted run tokens cannot change configuration. Existing SDK REST methods are unchanged. See [management MCP tools](../../docs/MANAGEMENT_MCP.md) for the MCP contract and replacement semantics.


Effect safety and continuation: run operations expose gateway intent metadata (no raw arguments or secrets). `Suspended` is an active status, so completion waits keep polling until a terminal status. Suspension and resume occur automatically for deployments with `suspensionEnabled` and compatible pinned harness `sessionFormat`; there are no manual suspend/resume endpoints. A raw CLI attempt lost after resuming fails closed if its new epoch lacks a safe checkpoint.

Remote agents use kind `Remote`, protocol `A2A` or `Mcp`, a full `remoteEndpointUrl`, and optionally `remoteCredentialSecretId` and `registrationTtlSeconds`; `mcpToolName` selects the remote MCP tool. Executors include `RemoteA2A` and `RemoteMcp`. See [remote agents](../../docs/REMOTE_AGENTS.md) and [tenant scheduling](../../docs/TENANT_SCHEDULING.md). Queue saturation returns HTTP 429 with code `QueueFull`, rather than creating a failed run.

System administrators can change tenant `schedulingWeight` (1 to 1000, default 1), use server settings for credential/run-token expiry policies and queue bounds, and run the master-key rotation method. Rotation uses keys already configured on the server and returns counts only; clients never supply key material to the endpoint. Keep old keys until a pass reports zero conflicts and failures.

LeaseBroker secret metadata uses `kind: "LeaseBroker"`, `brokerResource`, and optional `brokerAudience`; it rejects a static `value`. Issuance/revocation endpoints and provider authorization are operator-only settings. See the [provider contract](../../docs/CREDENTIAL_BROKER.md) for TTL, tombstone, and tenant authorization requirements.

`await client.runs.placement(runId)` returns read-only placement diagnostics. `await client.runs.databaseUsage(runId)` returns exact SQL attempts inside completed instrumented lifecycle scopes. Placement eligibility is advisory and reserves no capacity. External invocation wait is best effort: when the server wait budget is full, it returns the accepted run for polling. Resident synchronous delegation instead fails with `DelegationCapacityExhausted` before child creation when no wait slot is available. Poll an accepted run's ID instead of submitting another invocation.
