# Garrison.Sdk

C# client for the Garrison REST API. Targets .NET 8 and .NET 10.

**Garrison Agent Studio.** Garrison is a runtime for headless agent harnesses: a multi-tenant control plane with pull-based workers, exposed over REST, MCP, and A2A. Since 0.2.0 it is also an agent studio built on that runtime, so one platform covers an agentic app from start to finish. You build it with the agent architect (chat) or the canvas, test it in the playground, apply it through an approval, promote it between environments, run and scale it on the workers, and give its end users their own chat at `/apps/{slug}/`. This SDK reaches both halves: the management API for the runtime and the studio, and the end-user gateway of each app.

## Install

The package is not published to NuGet yet, so `dotnet add package Garrison.Sdk` finds nothing. Reference the project from your checkout of the repository instead:

```bash
dotnet add reference /path/to/Garrison/sdk/csharp/Garrison.Sdk/Garrison.Sdk.csproj
```

Or build a package and install it from a local folder:

```bash
dotnet pack /path/to/Garrison/sdk/csharp/Garrison.Sdk -c Release -o ./local-packages
dotnet add package Garrison.Sdk --prerelease --source ./local-packages
```

## Quick start

```csharp
using Garrison.Sdk;
using Garrison.Sdk.Models;
using Garrison.Sdk.Requests;

using (GarrisonClient client = new GarrisonClient("http://127.0.0.1:8700"))
{
    // The same email and password you use in the dashboard.
    await client.LoginAsync("admin@garrison", "password", "default");

    Run run = await client.Agents.InvokeAsync("my-agent", new InvokeRequest
    {
        Input = "Summarize the release notes",
        Wait = true,
        WaitSeconds = 120
    });

    Console.WriteLine(run.Status + ": " + run.ResultText);
}
```

To sign in with an access key pair instead, call `client.LoginWithKeysAsync(accessKey, secretKey)`. See "Where the credentials come from" below.

## Where the credentials come from

Email and password sign-in works the same on every runtime: tenant `default`, user `admin@garrison`, and the administrator password. There is no default: on Docker Compose it is `GARRISON_ADMIN_PASSWORD` in `docker/.env`, which `update.sh` generates when it is missing. On Kubernetes it is whatever `GARRISON_ADMIN_PASSWORD` held when `k8s/scripts/generate-secrets.sh` ran, or the random one it printed, stored in Secret `garrison-secrets`. A source build in development mode (`GARRISON_ALLOW_INSECURE_DEFAULTS=true`) uses `password`.

The seeded administrator access and secret keys depend on the runtime:

| Runtime | Access key | Secret key |
|---|---|---|
| Docker Compose | `GARRISON_DEFAULT_ACCESS_KEY` in `docker/.env` (generated by `update.sh`) | `GARRISON_DEFAULT_SECRET_KEY` in `docker/.env` |
| Source build in development mode | `access_garrison_default` | `secret_garrison_default_change_me` |
| Kubernetes (Kustomize or Helm) | random, key `default-access-key` in Secret `garrison-secrets` | random, key `default-secret-key` in Secret `garrison-secrets` |

On Kubernetes, read them with:

```bash
kubectl -n garrison get secret garrison-secrets -o jsonpath='{.data.default-access-key}' | base64 --decode; echo
kubectl -n garrison get secret garrison-secrets -o jsonpath='{.data.default-secret-key}' | base64 --decode; echo
kubectl -n garrison get secret garrison-secrets -o jsonpath='{.data.admin-password}' | base64 --decode; echo
```

You can also create a credential of your own in the dashboard (Access > Credentials); the secret key is shown once.

## Authentication

| Method | Effect |
|---|---|
| `LoginAsync(email, password, tenantId)` | Issues a user token and switches to bearer authentication. |
| `LoginWithKeysAsync(accessKey, secretKey)` | Issues a credential token and switches to bearer authentication. |
| `UseToken(token, tenantId)` | Uses an existing token. |
| `UseAccessKey(accessKey, secretKey, tenantId)` | Sends the key pair on every request. |
| `UseSignedRequests(accessKey, secretKey, tenantId)` | Signs every request with HMAC-SHA256. The secret never goes over the wire. |
| `UseAdminApiKey(apiKey, tenantId)` | Uses the platform admin API key. |

`GetTokenDetailsAsync`, `RefreshAsync`, and `LogoutAsync` manage the current token. The tenant for tenant-scoped calls comes from the login response or the `tenantId` argument.

## Modules

`GarrisonClient` exposes one client per resource: `Tenants`, `Users`, `Credentials`, `Roles`, `Permissions`, `RolePermissions`, `UserRoleAssignments`, `CredentialScopeAssignments`, `Agents`, `Deployments`, `HarnessProfiles`, `PromptTemplates`, `McpServers`, `Secrets`, `WorkspaceTemplates`, `ArtifactStores`, `Manifests`, `Runs`, `Conversations`, `Approvals`, `Pipelines`, `PipelineRuns`, `PipelineReviews`, `Triggers`, `NotificationEndpoints`, `AgentRevisions`, `AgentAssets`, `FileSpaces`, `Capabilities`, `FanOutGroups`, `Apps`, `StudioDrafts`, `Promotions`, `Analytics`, `Nodes`, `ControlNodes`, `NodePools`, `RequestHistory`, `Audit`, and `Settings`. Resource clients provide `ListAsync`, `GetAsync`, `CreateAsync`, `UpdateAsync`, and `DeleteAsync`, plus resource-specific operations such as `Agents.InvokeAsync`, `Credentials.RotateAsync`, and `PromptTemplates.RenderAsync`.

Control-plane replicas are read-only: `ControlNodes.ListAsync(query)` returns a `ControlNodeListResponse` (a page of `ControlNode` plus `RespondingNodeId`, the replica that answered) and `ControlNodes.GetAsync(id)` reads one replica by node ID. Each `ControlNode` carries `Status` (`ControlNodeStatusEnum`: `Starting`, `Ready`, `Draining`, `Offline`), version, schema version, backplane, start and heartbeat times, activity (`ActiveRequests`, `OpenStreams`, `HeldLongPolls`), `IsLeader`, and `LeaderEpoch` (leader only). `OverviewResponse` also has `ControlNodesByStatus` and `LeaderNodeId`. Reading needs Read on Node, like worker nodes.

Models, enums, request types, and response types live in `Garrison.Sdk.Models`, `Garrison.Sdk.Enums`, `Garrison.Sdk.Requests`, and `Garrison.Sdk.Responses`. They mirror the server contracts.

Fields whose content is free-form JSON are `System.Text.Json.JsonElement?`, not JSON text in a string, and are null when absent: agent, revision, and capability `InputSchema` and `OutputSchema`, `Run.StructuredOutput` and `FanOutMember.StructuredOutput`, `RunEvent.RawEvent`, `ToolInput`, and `ToolOutput` (also on `TranscriptEntry`), `Approval.Input` and `TranscriptApproval.Input`, `NotificationDelivery.Payload`, `McpToolDetail.InputSchema` in `McpServerTestResponse.ToolDetails`, and `AgentRevisionChange.From` and `To`. To send one, parse your JSON text first:

```csharp
Agent agent = new Agent();
agent.Name = "summarizer";
agent.InputMode = AgentInputModeEnum.Structured;
agent.InputSchema = JsonSerializer.Deserialize<JsonElement>("{\"type\":\"object\",\"properties\":{\"topic\":{\"type\":\"string\"}},\"required\":[\"topic\"]}");
agent = await client.Agents.CreateAsync(agent);
```

A `RunEvent` carries the harness line (or Garrison notice) as `RawEvent`, a JSON object; when the line is not valid JSON, for example because it was truncated, `RawEventText` carries the text and `RawEvent` is null. A `ToolCall` event whose arguments are JSON sets `ToolInput` and leaves `Text` null, and a `ToolResult` whose output is a JSON object or array sets `ToolOutput` and leaves `Text` null; any other event uses `Text`.

## Permission approvals

When a deployment has `ApprovalsEnabled` set (Claude Code profiles, and Codex profiles with CodexAppServer delivery), the harness relays permission prompts to Garrison. The deployment's `ApprovalRules` (a list of `DeploymentApprovalRule` with `Action`, `Pattern` in Claude Code rule syntax such as `Bash(git status:*)` or `mcp__github__*`, optional `InputPattern`, and `Description`) decide each request, and `ApprovalDefaultAction` (`ApprovalRuleActionEnum`: `Allow`, `Deny`, `Ask`) covers requests no rule matches. `Ask` sends the request to a person, who has `ApprovalTimeoutSeconds` (10 to 3600, default 300) before `ApprovalTimeoutDecision` applies.

```csharp
ApprovalFilter filter = new ApprovalFilter();
filter.Status = ApprovalStatusEnum.Pending;
EnumerationResult<Approval> pending = await client.Approvals.ListAsync(filter);

ApprovalDecideRequest decide = new ApprovalDecideRequest();
decide.Decision = ApprovalDecisionEnum.Allow;
decide.Remember = true; // also add an Allow rule (the approval's SuggestedRule) to the deployment
Approval decided = await client.Approvals.DecideAsync(pending.Objects[0].Id, decide);

ApprovalCheckRequest check = new ApprovalCheckRequest();
check.ToolName = "Bash";
check.Input = new ApprovalToolInput();
check.Input.Command = "git status --short";
ApprovalCheckResponse result = await client.Approvals.CheckAsync(deploymentId, check);
```

`Approvals.ListAsync` filters by status, run, root run, agent, deployment, decision source (`ApprovalSourceEnum`), and time range; for a pending count, filter on `Pending` with `MaxResults = 1` and read `TotalRecords`. `GetAsync` returns 404 for an approval outside the tenant. `DecideAsync` answers 409 (`ApprovalNotPending`) when the approval was already decided, and `Remember` needs Update on the approval's deployment. `Approval.Input` is the request's input (tool call arguments, or a studio draft's diff) as a JSON object with secrets redacted; when the stored input is not a JSON object, for example because it was clipped, `InputPreview` carries it as text instead. Only one of the two is set. `CheckAsync` records nothing and returns the action, whether a rule or the default decided (`Source`), the matching rule, a `SuggestedRule`, and whether approvals are enabled. `Run` carries `PendingApprovals`, `AwaitingApproval` (the run stays `Running` while it waits), and `ApprovalWaitMs`.

## Pipelines

A pipeline runs agents as ordered stages. Each stage runs in its own workspace and receives the caller's input plus the earlier stages' results through a `PipelineStage` prompt template. A stage with `RequiresReview` waits for a person before the pipeline continues.

```csharp
Pipeline pipeline = new Pipeline { Name = "draft-and-edit" };
pipeline.Stages.Add(new PipelineStage { Name = "write", AgentId = writerId, RequiresReview = true });
pipeline.Stages.Add(new PipelineStage { Name = "edit", AgentId = editorId });
pipeline = await client.Pipelines.CreateAsync(pipeline);

PipelineRun run = await client.Pipelines.StartAsync(pipeline.Name, new PipelineStartRequest { Input = "Write a haiku", Wait = true, WaitSeconds = 60 }, idempotencyKey: "haiku-1");
PipelineReview review = (await client.PipelineReviews.ListAsync(new PipelineReviewFilter { Status = PipelineReviewStatusEnum.Pending, PipelineRunId = run.Id })).Objects[0];
await client.PipelineReviews.DecideAsync(review.Id, new PipelineReviewDecideRequest { Decision = PipelineReviewDecisionEnum.Approve, Comment = "Keep the second line." });
run = await client.PipelineRuns.GetAsync(run.Id, waitSeconds: 60);
```

`Pipelines` adds `StartAsync` (Pipeline Execute plus Agent Execute on every stage agent; the optional idempotency key is sent as the `Idempotency-Key` header, and a repeat with different content answers 409 `IdempotencyKeyConflict`) and `PreviewAsync` (renders every stage prompt from sample input and sample stage outputs; nothing runs) to the standard CRUD calls, which accept an identifier or a name. Updates advance `Version`; started pipeline runs keep their snapshot. Deleting a pipeline with active pipeline runs answers 409 `PipelineInUse`.

`PipelineRuns` lists by pipeline, status (`PipelineRunStatusEnum`), caller, and time range; `GetAsync` takes an optional `waitSeconds` (up to 600) and returns when the pipeline run ends or waits for a review, with its `Stages`, stage `Runs`, and `Reviews`. `CancelAsync` cancels the pending review and the current stage run; `RetryAsync` resumes a `Failed`, `TimedOut`, or `Cancelled` pipeline run at the stage where it stopped; `DeleteAsync` removes a finished pipeline run (409 `PipelineRunActive` otherwise).

`PipelineReviews` lists by status (`PipelineReviewStatusEnum`), pipeline run, pipeline, stage run, and decision source, and `DecideAsync` takes `Approve` (the comment reaches the next stage as review notes), `RequestChanges` (comment required; the stage runs again with it, up to the stage's `MaxRevisions`, then 409 `RevisionLimitReached`), or `Reject` (the pipeline run fails with outcome `ReviewRejected`). A second decision answers 409 `ReviewNotPending`. Reviews are authorized as `Approval` Read and Update. Run tokens cannot use pipelines, pipeline runs, or reviews.

## Triggers and notifications

A trigger starts an agent run or a pipeline run on a cron schedule or when a signed webhook arrives. It runs as the principal that last created or changed it, so creating one needs Execute on its agent (or on the pipeline and every stage agent). A webhook trigger's `SigningSecret` is returned only by `CreateAsync` and `RotateSecretAsync`; store it then.

```csharp
Trigger hook = await client.Triggers.CreateAsync(new Trigger { Name = "on-push", Type = TriggerTypeEnum.Webhook, AgentId = agentId });
string secret = hook.SigningSecret!;
TriggerFire fire = await client.Triggers.DeliverWebhookAsync(hook.Id, secret, "{\"ref\":\"main\"}", "application/json", deliveryId: "delivery-1");
Trigger nightly = await client.Triggers.CreateAsync(new Trigger { Name = "nightly", Type = TriggerTypeEnum.Cron, AgentId = agentId, CronExpression = "0 2 * * *", TimeZone = "America/New_York" });
EnumerationResult<TriggerFire> fires = await client.Triggers.ListFiresAsync(nightly.Id, TriggerFireOutcomeEnum.Failed);
```

`Triggers` adds `ListAsync(query, type)`, `RotateSecretAsync`, `FireAsync` (fires now; an optional `TriggerFireRequest` payload reaches the input template as `webhook.body`), `ListFiresAsync` (filter by `TriggerFireOutcomeEnum`), and `DeliverWebhookAsync` (signs and posts a webhook as an external sender would). Runs a trigger started have `Kind` `Trigger` and `TriggerId`; `RunFilter.TriggerId` lists them, and `PipelineRun.TriggerId` is set the same way.

`NotificationEndpoints` manages URLs that receive signed JSON notifications for `NotificationEventEnum` events (`RunSucceeded`, `RunFailed`, `RunCancelled`, `RunTimedOut`, `PipelineCompleted`, `PipelineFailed`, `ApprovalRequested`). It adds `RotateSecretAsync`, `TestAsync` (sends a `Test` notification and returns the `NotificationDelivery` after its first attempt), `ListDeliveriesAsync` (filter by `NotificationDeliveryStatusEnum`), and `GetDeliveryAsync`; a delivery's `Payload` is the JSON body as a `JsonElement?` object. A loopback or private URL answers 400 with field code `DestinationBlocked` in `GarrisonException.Error.FieldCodes` unless the operator turned on `Notifications.AllowPrivateDestinations`; link-local addresses such as 169.254.169.254 are always refused.

`WebhookSignature.Header(secret, unixSeconds, body)` builds a signature and `WebhookSignature.Verify(header, secret, body, toleranceSeconds)` checks one. The signature header is `X-Garrison-Signature: t=<unix seconds>,v1=<hex>`, where the hex value is the lowercase HMAC-SHA256, keyed with the UTF-8 bytes of the signing secret, of the timestamp, a period, and the raw body. A header may carry several `v1` values; any match is accepted. The server accepts a webhook only within `Triggers.WebhookToleranceSeconds` (default 300) of its clock, answers every failed check with the same 401 `InvalidSignature`, and returns the earlier fire (HTTP 200, `duplicate` true) for a repeated `X-Garrison-Delivery`. Notifications are signed the same way, so a receiver checks them with the same verify function and ignores a `X-Garrison-Delivery` it has seen before: delivery is at least once.

## Agent revisions and promotion

`AgentRevisions` works on one agent at a time; the agent is addressed by ID or name and a revision by its `arv_` ID or its number. `SaveDraftAsync` creates or replaces the agent's single open draft, `PublishAsync` publishes it (optional `RevisionPublishRequest.ChangeNote`), `DiscardDraftAsync` deletes a draft, `ListAsync` returns revisions newest first, `GetAsync` reads one, and `DiffAsync(agentId, from, to)` returns an `AgentRevisionDiff` with one `AgentRevisionChange` per field (`RevisionChangeTypeEnum` `Changed`, `Added`, or `Removed`). `From` and `To` are `JsonElement?` values: objects for the `inputSchema` and `outputSchema` fields, strings for every other field. `Agent` reports `LatestPublishedRevisionId` and `DraftRevisionId`.

Each `Deployment` has an `Environment` (default `dev`) and an optional `AgentRevisionId` pin; an unpinned deployment runs the agent's current content. `Run.AgentRevisionId` records the revision a run executed.

`Promotions.GetEnvironmentsAsync` reads the tenant's ladder (`dev`, `staging`, `prod` until changed, with `IsDefault` true) and `UpdateEnvironmentsAsync` replaces it. `PromoteAsync(PromotionRequest)` pins the target environment's deployments of the agent to a revision; `TargetEnvironment` defaults to the next rung after `SourceEnvironment`, and `AllowSkip` permits jumping past one. `RollbackAsync` restores each deployment's previous pin and returns a `Rollback` record. `ListAsync(agentId, appId)` and `GetAsync` read the `PromotionRecord` history.

```csharp
AgentRevision draft = await client.AgentRevisions.SaveDraftAsync("my-agent", new AgentRevision { Description = "Sharper summary." });
AgentRevision published = await client.AgentRevisions.PublishAsync("my-agent", draft.Id, new RevisionPublishRequest { ChangeNote = "Tighter prompt." });
PromotionRecord promotion = await client.Promotions.PromoteAsync(new PromotionRequest { AgentId = "my-agent", SourceEnvironment = "dev", AgentRevisionId = published.Id });
await client.Promotions.RollbackAsync(promotion.Id);
```

## Agent assets

An agent asset is a versioned system prompt, skill, reference file, or document template (kind `SystemPrompt`, `Skill`, `ReferenceFile`, or `DocumentTemplate`; a `SystemPrompt` asset requires a prompt template ID). Assets are addressed by ID or name and their versions by number. Uploading a version sends every file base64-encoded; uploading files identical to the current version returns that version instead of creating a new one. Each returned file carries its lowercase hex `sha256`. A revision pins assets through `AgentRevision.AssetPins` (`assetId` plus an optional `version`; no version follows the current one), and deleting an asset a revision pins fails with HTTP 409 and code `AssetInUse`. Upload limits answer 413 (`AssetFileTooLarge`, `AssetVersionTooLarge`, `AssetTooManyFiles`). A run whose pinned file fails its SHA-256 check on the worker ends with outcome `AssetIntegrityFailed`.

`AgentAssets` offers `ListAsync(kind, query)`, `GetAsync`, `CreateAsync`, `UpdateAsync`, `DeleteAsync`, `ListVersionsAsync` (newest first), `GetVersionAsync`, `UploadFilesAsync` (files built with `AgentAssetUploadFile.FromBytes` or `FromText`), `UploadVersionAsync` (an `AgentAssetUploadRequest`), `UploadRawAsync` (one file as raw bytes), and `DownloadFileAsync`.

```csharp
AgentAsset asset = await client.AgentAssets.CreateAsync(new AgentAsset { Name = "release-notes-skill", Kind = AgentAssetKindEnum.Skill });
AgentAssetVersion version = await client.AgentAssets.UploadFilesAsync(asset.Id, new List<AgentAssetUploadFile> { AgentAssetUploadFile.FromText("SKILL.md", "# Release notes\n") }, "first cut");
byte[] skill = await client.AgentAssets.DownloadFileAsync(asset.Id, version.Number, "SKILL.md");
AgentRevision draft = await client.AgentRevisions.SaveDraftAsync("my-agent", new AgentRevision { AssetPins = new List<AgentRevisionAssetPin> { new AgentRevisionAssetPin { AssetId = asset.Id } } });
```

## Conversation file spaces

Every conversation has a file space: versioned files that all of its turns share. The worker mounts the space into each run's workspace under the deployment's `fileSpaceMountPath` (default `files`), and a run reports the space it used as `fileSpaceId`. `client.FileSpaces` reads and writes the space from outside. Each method takes a `FileSpaceOwnerEnum` (`Conversation` or `Run`) and the conversation or run ID, so you can reach a space from any of its turns.

Writes accept an optional base version. Pass the version you last read (0 for a file that should not exist yet). If someone wrote in between, the server keeps both copies: your content lands under a conflict name, and the result has its conflict flag set and its path set to that name. Leave the base version out to overwrite unconditionally.

```csharp
FileSpaceUploadResult result = await client.FileSpaces.WriteTextAsync(FileSpaceOwnerEnum.Conversation, conversationId, "notes/a.md", "# Notes\n", 0, "text/markdown");
await client.FileSpaces.WriteBytesAsync(FileSpaceOwnerEnum.Conversation, conversationId, "data/raw.bin", new byte[] { 0, 1 }); // raw octet-stream body
FileSpaceListing listing = await client.FileSpaces.ListAsync(FileSpaceOwnerEnum.Conversation, conversationId);
List<ConversationFileVersion> versions = await client.FileSpaces.ListVersionsAsync(FileSpaceOwnerEnum.Conversation, conversationId, "notes/a.md"); // newest first
byte[] data = await client.FileSpaces.ReadAsync(FileSpaceOwnerEnum.Conversation, conversationId, "notes/a.md", 1); // ReadTextAsync decodes UTF-8
FileDownloadUrl link = await client.FileSpaces.DownloadUrlAsync(FileSpaceOwnerEnum.Run, runId, "notes/a.md"); // no credentials needed
await client.FileSpaces.DeleteAsync(FileSpaceOwnerEnum.Conversation, conversationId, "notes/a.md");
```

`WriteAsync` takes a `FileSpaceWriteRequest` when you want to set `ContentBase64` or `Content` yourself. Errors: 400 `InvalidFilePath`, 404 for an unknown conversation, run, or file, and 413 `FileTooLarge`, `FileSpaceFull`, or `TooManyFiles`. `Run.FileSpaceId` and `Deployment.FileSpaceMountPath` carry the new fields.

## Capability catalog

The capability catalog describes agents, MCP server tools, and harness built-ins the same way, so an orchestrator can choose between them. Each `CapabilityDescriptor` has an `Id` (`cap_...`), `Name`, `Kind` (`CapabilityKindEnum`: `Agent`, `McpTool`, `HarnessBuiltIn`), `Origin` (`CapabilityOriginEnum`: `Derived` or `Manual`), `SourceKey`, the source fields (`SourceAgentId`, `SourceRevisionId`, `SourceMcpServerId`, `SourceToolName`, `SourceHarnessProfileId`, `SourceHarnessType`), `Summary`, `InputSchema` and `OutputSchema` (`JsonElement?`, usually objects), `Tags`, `Requirements` (node labels a run needs, as `CapabilityRequirement` `Key` and `Value`), `Hints`, `RefreshWarning`, and timestamps. `TenantId` is null for descriptors every tenant shares (harness built-ins of built-in profiles).

Derived descriptors follow their source: an agent gets one from its latest published revision, an MCP server one per listed tool, and a harness profile one per entry in `HarnessProfile.ToolProbes`. You cannot change or delete them (409 `CapabilityDerived`). Manual descriptors are yours to create, replace, and delete. Their names are unique per tenant (409 `NameConflict`), and schemas must be JSON Schema (400 with code `InvalidJsonSchema`). `Hints` (`CapabilityHints`) carry `Status` (`CapabilityHintStatusEnum`: `Unknown` until enough runs finish, then `Known`), `SampleSize`, `MedianDurationMs`, `P90DurationMs`, `MeanCostUsd`, `WindowDays`, and `ComputedUtc`; values are null while the status is `Unknown`.

```csharp
EnumerationResult<CapabilityDescriptor> agents = await client.Capabilities.ListAsync(CapabilityKindEnum.Agent);
EnumerationResult<CapabilityDescriptor> tagged = await client.Capabilities.ListAsync(null, "billing", "invoice"); // kind, tag, search
CapabilityDescriptor created = await client.Capabilities.CreateAsync(new CapabilityDescriptor
{
    Name = "lookup-invoice",
    Kind = CapabilityKindEnum.McpTool,
    Summary = "Find an invoice by number.",
    InputSchema = JsonSerializer.Deserialize<JsonElement>("{\"type\":\"object\",\"properties\":{\"number\":{\"type\":\"string\"}}}"),
    Tags = new List<string> { "billing" }
});
CapabilityDescriptor byName = await client.Capabilities.GetAsync("lookup-invoice"); // ID or name
created.Summary = "Find an invoice by its number.";
await client.Capabilities.UpdateAsync(created.Id, created);
CapabilityRefreshResult refreshed = await client.Capabilities.RefreshAsync(); // or RefreshAsync(mcpServerId)
await client.Capabilities.DeleteAsync(created.Id);
```

`RefreshAsync` refreshes derived descriptors now and returns `CapabilityRefreshResult`: `Agents`, `HarnessBuiltIns`, and `Hints` counts, plus one `CapabilityServerRefresh` per MCP server (`McpServerId`, `McpServerName`, `Tools`, `Removed`, `Warned`, and `Error` when the listing failed). A tool probe (`HarnessToolProbe`) names a tool, a bare `Executable` on the worker's PATH, at most one argument from `HarnessToolProbe.AllowedArguments` (default `--version`), and a `Description`; workers that find the tool report the node label `garrison.io/tool-{name}=true`.

## Fan-out groups

A run fans work out to several agents at once by calling the `garrison_fan_out` MCP tool, then collects the results with `garrison_gather`. The SDK cannot start a group; `client.FanOutGroups` reads and cancels them. A `FanOutGroup` has `FanOutGroupId` (`fog_...`), `ParentRunId`, `Status` (`FanOutGroupStatusEnum`: `Running`, `Joined`, `TimedOut`, `BudgetExceeded`, `Cancelled`; every status but `Running` is final), `StatusReason`, `JoinPolicy` (`FanOutJoinPolicyEnum`: `All`, `Any`, `Quorum`), `Quorum`, the counts `Total`, `Finished`, and `Succeeded`, the label lists `Pending` and `Failed`, `Members`, the totals `CostUsd` and `Tokens`, the budget `MaxCostUsd` and `MaxTokens` (null when unset), `DeadlineUtc`, `CreatedUtc`, and `CompletedUtc`. `Summary`, `ContinuationMarker`, and `ContinuationInstruction` are what a harness sees through `garrison_gather` and are normally null here.

Each `FanOutMember` has `Label`, `Agent`, `RunId` (the child run), `Status` (`RunStatusEnum`), `Outcome` (null until it finishes), `ResultText` with `ResultTruncated`, `StructuredOutput` (`JsonElement?`), `ErrorMessage`, `FilesWritten` (paths in the shared file space), `CostUsd`, and `Tokens`. A child run's `Run.FanOutGroupId` names its group.

```csharp
List<FanOutGroup> groups = await client.FanOutGroups.ListByRunAsync(runId); // oldest first; 404 when the run does not exist
FanOutGroup group = await client.FanOutGroups.GetAsync(groups[0].FanOutGroupId);
foreach (FanOutMember member in group.Members) Console.WriteLine(member.Label + " " + member.Status + " " + member.RunId);
FanOutGroup cancelled = await client.FanOutGroups.CancelAsync(group.FanOutGroupId); // cancels members still running
```

A group that does not exist, or belongs to another tenant, throws `GarrisonException` with status 404.

## Agentic apps

An agentic app is a group of agents behind one chat UI at `/apps/{slug}/` (see [docs/APPS.md](../../docs/APPS.md)). `client.Apps` lists, reads (by identifier or name), creates, replaces, and deletes them, and adds the delegation plan, app revisions, and promotion. An `AgenticApp` has `Id` (`app_...`), `Name` (1 to 64 lowercase letters, digits, and hyphens, unique in the tenant), `Slug` (unique across the cluster, default the name; 409 `AppSlugTaken`), `Description`, `EntryAgentId`, `Members` (`AgenticAppMember`: `AgentId`, `AgentName`, `Role`), `Edges` (`AgenticAppEdge`: `CallerAgentId`, `CalleeAgentId`, `FanOutAllowed`, default true), `Environments` (`AgenticAppEnvironment`: `Environment`, `DeploymentId`), `LiveEnvironment` (default `dev`), `AuthMode` (`AppAuthModeEnum`: `TenantUsers`, `AppUsers` (default), `Anonymous`), `AnonymousEnabled`, `ShowOperatorDetail`, the branding fields `DisplayName`, `LogoAssetId`, `PrimaryColor`, `AccentColor`, and `WelcomeText`, and `LatestPublishedRevisionId`. Members, the entry agent, and edge ends may be given by agent name on create and update. The server checks that the entry agent is a member, edges connect members, every member is reachable from the entry agent, and the edges have no cycle. An agent in an app cannot be deleted (409 `AgentInUse`).

```csharp
AgenticApp app = await client.Apps.CreateAsync(new AgenticApp
{
    Name = "research",
    EntryAgentId = "orchestrator",
    Members = new List<AgenticAppMember> { new AgenticAppMember { AgentId = "orchestrator" }, new AgenticAppMember { AgentId = "researcher" } },
    Edges = new List<AgenticAppEdge> { new AgenticAppEdge { CallerAgentId = "orchestrator", CalleeAgentId = "researcher" } },
    AuthMode = AppAuthModeEnum.AppUsers
});
AppDelegationPlan plan = await client.Apps.GetDelegationAsync(app.Id);   // Drift marks members whose published policy differs
AppDelegationPlan applied = await client.Apps.ApplyDelegationAsync(app.Id); // writes drafts; nothing is published
AppRevision draft = await client.Apps.CreateRevisionAsync(app.Id, new AppRevisionRequest { ChangeNote = "first cut" });
AppRevision published = await client.Apps.PublishRevisionAsync(app.Id, draft.Number.ToString());
PromotionRecord record = await client.Apps.PromoteAsync(app.Id, new AppPromotionRequest { SourceEnvironment = "dev" });
```

`AppDelegationPlan.Members` holds one `AppDelegationMember` per member: the graph's `DesiredMode` (`AllowList`, or `None` for a member that calls nobody), `DesiredAllowList`, and `DesiredMaxDepth`, the latest published revision's `PublishedMode`, `PublishedAllowList`, and `PublishedMaxDepth`, `Drift`, and after an apply `DraftRevisionNumber` or `SkippedReason` (`DraftConflict` when the member's open draft already changes its delegation another way). `CreateRevisionAsync` pins every member's latest published revision (409 `NoPublishedRevision` when a member has none); `ListRevisionsAsync` returns them newest first and `GetRevisionAsync` reads one by identifier (`apv_...`) or number. `PromoteAsync` moves every member's pin to every deployment of that member in the target environment under one `PromotionRecord` (409 `NoTargetDeployments` names a member without one); roll it back with `client.Promotions.RollbackAsync`. Promotion needs Execute on `Promotion` for the target environment.

`ResourceTypeEnum.AgenticApp` names apps in permissions. The built-in role `AppUser` lets a user use one app's chat UI when assigned with resource scope on the app identifier, and grants nothing in the management API. `Conversation.AppId` names the app whose chat UI started a conversation.

## Studio drafts

A studio draft holds manifest documents, one per resource, that a person or the agent architect edits before anything changes in live configuration (see [docs/STUDIO.md](../../docs/STUDIO.md)). Applying one takes a person's approval. `client.StudioDrafts` covers the routes under `/v1.0/api/tenants/{tenantId}/studio/drafts`.

```csharp
StudioDraft draft = await client.StudioDrafts.CreateAsync(new StudioDraftCreateRequest { Title = "research app" }); // or FromApp = "research"
draft = await client.StudioDrafts.PutItemAsync(draft.Id, "Agent", "researcher", draft.Version, yamlText);
StudioGraph graph = await client.StudioDrafts.ApplyGraphOperationAsync(draft.Id, new StudioGraphOperationRequest
{
    Version = draft.Version,
    Operation = StudioGraphOperationEnum.AddMember,
    App = "research",
    Agent = "researcher"
});
StudioDraftDiff diff = await client.StudioDrafts.DiffAsync(draft.Id);           // or ValidateAsync
Approval approval = await client.StudioDrafts.RequestApplyAsync(draft.Id, graph.Version);
await client.Approvals.DecideAsync(approval.Id, new ApprovalDecideRequest { Decision = ApprovalDecisionEnum.Allow });
```

A `StudioDraft` has `Id` (`sdr_...`), `Title`, `OwnerUserId`, `OwnerName`, `ConversationId`, `TargetApp`, `Version`, `Status` (`StudioDraftStatusEnum`: `Open`, `PendingApproval`, `Applied`, `Discarded`), `ApprovalId`, `PublishOnApply`, `ManifestApplyId`, `Items` (`StudioDraftItem`: `Kind`, `Name`, `Operation`, `Document`, `BaseHash`), and `Layout` (`StudioDraftNode`: `NodeKey`, `X`, `Y`). `ListAsync(mine: true, query)` returns your own drafts, newest change first, and `query.Search` matches the title.

Every change names the version you read. If the draft moved on, the call throws `GarrisonException` with status 409 and `Error.Code` `DraftVersionConflict`, and changes nothing; read the draft again and retry. A draft that is not `Open` answers 409 `DraftNotOpen`. `PutItemAsync` takes one manifest document whose kind and name match the path, and an optional `StudioDraftOperationEnum` (`Upsert`, the default, or `Delete`; drafts delete only `Agent`, `Deployment`, `Pipeline`, and `AgenticApp`). `RemoveItemAsync(id, kind, name, version)` drops an item.

`DiffAsync` and `ValidateAsync` return a `StudioDraftDiff`: `Valid` is true when nothing failed and nothing is stale, and each `StudioDraftDiffItem` has `Change` (`Create`, `Update` with `Changes`, `Delete`, `Unchanged`, or `Failed` with `Message` and `ErrorCode`) and `Stale`, set when the live resource changed after the draft was based on it. `GetGraphAsync` draws the draft's apps as `StudioGraphNode` entries (`Key`, `Kind`, `Name`, `InDraft`, `Deleted`, `EntryOf`, `MemberOf`, `Capabilities`, `X`, `Y`) and `StudioGraphEdge` entries (`App`, `From`, `To`, `FanOut`, `Depth`). `Capabilities` lists, for an agent the draft holds, the capabilities its document names (host tools such as pandoc), and `Depth` is the delegation depth an edge needs: one plus the longest chain of calls below the called member. `ApplyGraphOperationAsync` runs one `StudioGraphOperationEnum`: `AddMember` (`Agent`, optional `Role`; the first member becomes the entry agent), `RemoveMember`, `Connect` (`From`, `To`, optional `FanOut`), `Disconnect`, `SetEntry`, or `MoveNode` (`NodeKey`, `X`, `Y`).

`RequestApplyAsync` returns an `Approval` whose `Kind` is `ApprovalKindEnum.DraftApply` and whose `DraftId` names the draft, and freezes the draft as `PendingApproval` (400 `DraftStale`, `DraftInvalid`, or `DraftEmpty` when it cannot). Decide it with `client.Approvals.DecideAsync`: `Allow` needs Create on `Manifest` (403 `ApproverLacksPermission`), answers 409 `DraftStale` when live configuration moved since the request, and otherwise applies the documents as one manifest apply and marks the draft `Applied`. `Deny` returns the draft to `Open`. `ResourceTypeEnum.StudioDraft` names drafts in permissions.

## Agent architects

An agent architect is a deployment that may edit studio drafts for the person talking to it: a deployment of the protected `agent-architect` agent seeded in every tenant, or any deployment granted `ManagementAccess` `Drafts` (`ManagementAccessEnum`: `None`, `Drafts`). Its runs edit drafts and never apply them. `client.StudioDrafts` manages architects directly, so you never build the deployment yourself:

```csharp
ArchitectRequest request = new ArchitectRequest();
request.Name = "architect";
request.HarnessProfileId = "hrn_builtin_claude_code";
request.Model = "claude-sonnet-4-5";                          // optional; null uses the harness default
request.ArchitectPromptTemplateId = "builtin/agent-architect"; // optional; null binds builtin/agent-architect
Architect architect = await client.StudioDrafts.CreateArchitectAsync(request);

EnumerationResult<Architect> page = await client.StudioDrafts.ListArchitectsAsync(new EnumerationQuery { MaxResults = 10, Search = "arch", ActiveOnly = true });
Architect read = await client.StudioDrafts.GetArchitectAsync("architect");       // identifier or name

request.Active = false;
request.ArchitectPromptTemplateId = "builtin/agent-architect-guided";
architect = await client.StudioDrafts.UpdateArchitectAsync(architect.Id, request);
await client.StudioDrafts.DeleteArchitectAsync(architect.Id);                    // drafts are kept
```

An `Architect` has `Id` (the deployment identifier), `TenantId`, `Name`, `Description`, `AgentId`, `AgentName`, `HarnessProfileId`, `Model`, `Active`, `ArchitectPromptTemplateId`, `ArchitectPromptName`, `ArchitectPromptVersion` (null follows the template's current version), `ArchitectPromptCurrentVersion`, `ConfigVersion`, `IsProtected`, `CreatedUtc`, and `LastUpdateUtc`. `ArchitectRequest` takes `Name` and `HarnessProfileId` (both required; 400 without them), `Description`, `Model`, `Active` (default true), `ArchitectPromptTemplateId`, and `ArchitectPromptVersion` (1 or more, or null). On update, a null `ArchitectPromptTemplateId` keeps the current prompt, and deployment settings the request does not name are kept. Create answers 409 `NameConflict` for a name in use and 409 `ArchitectAgentMissing` when the tenant has no `agent-architect`; both create and update answer 400 `InvalidArchitectPrompt` for a template that is not a System template the tenant can read. `GetArchitectAsync`, `UpdateArchitectAsync`, and `DeleteArchitectAsync` answer 404 for a deployment that is not an architect. `ListArchitectsAsync` takes `MaxResults` (1 to 1000, default 25), `Skip`, `Ordering`, `Search` (part of the name), and `ActiveOnly`. These calls need Read, Create, Update, or Delete on `Deployment`. An `Architect` also carries `CredentialSecretId`, `CredentialSecretName`, and `CredentialSecretKind` (all null when none is bound). `ArchitectRequest.CredentialSecretId` takes the identifier or name of an active tenant secret that the harness signs in with, bound to the deployment under the alias `credential` (400 `InvalidCredentialSecret` otherwise); null binds none on create and keeps the current one on update, and an empty string on update removes it.

`Deployments.CreateAsync` still accepts `Deployment.ArchitectPromptTemplateId` and `ArchitectPromptVersion` on create for a deployment of `agent-architect`; without them it binds `builtin/agent-architect`. Both read back as null on a `Deployment`, so read the choice from the `Architect` or with `GetArchitectPromptAsync`.

## Conversations

A conversation is a multi-turn session with one agent. Each turn is a run, and every turn after the first resumes the harness session the earlier turns built, on the node that holds that session's directories. Set `StartConversation = true` on an `InvokeRequest` or `RunCreateRequest` (also accepted by `Deployments.TestAsync`) to start one; the returned run's `ConversationId` names it. Pass that ID as `ConversationId` to send the next turn.

```csharp
Run first = await client.Agents.InvokeAsync("my-agent", new InvokeRequest { Input = "Plan the migration", StartConversation = true });
string conversationId = first.ConversationId!;

Run second = await client.Agents.InvokeAsync("my-agent", new InvokeRequest { Input = "Now write step 1", ConversationId = conversationId });
Console.WriteLine(second.ConversationTurn + ": " + second.ResultText);   // 2: ...

Conversation conversation = await client.Conversations.GetAsync(conversationId);
EnumerationResult<Run> turns = await client.Conversations.ListRunsAsync(conversationId);   // oldest first
await client.Conversations.DeleteAsync(conversationId);   // the runs are kept
```

Turns of one conversation never overlap. A turn sent while the previous one is unfinished is refused, not queued, with 409 `ConversationBusy`; wait for the previous run (or cancel it) and send again:

```csharp
try
{
    await client.Agents.InvokeAsync("my-agent", new InvokeRequest { Input = "Next", ConversationId = conversationId });
}
catch (GarrisonException e) when (e.StatusCode == 409 && e.Error?.Code == "ConversationBusy")
{
    Conversation current = await client.Conversations.GetAsync(conversationId);
    if (current.ActiveRunId != null) await client.Runs.WaitForCompletionAsync(current.ActiveRunId, TimeSpan.FromMinutes(5));
}
```

Other 409 codes are `ConversationAgentMismatch` (the conversation belongs to another agent), `ConversationDeploymentMismatch` (the request names a deployment other than the conversation's), and `ConversationDeploymentUnavailable` (the conversation's deployment was deleted). An unknown `ConversationId` returns 404. `DeleteAsync` also returns 409 `ConversationBusy` while a turn is unfinished.

`Conversations.ListAsync(ConversationFilter)` filters by `AgentId`, `ContextId` (the A2A context the conversation was created for), `CallerId`, and `Search`, with `Skip`, `MaxResults`, and `Ordering`. `RunFilter.ConversationId` lists a conversation's runs through `Runs.ListAsync`. A `Conversation` carries `TurnCount`, `SessionId`, `AffinityNodeId` and `AffinityNodeName`, `ActiveRunId`, `LastRunId`, `Busy` (true while a turn is unfinished), `FallbackCount`, and `LastFallbackReason`.

Each turn's `Run` has `ConversationId`, `ConversationTurn` (1 for the first turn, 0 outside a conversation), `ResumeSessionId`, `AffinityNodeId`, `AffinityUntilUtc`, and `ConversationFallbackReason`. A fallback happens when the turn cannot resume and starts a fresh session seeded with the transcript of the earlier turns instead: `ConversationFallbackReasonEnum` is `AffinityNodeLost`, `AffinityWaitExpired`, `WorkspaceLost`, `SessionMissing`, `HarnessChanged`, `ResumeUnsupported`, or `ExecutorWithoutState`. A turn that could not even fall back ends with `RunOutcomeEnum.ConversationStateLost`. Deleting a conversation writes an `AuditEventTypeEnum.ConversationDeleted` record. See "Conversations" in `REST_API.md`.

## Run timing and usage

Finished runs carry timing and usage fields in addition to `InputTokens`, `OutputTokens`, `CachedTokens`, and `CostUsd`:

| Property | Type | Meaning |
|---|---|---|
| `FirstTokenUtc`, `LastTokenUtc` | `DateTime?` | First and last model output event (UTC). |
| `TimeToFirstTokenMs` | `long?` | Process start to the first model output event. |
| `StreamingMs` | `long?` | First to last model output event. |
| `ExecutionMs` | `long?` | Start to completion. |
| `QueueMs` | `long?` | Time spent queued before the run was leased. |
| `TotalMs` | `long?` | Creation to completion. |
| `DelegationWaitMs` | `long?` | Time the run spent waiting on child runs it started (delegation), measured from server timestamps of the runs whose `ParentRunId` is this run. |
| `TimeToFirstTokenExcludingDelegationMs` | `long?` | `TimeToFirstTokenMs` minus the delegation wait that happened before the first token; never negative. |

## Blocked runs

`Run.BlockedReason` (`RunBlockedReasonEnum?`) is computed by the server when a run is read. It is null unless the run is `Queued` and no Ready worker can run it. Values: `NoReadyWorker` (no node is Ready), `NoCapableWorker` (no Ready node reports the run's harness), `NoMatchingPool` (capable nodes exist but none matches the deployment's node pool or node selector), `NoIsolatingWorker` (the run is `Untrusted` or its deployment has an egress allowlist, and no Ready node with its harness can isolate it or enforce the allowlist), `NoToolWorker` (the run's agent uses a harness built-in capability such as pandoc, and no Ready worker that can run it reports that tool). The tenant overview counts these runs as `OverviewResponse.BlockedRuns`. See "Blocked runs" in `REST_API.md`.

Runs stopped by a worker run guard end `Failed` with `RunOutcomeEnum.RepetitionDetected` (the assistant text degenerated into a short repeated unit or into text with no letters or digits), `RunOutcomeEnum.OutputLimitExceeded` (more assistant text than the deployment's `MaxAssistantChars`), or `RunOutcomeEnum.NoProgress` (nothing happened for `NoProgressSeconds`). The partial output is in `Run.ResultText`, and the run has one `Warning` event with code `RunGuardTriggered`. `Deployment.RepetitionGuard`, `Deployment.MaxAssistantChars`, and `Deployment.NoProgressSeconds` set the limits per deployment; null uses the cluster defaults. A waiting invoke (`InvokeRequest.Wait` true) cancels its run when the connection drops, for example when the `CancellationToken` passed to `InvokeAsync` is cancelled; set `InvokeRequest.CancelOnDisconnect = false` to keep the run going. See "Run guards" and "Cancellation" in `REST_API.md`.

When the agent has an output schema, the server validates each run's final output against it. `Run.OutputSchemaValid` (`bool?`) is true or false after validation and null when nothing was validated, `Run.SchemaValidationErrors` (`string?`) holds the first few errors of a failed validation, and `Run.RepairAttempts` (`int`, 0 or 1) counts the structured output repair Garrison makes when the harness can resume its session. A run whose output still does not validate fails with `RunOutcomeEnum.SchemaValidationFailed`. See "Structured output validation" in `REST_API.md`.

## Executors and run pods

`Deployment.Executor` chooses how runs execute: `RunExecutorEnum.Process` (a subprocess of the worker, the default) or `RunExecutorEnum.KubernetesJob` (a Kubernetes Job per run, in its own pod with no service account token and a hardened security context). Null uses the node pool's `NodePool.DefaultExecutor`, then Process. `Deployment.PodResources` (`RunPodResources`: `CpuRequest`, `CpuLimit`, `MemoryRequest`, `MemoryLimit`, `EphemeralStorageRequest`, `EphemeralStorageLimit`, as Kubernetes quantities such as `500m` or `2Gi`) sets the run pod's requests and limits. Each run records its executor in `Run.Executor`, and only nodes whose `Node.Executors` include it claim the run; a run nobody can take reports `RunBlockedReason` `NoCapableWorker`. `WorkspaceKindEnum.PersistentVolume` with `WorkspaceTemplate.PersistentVolumeClaim` mounts an existing claim at the workspace path (KubernetesJob runs only). Run pod failures outside the harness (unschedulable, image pull, OOMKilled, evicted) end with `RunOutcomeEnum.PodFailed` and a message naming the cause. See `docs/KUBERNETES.md`.

## Secret status

The control plane refreshes ChatGPT logins stored in `CodexAuthJson` secrets itself, shortly before the access token expires, and writes the rotated tokens back to the secret. When OpenAI rejects the stored refresh token for good (reused, expired, or revoked), the secret's status becomes `NeedsReauthentication`.

`Secret` carries `Status` (`SecretStatusEnum`: `Ok` or `NeedsReauthentication`), `StatusMessage` (the provider error, or null when `Ok`), `StatusUtc` (when the status left `Ok`), `RefreshedUtc` (when the control plane last refreshed the login itself), and `AccessTokenExpiresUtc` (expiry of the stored access token; `CodexAuthJson` only). To find secrets that need attention, list them and check `Status == SecretStatusEnum.NeedsReauthentication`. A run whose deployment binds a secret in that state fails before it starts, with outcome `NotCredentialed` and an error message that starts with `SecretNeedsReauthentication:`. (`SecretRefreshFailed:` means the access token was expired and the refresh failed for a passing reason such as a network error; the secret stays `Ok` and a retry may work.) The fix is to replace the value: sign in again with `codex login` using a `CODEX_HOME` nothing else uses, then set the new `auth.json` as the secret's value. Setting a value returns the status to `Ok`. Do not keep using that login on another machine, because both copies share one refresh token; for shared deployments an `OpenAiApiKey` secret is simpler. See "Codex logins" in `docs/SECURITY.md`.

## Run analytics

`Analytics.RunsAsync` returns totals and time-bucketed series of run counts, tokens, cost, latency percentiles, and throughput for the tenant.

```csharp
RunAnalyticsQuery query = new RunAnalyticsQuery();
query.From = DateTime.UtcNow.AddDays(-1);
query.To = DateTime.UtcNow;
query.Interval = AnalyticsIntervalEnum.Hour;
query.GroupBy = AnalyticsGroupByEnum.Agent;

RunAnalyticsResponse analytics = await client.Analytics.RunsAsync(query);
Console.WriteLine("runs: " + analytics.Totals.Runs + ", p95 TTFT: " + analytics.Totals.TimeToFirstTokenMsP95);
foreach (RunAnalyticsSeries series in analytics.Series)
{
    foreach (RunAnalyticsBucket bucket in series.Buckets) Console.WriteLine(series.Label + " " + bucket.StartUtc + " " + bucket.Runs);
}
```

Every query member is optional. `Interval` is `Auto`, `Minute`, `Hour`, `Day`, or `Week`. `GroupBy` is `None`, `Agent`, `Harness`, `Model`, or `HarnessModel` (sent as `harnessModel`); with `HarnessModel` each series key is `Harness|model` (for example `ClaudeCode|claude-sonnet-5-5`) and its label is `Harness / model`. `AgentId`, `DeploymentId`, `HarnessType`, and `Model` filter the runs; `Model` matches the run's served model, and `"unknown"` matches runs without a recorded model. `BucketSeconds` in the response is the authoritative bucket size, and `Truncated` is true when the server hit its 100,000-run cap. `RunAnalyticsMetrics` (on `Totals` and every bucket) also carries `TimeToFirstTokenExcludingDelegationMsAvg`, `TimeToFirstTokenExcludingDelegationMsP50`, `TimeToFirstTokenExcludingDelegationMsP95`, and `DelegationWaitMsAvg`, so agents that delegate can be compared with agents that answer directly. The server returns 400 (thrown as `GarrisonException`) when `From` is not earlier than `To`, when the range needs more than 400 buckets, or when a parameter is invalid.

`Analytics.DimensionsAsync(from, to)` returns the distinct agents, harness types, deployments, and served models among runs in a range (default: the last 24 hours), which is what a filter picker needs. Lists are sorted by name and never null.

```csharp
RunAnalyticsDimensions dimensions = await client.Analytics.DimensionsAsync(DateTime.UtcNow.AddDays(-7), DateTime.UtcNow);
foreach (string model in dimensions.Models)
{
    RunAnalyticsQuery byModel = new RunAnalyticsQuery();
    byModel.Model = model;
    byModel.GroupBy = AnalyticsGroupByEnum.HarnessModel;
    RunAnalyticsResponse report = await client.Analytics.RunsAsync(byModel);
    Console.WriteLine(model + ": " + report.Totals.Runs);
}
```

`RunAnalyticsDimensions` has `Agents` (`RunAnalyticsAgentDimension`: `Id`, `Name`), `Harnesses`, `Deployments` (`RunAnalyticsDeploymentDimension`: `Id`, `Name`, `AgentId`), `Models`, and `Truncated`.

## Manifests

```csharp
ManifestApply result = await client.Manifests.ApplyAsync(File.ReadAllText("agents.yaml"), dryRun: true);

{
```

Each item reports what the apply did, or for a dry run what it would do. `Manifests.ExportAsync` returns a multi-document YAML bundle that apply accepts unchanged (`GET .../manifests/export`). With no selectors it exports every tenant-owned resource. `ManifestExportRequest.Kinds` names whole kinds, `Resources` names single records as `Kind/name` (split on the first `/`), `FollowReferences` also exports what the selection depends on (an agent brings its deployments, the triggers and notification endpoints that target it, and agents it may delegate to; a deployment brings its agent, harness profile, prompt templates, workspace template, and MCP servers; a pipeline brings its stage agents, pinned deployments, handoff templates, and triggers), and `IncludeBuiltIn` adds referenced built-in prompt templates and harness profiles. An unknown kind is a 400 with field code `UnknownKind`, a malformed resource selector is a 400 with `InvalidSelector`, and a selected resource that does not exist is a 404.

```csharp
ManifestExportRequest selection = new ManifestExportRequest();
selection.Resources.Add("Agent/triage");

```

## Transcripts

```csharp
string markdown = await client.Runs.GetTranscriptMarkdownAsync(runId);

```

A transcript covers one run, or every turn of a conversation oldest first (`GET .../runs/{id}/transcript` and `GET .../conversations/{id}/transcript`). The Markdown form is for reading and sharing; the JSON form is the typed `Transcript` document (schema `garrison.transcript/v1`): `kind` (`Run` or `Conversation`), `turnCount`, total `usage`, and `turns`, each with the redacted `input`, `entries` (assistant text, tool calls and results, warnings, errors, lifecycle notes; thinking only when requested; JSON tool arguments and results arrive in `toolInput` and `toolOutput` with `text` null), `approvals` (`input` as a JSON object, or `inputPreview` text when the input is not one), `result`, `errorMessage`, `usage` (tokens, tool calls, cost, duration), and timestamps. Secrets read `[REDACTED]`, tool text is cut to the server's `Transcripts.ToolTextMaxChars` (`textTruncated`), and a transcript over `Transcripts.MaxBytes` is cut with `truncated` and a `truncationNote`. Unknown or other-tenant identifiers are a 404.

## Structured input

An agent with `inputSchema` (a JSON Schema object) only accepts input that is a JSON document matching it, on every surface. Saving a schema that is not valid JSON Schema fails with field code `InvalidJsonSchema`. An invocation whose input is not JSON is a 400 with field code `InputNotJson` on `input`; one that breaks the schema is a 400 with `InputSchemaViolation` on `input` or `input.<path>` (for example `input.topic` or `input.tags[1]`; a missing required property is reported on its own key).

```csharp
try
{
    await client.Agents.InvokeAsync("triage", new InvokeRequest { Input = "{\"count\":2}", InputContentType = "application/json" });
}
catch (GarrisonException e) when (e.StatusCode == 400)
{
    foreach (KeyValuePair<string, string> code in e.Error?.FieldCodes ?? new Dictionary<string, string>()) Console.WriteLine(code.Key + ": " + code.Value);
}
```

## Warnings

A few numeric fields have a documented range, and the server clamps an out-of-range value to the nearest allowed value instead of rejecting the request. The create and update responses of `Agents`, `Deployments`, `HarnessProfiles`, `McpServers`, and `WorkspaceTemplates` then carry `Warnings` (`List<FieldWarning>?`): one `FieldWarning` per value, with `Field` (the REST field name, for example `maxAttempts` or `delegationMaxDepth`), `Code` (`ValueClamped`), `Given` and `Stored` (the values as text), and `Message`. `Warnings` is null when there is nothing to report and on reads, and the server never stores it. Manifest apply items carry the same warnings on dry runs and applies.

```csharp
Deployment saved = await client.Deployments.UpdateAsync(deployment.Id, deployment);
if (saved.Warnings != null)
{
    foreach (FieldWarning warning in saved.Warnings) Console.WriteLine(warning.Field + ": " + warning.Message);
}
```

The typed models in this SDK clamp the same ranges when you set a property (setting `MaxAttempts = 99` stores 10 locally), so a request built from them rarely produces a warning. Warnings matter when values come from somewhere else: manifests, or bodies sent through `client.Transport`. See "Warnings" in `REST_API.md`.

## Errors

Non-success responses throw `GarrisonException` with `StatusCode`, the parsed `Error` (`ErrorResponse`: `Code`, `Message`, `RequestId`, and more), and the raw `ResponseBody`. Validation failures fill `Error.Fields`. The settings routes return 400 with `Error.Errors`, a dictionary keyed by setting path (for example `Audit.RetentionDays`) whose values say what is wrong; nothing is saved when any value is rejected. Every async method accepts a `CancellationToken`.

## Usage quotas

The usage-quota module provides CRUD operations and `client.UsageQuotas.UsageAsync(id, token)` for current daily UTC meters. ## Executor capabilities

Deployments accept `requiredCapabilities`: `isolation` (`Process`, `Container`, `SandboxedRuntime`), `egressControl`, `filesystemSnapshot`, `sessionContinuation`, `crossNodeRestore`, and optional required `coldStartClass` (`Immediate`, `Cold`, `Warm`). Defaults add no requirement beyond Process. Runs retain an admission-time copy. Workers expose `executorCapabilities`; legacy executor names promise no advanced capabilities. Set `executor: "KubernetesJob"` with Container requirements. Unsupported requirements remain queued with `NoCapableWorker`.

Kubernetes workers can report `warmStart: true` alongside `coldStartClass: "Cold"`; this satisfies either Cold or Warm requirements. Warm support requires enabled warming and Kubernetes RBAC. Explicit Warm requirements reject PersistentVolume workspaces and custom pod resources.

## Trust level

`Deployment.TrustLevel` (`DeploymentTrustLevelEnum`) is `Trusted` (the default) or `Untrusted`. Untrusted runs need at least Container isolation on top of `RequiredCapabilities`: an unset `Executor` resolves to `KubernetesJob`, `Process` is rejected with field code `UntrustedNeedsIsolation`, and a run no Ready worker can isolate stays `Queued` with `BlockedReason` `RunBlockedReasonEnum.NoIsolatingWorker`. `Run.TrustLevel` reports the admitted level. `Tenant.RequireUntrustedDeployments` and `TenantRequest.RequireUntrustedDeployments` control the tenant policy that rejects Trusted deployments with field code `TenantRequiresUntrusted`. See "Deployment trust level" in `REST_API.md`.

## Egress allowlist

`Deployment.EgressRules` (`List<DeploymentEgressRule>`, never null) is the deployment's egress allowlist. Each rule has `Cidr` (required, for example `203.0.113.0/24`), `Port` (`int?`, 1 to 65535, null for every port), and `Protocol` (`EgressProtocolEnum.TCP`, the default, or `UDP`). An empty list (the default) keeps the cluster's default run egress. With rules, a run pod may reach only DNS, the Garrison server MCP port, and the listed rules; host names are not accepted, so resolve them to CIDR blocks first. Validation errors are 400 field codes: `TooManyEgressRules` (more than 64 rules), `InvalidCidr` (not a CIDR network address, for example a host name or `203.0.113.7/24` with host bits set), `PortOutOfRange`, `InvalidProtocol`, `EgressRulesNeedKubernetesJob` (`executor` `Process` with rules), and `EgressRulesNeedColdStart` (`coldStartClass` `Warm` with rules). With rules, every run needs egress control and at least Container isolation: an unset executor resolves to `KubernetesJob`, and a run no Ready worker can enforce the allowlist for stays `Queued` with `BlockedReason` `RunBlockedReasonEnum.NoIsolatingWorker`; it is never run unenforced. See "Egress allowlists" in `docs/SECURITY.md`.

## Effect policy

`Deployment.EffectPolicy` (`DeploymentEffectPolicyEnum`) decides what happens to a run that was already `Running` when its worker was lost: `AtMostOnce` (the default for new deployments) ends it `Failed` with outcome `NodeLost`, `AtLeastOnce` requeues it while `MaxAttempts` allows, and `Journaled` behaves as `AtMostOnce` until the effect journal exists. A run that was still `Leased` never started, so it is requeued under every policy. `Run.EffectPolicy` reports the policy the run was admitted under; changing the deployment later does not change how that run is handled. `Deployment.RetryOnNodeLoss` is deprecated: it reads `true` only for `AtLeastOnce`, setting it to `true` selects `AtLeastOnce` and `false` selects `AtMostOnce` (a `Journaled` deployment stays `Journaled`), and this SDK always sends it consistent with `EffectPolicy`. The server rejects a request whose `retryOnNodeLoss` disagrees with its `effectPolicy` with a 400 field error on `effectPolicy` (code `EffectPolicyConflict`). See "Effect policy" in `REST_API.md`.

Effect safety and continuation: run operations expose gateway intent metadata (no raw arguments or secrets). `Suspended` is an active status, so completion waits keep polling until a terminal status. Suspension and resume occur automatically for deployments with `suspensionEnabled` and compatible pinned harness `sessionFormat`; there are no manual suspend/resume endpoints. A raw CLI attempt lost after resuming fails closed if its new epoch lacks a safe checkpoint.

Remote agents use kind `Remote`, protocol `A2A` or `Mcp`, a full `remoteEndpointUrl`, and optionally `remoteCredentialSecretId` and `registrationTtlSeconds`; `mcpToolName` selects the remote MCP tool. Executors include `RemoteA2A` and `RemoteMcp`. See [remote agents](../../docs/REMOTE_AGENTS.md) and [tenant scheduling](../../docs/TENANT_SCHEDULING.md). Queue saturation returns HTTP 429 with code `QueueFull`, rather than creating a failed run.

System administrators can change tenant `schedulingWeight` (1 to 1000, default 1), use server settings for credential/run-token expiry policies and queue bounds, and run the master-key rotation method. Rotation uses keys already configured on the server and returns counts only; clients never supply key material to the endpoint. Keep old keys until a pass reports zero conflicts and failures.

LeaseBroker secret metadata uses `kind: "LeaseBroker"`, `brokerResource`, and optional `brokerAudience`; it rejects a static `value`. Issuance/revocation endpoints and provider authorization are operator-only settings. See the [provider contract](../../docs/CREDENTIAL_BROKER.md) for TTL, tombstone, and tenant authorization requirements.

`await client.Runs.GetPlacementAsync(runId, token)` returns read-only placement diagnostics. `await client.Runs.GetDatabaseUsageAsync(runId, token)` returns exact SQL attempts inside completed instrumented lifecycle scopes. Placement eligibility is advisory and reserves no capacity. External invocation wait is best effort: when the server wait budget is full, it returns the accepted run for polling. Resident synchronous delegation instead fails with `DelegationCapacityExhausted` before child creation when no wait slot is available. Poll an accepted run's ID instead of submitting another invocation.
