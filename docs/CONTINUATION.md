# Durable continuation and workspace caches

A deployment can set `suspensionEnabled: true` to release its worker while a permission approval waits for a person or a delegated child runs. This is opt-in. It requires Process execution, an isolated HOME, a harness profile with `supportsResume` and a nonempty `sessionFormat`, and an active tenant artifact store. KubernetesJob and remote executors reject this configuration. Suspension does not turn an arbitrary process kill into a safe checkpoint.

When an approval needs review, Garrison persists the pending approval and answers the harness with a denial rendered from `builtin/continuation-wait`, carrying the `GARRISON_CONTINUATION_WAIT` protocol marker and asking it to finish its turn without polling or executing more tools. An active tenant Task template named `continuation-wait` can replace this instruction and must retain the marker. The Codex app-server relay also reads the typed `suspended` response. The harness must finish its current turn normally and report its session identifier. A killed, cancelled, timed-out, or sessionless harness fails rather than reporting successful suspension. This boundary deliberately declines the unreviewed operation before saving state. It does not execute the pending operation in the background.

After the harness stops, the worker archives `work/`, `home/`, and `config/` and uploads the archive to the deployment's artifact store as `.garrison/continuation.zip`. Archives reject links and paths outside those directories. Capture and restore bound entry count and uncompressed bytes; download and upload also obey the artifact file limit. Restore verifies the artifact SHA-256 and publishes a complete temporary directory atomically. Unix file permission bits are retained. Config and HOME may contain credentials or private session data. The reserved `.garrison/` namespace is internal: ordinary artifact listings, read/content/download-link/delete routes, and pipeline artifact handoffs cannot expose these archives, even to administrators. Only the trusted execution service mints a short-lived download ticket for a worker. Internal uploads use `POST /v1.0/api/node/runs/{runId}/artifacts` with the worker node credential and a live node/epoch/repair lease fence. The upload transport is a private worker callback omitted from assignment serialization; the harness run bearer cannot create these archives. Public REST and MCP artifact uploads reject the reserved namespace even for administrators. Prepared-cache restore additionally rejects every archive entry outside `work/`, so it cannot introduce HOME or configuration state. An archive that exceeds a limit cannot suspend the run.

The marker itself has no authority: checkpoint acceptance requires a persisted current-epoch approval wait (including a human/timeout decision that raced the upload) or a child wait created during the current lease. Ordinary model/tool text containing the marker completes normally and cannot requeue the run or reset its deadline. Old approvals and completed waits from earlier lease epochs do not qualify. The control plane accepts the checkpoint only at the current node and lease epoch, with a matching session format and run-owned artifact. It locks the run while checking the effect journal. A dispatched or unknown operation prevents suspension. On acceptance the status becomes `Suspended`, with no lease, deadline, node affinity, or worker slot. Pending approvals remain available for review. Suspended runs are excluded from active concurrency and queue accounting and are retained until they finish or are explicitly deleted.

An approval decision or child completion requeues the run once every pending approval and child wait has resolved. A decision that arrives during upload is handled too. Any capable Process worker can download the checkpoint and resume the same session. The compiler renders `builtin/continuation-resume`, or a tenant template named `continuation-resume`, with `continuation.reason` and a `continuation.decisions` list containing `approvalId`, `tool`, `decision`, and `reason`. Delegation adds `continuation.children`, with each child's `runId`, `agent`, `status`, `result`, and `error`. It uses the harness profile's normal prompt delivery, including argument-based prompts. The saved session provides completed tool history; the continuation prompt tells the harness to honor the reviewed decision without repeating completed effects. Cancellation of a suspended run is immediate.

Supported boundaries are permission approvals and synchronous child invocations through Garrison MCP tools. A synchronous child invocation persists its wait and returns the checkpoint marker immediately; the parent saves its session, releases its slot, and resumes with the child results after all children finish. A maintenance sweep handles lost completion notifications and child failures outside the normal worker completion path. Arbitrary A2A `input-required` waits do not trigger durable suspension, because remote executors have no local resumable session contract. Harnesses that cannot finish and resume a permission checkpoint remain unsupported. The deterministic integration tests cover both Claude stream-json and Codex app-server protocol paths, saved session files, loss of the original worker, another node restoring the same session, and a historical 10,000-record passive-state check holding no active leases. That record count is not an actual CLI population or an acceptance threshold. Actual process-session and archive-policy evidence is recorded in [D062 scale validation](testing/D062_SCALE_RECOVERY.md) and [D063 continuation validation](testing/D063_CONTINUATION.md). The recorded CLI compatibility gate below separately runs the installed binaries. The credentialed Compose gate checks tool effects across actual worker replacement.

## Archive size policy

Continuation preserves the complete isolated `work/`, `home/` and `config/` trees. It does not silently omit Codex plugin/app catalogs, caches or session files to fit a limit. Catalog-enabled accounts can therefore need a larger archive than the default upload policy allows. The operator chooses that policy explicitly; Garrison does not enlarge a limit automatically.

`Artifacts.MaxFileBytes` bounds the compressed ZIP at capture upload and restore download. Its default remains **16 MiB**; its configurable range is **1 KiB to 256 MiB**. The former 64 MiB upper clamp prevented a valid explicit setting from accommodating an approximately 80 MiB archive. The worker's uncompressed snapshot guard remains **256 MiB total** across the three trees, with **100,000 entries**. Raising the compressed cap does not relax either extraction guard, path safety, checksum checks, session identity or epoch fencing. ZIP headers and compression overhead also count toward the compressed limit, so leave headroom rather than setting it equal to the estimated HOME size.

For example, allow a 96 MiB compressed checkpoint while retaining the existing 128 MiB REST request ceiling:

```json
{
  "Artifacts": { "MaxFileBytes": 100663296 },
  "Rest": { "MaxRequestBodyBytes": 134217728 }
}
```

The per-file cap can also be supplied as `GARRISON_ARTIFACT_MAX_FILE_BYTES=100663296`. Use matching server and worker builds, since older builds retain the 64 MiB clamp. Apply these node-local settings consistently to control-plane replicas and restart them so newly compiled assignments carry the policy. Ensure every upload proxy/ingress permits at least that body size; if selecting a cap above the default 128 MiB REST ceiling, raise `Rest.MaxRequestBodyBytes` or `GARRISON_REST_MAX_REQUEST_BODY_BYTES` as well. The checkpoint travels through the private binary node REST route, so it does not need a larger MCP JSON message limit. Filesystem stores need durable storage; larger transfers also need sufficient timeout, disk and memory. Current capture, transfer and restore buffer archive/file bytes, so compressed size is not a peak-memory estimate.

This cap is shared with ordinary collected artifact files. Normal glob collection additionally obeys `Artifacts.MaxTotalBytes` and its file-count limits. A continuation snapshot is one internal execution-state archive and uses the file cap independently of that normal collection aggregate; it is not a way to expose HOME through artifact globs.

Downloads also use the current configured cap for database, filesystem and S3 stores. Lowering it can therefore make an older larger artifact unavailable until the cap is raised again.

An oversized archive fails the execution with a size-limit error before reporting `Suspended`; the worker never uploads a truncated checkpoint. A server-side mismatch independently rejects it. A failed or cancelled checkpoint preserves the workspace when `KeepOnFailure` is selected and removes private HOME/config directories for ordinary non-conversation execution. Conversation retention follows its existing separate lifecycle. Failed restore removes staging and never publishes a partial destination. Operators can then choose a larger bounded cap or keep the failure; excluding arbitrary HOME paths is not an automatic recovery action.

The bounded regression captures an incompressible 80 MiB Codex-shaped HOME fixture, verifies default rejection, explicitly opts into 96 MiB, transfers through the node route and signed download, and compares bytes after restoring at another root. It uses synthetic data and no model access. See [D063 continuation validation](testing/D063_CONTINUATION.md).

## Session formats

A harness profile's `sessionFormat` is its compatibility contract. Built-in Claude Code uses `claude-project-jsonl-v1`, Codex exec and app-server use `codex-rollout-jsonl-v1`, Mux uses `mux-session-json-v1` (recorded schemaVersion 1 JSON), Gemini uses `gemini-chat-jsonl-v1` (chat metadata and message/update JSONL), provider-api uses `garrison-provider-history-json-v1` (provider/model/endpoint-bound message history), and the deterministic harness uses `garrison-fake-session-v1`. A checkpoint cannot resume under a changed contract. The archive includes a manifest binding the session ID and format to its original workspace. When a Claude workspace root changes across workers, restoration relocates the project directory containing that session to the new workspace key while preserving its history bytes. Codex app-server resumes its saved thread with the current workspace explicitly supplied. Keep a profile's CLI image pinned until its saved-session compatibility has been tested. Changing the format disables restoration of older checkpoints instead of silently starting a fresh session. The `Recorded session compatibility` CI workflow builds the candidate worker image and resumes committed, sanitized recordings with actual installed Claude, Codex exec, Codex app-server, Mux, and provider-api binaries. Its Gemini-enabled image also tests the optional pinned Gemini CLI. A local provider protocol server asserts that each resumed request contains the saved first-turn history; containers have no external network or real credentials. Run `scripts/check-session-compatibility.sh IMAGE`, adding `GARRISON_SESSION_GEMINI=true` for the optional image. The gate also requires each seeded profile, its recorded metadata, and the gate's pinned format contract to agree; missing or changed formats fail before invoking a CLI. Existing recordings are read-only and are never regenerated by CI. See `scripts/session-compatibility/README.md`. Session-reader compatibility alone does not enable durable permission suspension for an otherwise unsupported profile.

## Workspace caches

Workers enable a private node-local git mirror cache by default under `<WorkRoot>/.git-cache`. Set `GitCacheEnabled` or `GARRISON_WORKER_GIT_CACHE_ENABLED=false` to disable it. Mirror keys include the repository and credential identity, and preparation serializes updates for the same key. A warm mirror is refreshed before cloning. Clones use `--reference-if-able` with `--dissociate`, so later mirror eviction or another run's writes cannot change a running workspace. If mirror creation or refresh fails, preparation tries a normal clone.

A GitRepository workspace with a full immutable commit and a deployment artifact store also stores a prepared workspace archive. Its content key includes tenant, workspace identity and update timestamp, commit, clone depth, seeded files, and credential reference/update timestamp. A branch or tag uses the git mirror but does not reuse a prepared archive because its target may move. Prepared archives include only `work/`, before execution files, HOME, config, or harness-generated state exist. Another node can restore the signed archive instead of cloning. Store failures warn and leave a successfully prepared workspace usable. Git HTTPS URLs cannot embed credentials; use a bound git secret. SSH URLs may specify a username but cannot embed a password. Git askpass credentials live outside the cached work tree. Prepared snapshots share normal artifact retention; deleting their producing run or artifact turns future lookups into misses.

`garrison.worker.workspace.cache` records hit/miss counts per tenant, agent, deployment, and cache layer. The worker Grafana dashboard shows hit rates. Existing workspace-stage timing includes clone or archive restoration. Tests use real git through a local SSH transport shim, validate independent cold/warm clones, and compare SHA-256 file bytes after an artifact cache restore on another worker. A separate three-round probe exercised real loopback HTTPS with controlled response delay and bandwidth pacing, measured Git and snapshot wire bytes, and verified identical restored work trees. Warm mirrors received zero new pack bytes; prepared snapshots traded additional archive bytes for restoration without cloning. See [D063 cache acceptance](testing/D063_CACHE.md). These bounded shared-host measurements do not establish production WAN latency or a universal cache speedup.

Filesystem checkpoint stores require persistent server storage. Docker Compose mounts a named server-data volume at `/app/data`; place filesystem artifact stores beneath it. Kubernetes operators should use durable shared storage or an S3 artifact store compatible with their replica topology.

The D-060 10,000-file probe measured cold/warm preparation and received payload and verified identical work-tree SHA-256 for uncached clones, both mirror states, and a prepared snapshot restored at another root. The warm mirror received zero new pack bytes. The prepared archive was larger than a git clone for the incompressible fixture because it retained both work files and git objects. See `benchmarks/D060_MEASUREMENTS.md` and `benchmarks/workspace-cache.sh`; these shared-host local-transport timings are indicative rather than production network guarantees.
