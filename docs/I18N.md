# Internationalization

The Garrison dashboard is translated end to end. Every visible string, tooltip, placeholder, `aria-label`, toast, error message, and empty state comes from a translation catalog. Dates, numbers, durations, currency, byte sizes, and lists are formatted with `Intl` for the active locale.

## Locales

| Code | Language | Direction | Purpose |
|---|---|---|---|
| `en` | English | LTR | Source of truth. Every key exists here first. |
| `de` | German | LTR | Complete translation. Exercises long words and text expansion. |
| `ja` | Japanese | LTR | Complete translation. Exercises CJK glyphs and line breaking. |
| `zz` | Pseudo (RTL) | RTL | Generated from English: accented letters, about 35% padding, wrapped in `⟦ ⟧`. Use it to spot hard-coded strings, truncation, and RTL layout bugs. |

The registry lives in `dashboard/src/i18n/localeRegistry.js`. It maps aliases (`de-AT`, `ja-JP`, `pseudo`, `rtl`) to canonical codes and tells `Intl` which locale to use. `zz` formats with `ar` so numerals and dates also render right to left.

## How the active locale is chosen

1. The `?lang=` query string (handy for screenshots and bug reports).
2. The saved choice in `localStorage` under `garrison.locale`.
3. The browser language.
4. English.

Changing the language from the top bar or the login page saves the choice and updates `<html lang>` and `<html dir>` immediately. No reload is needed.

## Files

| Path | Contents |
|---|---|
| `src/i18n/locales/en.js` | English catalog. |
| `src/i18n/locales/de.js` | German catalog. |
| `src/i18n/locales/ja.js` | Japanese catalog. |
| `src/i18n/resources.js` | Deep-merges `de` and `ja` over English and generates `zz`. |
| `src/i18n/index.js` | i18next bootstrap and `lang`/`dir` sync. |
| `src/i18n/formatters.js` | Locale-aware formatters. |

## Key layout

| Namespace | What lives there |
|---|---|
| `common` | Shared actions, states, errors, toasts, units. |
| `errorCodes` | Messages for the server's stable error codes (`AuthorizationDenied`, `ValidationFailed`, and so on) plus HTTP status fallbacks. |
| `enums` | Labels for every enum the API returns, grouped by enum name. Raw enum values are never shown. |
| `nav`, `topbar`, `login`, `roles` | Application shell. |
| `components` | Shared components: tables, filters, forms, modals, charts. |
| `resources.<id>` | One block per record page: `title`, `subtitle`, `add`, `create`, `edit`, `view`, `deleteTitle`, `emptyTitle`, `emptyBody`, then `columns`, `fields`, `hints`, `steps`, `sections`, `actions`, `errors`. |
| `views.<id>` | Custom pages such as Home, Invoke, Run detail, Settings, and API Explorer. |
| `wizard`, `tour` | Setup wizard and guided tour. |

Settings labels fall back to the setting path when `views.settings.fields.<path>` has no entry, so new server settings appear without a dashboard release.

## Rules for contributors

- Never write user-facing text in JSX or JavaScript. Add a key to `en.js`, then add the same key to `de.js` and `ja.js`.
- Use interpolation (`{{name}}`) instead of string concatenation, because word order differs between languages.
- Use i18next plurals for counts: add `key_one` and `key_other` in English. Japanese uses the same text for both.
- Never use em-dashes in any catalog. Restructure the sentence instead.
- Format values with the helpers in `formatters.js`, passing `i18n.language`. Do not call `toLocaleString()` without a locale or build dates by hand.
- Prefer CSS logical properties and flex or grid layouts so RTL works without special cases.
- Leave room for German, which runs about 30% longer than English. Check the `zz` locale at 390 px wide.

## Tests

`npm test` runs `src/tests/i18nKeys.test.jsx`, which fails when:

- a static `t('...')` key in the source does not exist in English;
- a key generated by a resource configuration (columns, fields, filters, steps, row actions) does not exist in English;
- a route is missing its navigation label or tooltip;
- an enum value has no label;
- `de` or `ja` has a key English lacks, or lacks a key English has (plural suffixes are compared by base key);
- a translation drops or renames an interpolation placeholder;
- any catalog contains an em-dash;
- the pseudo-locale is incomplete or loses placeholders.

The Playwright suite switches to German and to `zz` and checks that `lang`, `dir`, and the visible text update and persist across a reload.

## Adding a locale

1. Add an entry to `LOCALES` in `localeRegistry.js` with its code, English name, native name, and direction. Add any aliases.
2. Create `src/i18n/locales/<code>.js` with a full copy of the English keys, translated.
3. Import it in `resources.js` and add it to the `resources` object with `deepMerge(en, <code>)`.
4. Add it to the parity checks in `src/tests/i18nKeys.test.jsx`.
5. Run `npm test`, then check every page in the new locale at 1280, 768, and 390 px.
