# Cluster external-effect acceptance

`BUILD=1 scripts/test-cluster-effects.sh` builds the server and worker from the checkout, creates an isolated k3d cluster, imports the test-only worker layer, and runs twelve external HTTP effect scenarios (nine worker-loss cases and three rolling control-plane replacements). Docker, k3d, kubectl and Python 3 are required. The script refuses an existing cluster name, uses an explicit private kubeconfig/context, and removes only its own cluster on exit. Override `CLUSTER_NAME`, `WORK_DIR`, `API_PORT`, `HTTP_PORT`, `SINK_PORT` and `RESULTS` for concurrent runs. `BUILD=0 IMAGE_TAG=...` imports existing local images instead.

The fixture sink runs in a separate pod, records every request, and performs no deduplication. Tests stop workers before dispatch, after an external commit, and after successful completion, for each of AtMostOnce, Journaled and AtLeastOnce. A force-delete acknowledgment is insufficient: the driver waits until the old container is no longer running in the node runtime before releasing the effect barrier. Each report records the pod UID, container ID, process-stop time, run attempts and individual receipts.

AtMostOnce and Journaled conservatively fail a lost running process with NodeLost and do not replay it. AtLeastOnce retries: a loss before the effect yields one receipt from attempt 2; a loss after the effect yields two receipts from attempts 1 and 2. Completed runs stay completed under all three policies. Journaled does not promise deduplication of arbitrary shell HTTP traffic. This fixture verifies the conservative process-loss boundary; gateway operation state and stale-session fencing have separate effect-boundary suites.

The weekly/manual `cluster-effects` job in `.github/workflows/effect-safety.yaml` can run this cluster driver and upload its JSON. Its `effect-boundaries` job tests both database providers independently. CI is an optional execution path; local execution and retained evidence are sufficient for P12.34 acceptance under D063.

## D060 evidence

The tracked report `k8s/tests/effect-safety/evidence/d060-policy-matrix.json` passed all nine cases on 2026-10-16 UTC, using a private single-node k3d cluster with PostgreSQL 17, one server and one four-slot worker. These were existing local development images, not a released build. The server pod image ID was `sha256:2036e5e5190e4d6493240d23ccdcdea27271d9f8124d8d2b02cd61ddfd64bc58`; the policy fixture worker/sink image ID was `sha256:da0f652e73f68e2f476d944639fc8e2176409a1c3b657467725a909a4921d504`. This is historical process-loss policy evidence. The current local multi-control-plane partition/failover acceptance is described in `D063_RECOVERY.md`; physical placement does not add a separate acceptance gate.

An initial trial exposed a test race: force-deleted pods could still execute before the kubelet stopped them. The verified report was rerun after adding the runtime termination barrier. The successful assertions do not depend on the API object merely disappearing.

## Gateway latency experiment

`RUN_GATEWAY_BENCHMARK=1` additionally runs `gateway.py`. A parent run issues alternating paired administrator and fenced Journaled MCP child-start calls after warmup. The report includes paired samples, completed journal operations, bounded operator/run intrinsic histograms, stage metrics and exact scoped database usage. No fixed latency budget is imposed by default. An operator can explicitly supply `gateway.py --max-overhead-ms N` to gate the paired diagnostic against a chosen budget. The earlier five-millisecond example is provisional, not a user-approved acceptance requirement.

The full paired diagnostic includes transport and child admission. Intrinsic gateway-owned timing excludes awaited tool dispatch. These measurements are distinct; a histogram bucket upper bound is not an exact sample percentile. The D062 final experiment completed all 210 journal operations and measured fenced intrinsic mean 4.087 ms with histogram p99 upper bound 25 ms. Full paired positive-difference p99 was 18.24 ms. See `D062_SCALE_RECOVERY.md` and `benchmarks/evidence/d061/d062-diagnostics-gateway.json` for provenance and limits.

For historical comparison only, the D060 diagnostic completed 200 paired samples after ten warmup pairs: administrator p99 175.83 ms, gateway p99 372.22 ms, positive-difference p99 260.91 ms. That report compared the then-plan five-millisecond example and failed it. D062 superseded that interpretation with instrumentation and optional caller-selected budgets; the historical result does not leave P12.31 open. Raw D060 samples remain in `k8s/tests/effect-safety/evidence/d060-gateway-p99.json`. The experiments had different concurrent host load, so their difference is not a controlled estimate of optimization speedup.
